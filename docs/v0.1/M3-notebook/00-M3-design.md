## 1. 目标

M3 结束时：

1. **笔记本**：工作区的成员与管理员创建笔记本，创建者是它的管理员；列表、读取、改名、改 `workspace_access`、删除（软删除，60 天后物理清除）。名称遵守页面标题的规则（总体设计 3.5）。
2. **成员与有效角色**：笔记本角色 `admin`、`editor`、`reader`；成员列表、添加（从工作区的有效成员中选，访客只能这样进来）、改角色、移出、离开。有效角色是显式角色与 `workspace_access` 给出的默认角色中较高的一个；看不到的笔记本一律 404，工作区管理员也看不到别人的私密笔记本。
3. **工作区成员关系结束时的级联**：离开工作区、被移出、被停用都结束他在这个工作区里的笔记本成员身份。他自己离开或停用时，若他是某个还有别的成员的笔记本唯一的管理员，就拒绝（409 `notebook.sole_admin`）；被工作区管理员移出时不拒绝，那里成为无主。
4. **无主笔记本**：没有有效管理员的笔记本。工作区管理员看到清单（名称、原所有者、成为无主的时刻、最后更新、大小），可以接管（成为它的管理员）或删除；原所有者回到工作区时，尚未被接管、也未被删除的自动归还给他。接管、删除、归还写进审计记录，工作区管理员可以查看。
5. **扩展点**（总体设计 12.4）：
   - 注册 M2 建立的：工作区成员身份结束（否决者与事件）、恢复（事件）、删除（事件）、权限的笔记本级、清理注册表；M1 建立的新手引导步骤。
   - 建立：笔记本删除事件、可见性变化事件、笔记本占用（只读）。
   - 在 workspace 模块补两个事件：成员加入、成员角色变化（M2 移交第 6 项）。
6. **前端**：左栏的"我的笔记本 / 团队笔记本"两组与新建笔记本；笔记本的首页与设置（常规、成员）；工作区设置里的无主笔记本页（清单、接管、删除、审计记录）；新手引导的第一个个人笔记本。
7. **M2 移交**的 6 项，每项落实或说明理由（第 7 节）。

## 2. 范围

**做**：第 1 节各项，以及它们的接口描述、页面与端到端故事。

**不做**：

| 事项 | 理由与去处 |
|---|---|
| 笔记本的模式（`mode`）、升级状态、来源根页面 | M10、M11 随契约一起加列。M3 没有页面，模式没有可以约束的东西；列先加上，每次读取都要带一个永远是 `standard` 的字段 |
| 页面、节点树 | M4。笔记本的首页在 M3 只显示名称与"还没有页面" |
| 恢复已删除的笔记本 | 与工作区相同（M2 总设计第 2 节）：v0.1 没有这个操作，60 天内运维可以从数据库恢复 |
| 笔记本的邀请、按邮箱添加成员 | 成员只能从工作区的有效成员中添加；工作区之外的人先经工作区邀请加入 |
| 一次添加多个成员 | 每次一个；批量插入要按键排序（Nerve 的约定五），单个插入不需要 |
| 访客的笔记本角色上限 | 不设上限：访客只能经显式加入访问笔记本（总体设计 3.3），给他什么角色由笔记本管理员决定 |
| 按成员汇总的存储占用 | M7（附件）之后才有意义；M3 只在无主清单里给每个笔记本的大小 |
| 实时推送 | M5。M3 建立可见性变化事件，M5 注册 |

## 3. 完成标准

- 本 M 的故事全部通过（本地 `make e2e` 与持续集成），之前各 M 的故事仍然通过。用到 `registerOnboarded` 的故事随引导的新步骤调整（A9 改为三步）：

  | 故事 | 内容 | 版本 |
  |---|---|---|
  | N1 创建笔记本 | 工作区的成员与管理员创建笔记本，成为它的管理员，它出现在"我的笔记本"里；访客答 403；名称不合规则答 422。落库：笔记本与成员行 | 页面、PAT 接口 |
  | N2 私密与分组 | `workspace_access = none` 的笔记本，非成员看不到：列表里没有，读取答 404，工作区管理员也一样。加了第二位成员，它对两人都移到"团队笔记本" | 页面、PAT 接口 |
  | N3 对工作区开放 | 管理员把 `workspace_access` 改为 `viewer` 或 `editor`：工作区的成员与管理员看到它，有效角色是 `reader` 或 `editor`；访客看不到 | 页面、PAT 接口 |
  | N4 笔记本成员 | 管理员从工作区成员中添加成员（含访客）、改角色、移出；有效角色取显式角色与默认角色中较高的。非管理员答 403；不能改自己的角色（409） | 页面、PAT 接口 |
  | N5 离开笔记本 | 成员离开；唯一的管理员不能离开（409 `notebook.sole_admin`），哪怕只有他一人 | 页面、PAT 接口 |
  | N6 改名与删除 | 管理员改名；删除需要输入名称确认，之后所有人都看不到它。落库：软删除连带成员行 | 页面、PAT 接口 |
  | N7 离开工作区的级联 | 离开工作区结束他的笔记本成员身份；他是某个还有别的成员的笔记本唯一的管理员时，离开被拒（409 `notebook.sole_admin`）；只有他一人的私密笔记本成为无主 | 页面、PAT 接口 |
  | N8 移出与停用的级联 | 工作区管理员移出唯一的管理员：不被拒绝，那里成为无主，其余成员照常使用。停用被拒的条件同 N7（页面与 `users deactivate` 都给出原因） | 页面、PAT 接口、命令行 |
  | N9 接管无主笔记本 | 工作区管理员在无主清单里看到它（名称、原所有者、时刻、大小），接管后成为它的管理员；私密的仍然私密。非管理员答 403。审计记录里有这一条 | 页面、PAT 接口 |
  | N10 删除无主笔记本 | 工作区管理员删除无主笔记本；审计记录里有这一条 | 页面、PAT 接口 |
  | N11 归还 | 原所有者经接受邀请或 `workspaces reactivate-member` 回到工作区：他名下尚未被接管、也未被删除的无主笔记本归还给他，审计记录里有这一条；已被接管的不归还 | 页面、PAT 接口、命令行 |
  | N12 引导的笔记本一步 | 新账户在引导中创建第一个个人笔记本；没有工作区或只是访客的，看到说明后继续 | 页面、PAT 接口 |
  | N13 连带删除与清理 | 删除工作区连带它的笔记本、成员行与审计记录；超过保留期之后由后台任务物理删除，保留期内的不动 | 页面、PAT 接口、后台任务 |

- **对等验收的例外**（总体设计 10.1）：N8、N11 的命令行部分与 N13 的清理只能由命令行或后台任务完成，只有那一个版本。
- 本 M 建立的扩展点已建好，并有测试证明注册者能挂上去（第 8 节）。M2 的扩展点已注册：第一个注册者经每条触发路径（移出、离开、停用的接口与命令行、接受邀请、`reactivate-member`、删除工作区）各有整个程序上的行为测试（M2 移交第 1 项）。
- 权限矩阵覆盖每个操作，加上笔记本级的列（第 9 节）。
- 满足总体设计 12.5 的其余各项；M2 移交的 6 项全部处理（第 7 节）。

## 4. 关键决定

| 决定 | 选择 | 放弃的方案及原因 |
|---|---|---|
| 模块 | 新模块 `notebook`：笔记本、成员、无主处理、审计记录、笔记本级的权限事实。它经端口读工作区（按 slug 找、锁住工作区行、成员的角色）与账户的公开资料，由组合根接上 | 放进 workspace 模块：M4 起的页面全部挂在笔记本下，workspace 会变成大杂烩 |
| 权限的笔记本级 | access 加 `LevelNotebook`：事实端口 `NotebookFacts` 声明在 `access/app`，由 notebook 模块以只凭连接池的构造实现（`notebook.NewFacts(pool)`）。判定：不是工作区的有效成员 → 看不到；有效角色为空 → 看不到；有效角色不在规则的集合里 → 403。`shared.Target` 加 `NotebookID`，`Grant` 加 `NotebookRole`（有效角色）。工作区级的代码不变 | 用例自己算有效角色：M4 起每个页面操作各算一遍，矩阵无处统一 |
| 有效角色 | 显式角色与默认角色中较高的一个，高低经显式的次序表 `reader < editor < admin`；默认角色只给工作区的成员与管理员：`none` 没有，`viewer` 是 `reader`，`editor` 是 `editor`。列表在 SQL 里按同一条规则过滤，一个集成测试核对"列表的结果"等于"对每个笔记本逐个判定 `notebook.read`"（Nerve 3.4 的做法） | 默认角色也给访客：总体设计 3.3 明确不给 |
| 成员关系的行 | 每对（笔记本，账户）在 `notebook_members` 中只有一行，`ended_at` 记结束的时刻，恢复即清空，与 `workspace_members` 相同。添加以前离开过的人时恢复那一行，角色取这次给的 | 每次加入插一行：归还要找"原来那一行"，多行时规则含糊 |
| 唯一管理员 | **规则一**：笔记本唯一的有效管理员不能离开，哪怕只有他一人（409 `notebook.sole_admin`），与工作区的规则一相同；只有一人时他可以删除笔记本。改角色不能改自己的（409 `notebook.own_membership`），也不能移出自己。判定在锁下，所以改完之后至少还剩发起操作的那位管理员。**规则二**：他自己离开工作区或停用账户时，他是某个还有别的有效成员的笔记本唯一的有效管理员，就拒绝，原因里列出这些笔记本的名称；被工作区管理员移出时不拒绝（见下一行）。修订总体设计 3.3、3.4 | 照原文，移出也拒绝：他离职又联系不上时只有他能提升别人，工作区管理员永远移不掉他，服务器管理员也停用不了他（负责人确认，2026-10-02） |
| 无主 | **无主 = 没有有效管理员**。成员关系结束时，他是唯一的有效管理员的笔记本成为无主：记下 `ownerless_since` 与原所有者 `former_owner_id`。可见性照常按有效角色：剩下的成员、按 `workspace_access` 有默认角色的人照常看得到、用得了；没有人能管理设置与成员，直到接管。私密而又没有成员的，谁都看不到，只出现在无主清单里。修订总体设计 3.4 | 照原文"变为无主，对所有人不可见"：一个对工作区开放的团队笔记本，创建者一走全工作区就看不到它（负责人确认，2026-10-02） |
| 无主笔记本的操作 | 工作区管理员经单独的资源寻址：`/workspaces/{slug}/ownerless-notebooks` 列出，`/ownerless-notebooks/{id}/take-over` 接管，`DELETE /ownerless-notebooks/{id}` 删除。不是无主的笔记本在这些路径上答 404：工作区管理员从这里看不到私密笔记本是否存在。接管：他成为管理员（新行、恢复已结束的行、或把他现有的角色升为管理员），`workspace_access` 不变 | 复用 `DELETE /notebooks/{id}`：无主的私密笔记本对工作区管理员本来就答 404，判定要为它开例外 |
| 归还 | 工作区成员身份恢复的订阅者：他名下（`former_owner_id` 是他）、尚未被接管与删除的无主笔记本，恢复他原来那一行（角色 `admin`），清除无主。只有恢复已结束的工作区成员关系时触发（接受邀请恢复、`reactivate-member`）：新加入的人名下没有无主笔记本 | 归还时问他要不要：多一个待确认的状态，而他本来就是这些笔记本的所有者 |
| 审计记录 | 表 `notebook_audit_events`：接管、删除、归还三种，记执行者、时刻、笔记本 id、名称的快照、原所有者。不引用笔记本（审计比笔记本活得久：笔记本清理之后记录仍在），随工作区一起删除与清理。工作区管理员在无主笔记本页查看，新的在前，游标分页（负责人确认，2026-10-02）。游标封套（总体设计 6.1、8.2 的 `shared`）在这里第一次用到，一次做完整，M8 复用 | 只写不读：没有人能看到，审计形同虚设 |
| 加锁 | 全局顺序接在工作区一支之后：`users → workspaces → workspace_invitations → workspace_members → notebooks → notebook_members`。笔记本的管理写（建、改、删、成员、接管、删除无主）先以 `FOR SHARE` 锁工作区行，再以 `FOR NO KEY UPDATE` 锁笔记本行，然后判定。工作区行的 `FOR SHARE` 与工作区成员关系的一切变化（它们持 `FOR NO KEY UPDATE`）串行，所以"笔记本成员 ⊆ 工作区有效成员"不靠别的路径：添加成员、建笔记本、接管在锁下读到的工作区成员关系就是提交时的。修订总体设计 13.1 第 5 条 | Nerve 的约定三（锁目标的工作区成员行）：在 Nerve Wiki 的顺序里工作区成员行排在笔记本之前，可行，但每条写路径要锁的行各不相同；锁工作区行一条规则覆盖全部，代价是同一工作区的笔记本管理写与工作区的成员变化互相等待，两者都少 |
| 级联在哪里锁 | 工作区成员身份结束的否决者在工作区行已锁之后，锁住他是有效成员的那些笔记本（`FOR NO KEY UPDATE`，按 `id` 升序），在锁下判断规则二；订阅者在同一事务里结束成员行、设置无主。期间他的笔记本成员关系不会变多：笔记本一侧的增长都要工作区行的 `FOR SHARE`，与结束路径持有的 `FOR NO KEY UPDATE` 冲突 | 订阅者里再判断一次：两处规则 |
| 可见性变化事件 | 值：工作区、一组账户（或 `Everyone`：工作区的全部成员）、时刻。笔记本模块自己的触发（建、加入、移出、离开、`workspace_access` 跨过 `none`、删除、接管、归还），加上它订阅的工作区事件（成员关系结束、恢复、加入、角色变化跨过访客、删除工作区）。M3 没有注册者，M5 注册 | 只靠笔记本模块的触发：降为访客会失去默认角色，新加入的人得到默认角色，M5 的事件流不知道（M2 移交第 6 项） |
| 工作区的两个新事件 | workspace 模块加"成员加入"（接受邀请插入新行）与"成员角色变化"（改角色）两个事件，在写入之后、同一事务里调用。这是修改 M2 的用例，属于总体设计 12.1 第 6 条的例外：扩展点在建立它的 M 漏掉了；修订 12.4 | 由笔记本模块定时比对：推送是否及时取决于周期，而 M5 要立即关闭连接 |
| 笔记本占用 | 只读的扩展点：注册者按笔记本 id 返回字节数，无主清单的"大小"是它们的和。M3 没有注册者，笔记本里还没有内容，大小如实为 0；M4（正文）、M7（附件）注册 | 无主清单不给大小：总体设计 3.4 要求它，而后面的 M 只能注册、不能改 M3 的用例 |
| 名称规则 | 页面标题的规则（总体设计 3.5）放进 `shared.CheckTitle`：去掉首尾空白，NFC 规范化，1–255 字节，禁止 `/ \ : * ? " < > \| # ^ [ ]`、控制字符，以及行与段落分隔符、双向控制字符（与 `CheckName` 相同的理由：它们能把名称显示成别的样子，`exe` 倒过来伪装成别的扩展名），不能以 `.` 开头或结尾，不能是 Windows 保留名。M4 的页面标题复用它；标题键（大小写折叠）由 M4 加，笔记本名称不要求唯一。修订总体设计 3.5 | 各模块各写一份：笔记本名称是导出 zip 的根目录名，必须与页面标题同一规则 |
| 新手引导的一步 | id `notebook`：在落点的工作区（最后访问的，或按名称的第一个）创建一个私密笔记本，名称默认"我的笔记"，可以改。没有工作区、或只是访客的，看到说明后继续。一次性创建，之后与引导无关（总体设计 3.3） | 由服务端在加入工作区时自动创建：与成员身份的生命周期绑在一起，离开再回来会多出一个 |
| 删除笔记本 | 软删除笔记本与它的成员行，用同一个时刻；发布笔记本删除事件，M4、M7 以这个时刻删除节点与附件。页面要求输入笔记本名称确认 | — |
| 删除工作区 | 笔记本模块订阅工作区删除：以事件的时刻软删除这个工作区的全部笔记本、成员行与审计记录，并发布一次笔记本删除事件（带这些笔记本的 id） | — |

## 5. 接口

新增 14 个操作，都在 `api/modules/notebook.yaml`：

| 方法与路径 | 认证 | 成功响应 |
|---|---|---|
| `GET /api/v0/workspaces/{slug}/notebooks` | Bearer | 200 `{data: Notebook[]}`（调用者看得到的，按名称） |
| `POST /api/v0/workspaces/{slug}/notebooks` | Bearer | 201 `Notebook` |
| `GET /api/v0/notebooks/{notebook_id}` | Bearer | 200 `Notebook` |
| `PATCH /api/v0/notebooks/{notebook_id}` | Bearer | 200 `Notebook`（名称、`workspace_access`） |
| `DELETE /api/v0/notebooks/{notebook_id}` | Bearer | 204 |
| `GET /api/v0/notebooks/{notebook_id}/members` | Bearer | 200 `{data: NotebookMember[]}`（有效的显式成员，按加入时间） |
| `POST /api/v0/notebooks/{notebook_id}/members` | Bearer | 201 `NotebookMember` |
| `PATCH /api/v0/notebook-members/{notebook_member_id}` | Bearer | 200 `NotebookMember` |
| `DELETE /api/v0/notebook-members/{notebook_member_id}` | Bearer | 204 |
| `POST /api/v0/notebooks/{notebook_id}/leave` | Bearer | 204 |
| `GET /api/v0/workspaces/{slug}/ownerless-notebooks` | Bearer | 200 `{data: OwnerlessNotebook[]}`（成为无主早的在前） |
| `POST /api/v0/ownerless-notebooks/{notebook_id}/take-over` | Bearer | 200 `Notebook` |
| `DELETE /api/v0/ownerless-notebooks/{notebook_id}` | Bearer | 204 |
| `GET /api/v0/workspaces/{slug}/notebook-audit-events` | Bearer | 200 `{data: NotebookAuditEvent[], next_cursor}`（新的在前，`?limit=&cursor=`） |

- **别的模块的修改**：`leaveWorkspace`、`deactivateMe` 的 `x-problem-codes` 加 `notebook.sole_admin`（第 4 节规则二）。`removeWorkspaceMember` 不加：移出不被笔记本拒绝。
- **结构**：
  - `Notebook`：`id`、`workspace_id`、`name`、`workspace_access`、`role`（调用者的有效角色）、`member_count`（有效的显式成员数）、`created_at`、`updated_at`。前端按"`workspace_access` 为 `none` 且 `member_count` 为 1"分出"我的笔记本"（总体设计 3.3）。
  - `NotebookMember`：`id`、`user_id`、`role`、对方的公开资料（显示名；邮箱只给工作区的管理员与成员，访客看到 `null`，与工作区成员列表相同）、`created_at`。
  - `OwnerlessNotebook`：`id`、`name`、`workspace_access`、`member_count`、`former_owner`（显示名与邮箱）、`ownerless_since`、`updated_at`、`size_bytes`。
  - `NotebookAuditEvent`：`id`、`action`（`taken_over`、`deleted`、`returned`）、`notebook_id`、`notebook_name`、`former_owner`、`actor`（公开资料）、`created_at`。
- **模块码**：

  | 码 | 状态 |
  |---|---|
  | `notebook.not_found` | 404 |
  | `notebook.member_not_found` | 404 |
  | `notebook.own_membership` | 409 |
  | `notebook.sole_admin` | 409 |

  另外：
  - 规则表的拒绝是平台码 `forbidden`（访客建笔记本、非管理员改设置与成员、非工作区管理员处理无主笔记本）。
  - 名称不合规则是 `name` 的字段错误；添加不是工作区有效成员的人是 `user_id: not_allowed`，已是有效成员是 `user_id: duplicate`。
  - 游标不合格式答 400 `bad_request`（结构在边界）。
- **限流**：不加新的桶。

## 8. 本 M 建立的扩展点与约定

**笔记本删除：事件**（M4 注册：软删除节点与正文；M7：附件）：

- 值：工作区、一组笔记本 id（删除工作区时一次带全部）、删除者、时刻。
- 订阅者在笔记本行软删除之后、同一事务内调用，以这个时刻作为自己的 `deleted_at`。没有否决者：删除是管理员显式的破坏性操作。

**可见性变化：事件**（M5 注册：关闭这些账户的事件流）：

- 值：工作区、一组账户 id 或 `Everyone`（工作区的全部有效成员）、时刻。
- 在引起变化的写入之后、同一事务内调用。触发见第 4 节；只改角色而不改可见性的（笔记本内的改角色、`viewer` 与 `editor` 之间）不触发。

**笔记本占用：只读**（M4、M7 注册）：

- 注册者按一组笔记本 id 返回各自的字节数，在调用方的读取里执行，不加锁；无主清单的大小是它们的和。

**workspace 模块的两个新事件**（M3 注册：可见性）：

- 成员加入：接受邀请插入新的成员行之后；值：工作区、账户、角色、执行者（账户本人）、时刻。
- 成员角色变化：改角色之后；值：工作区、账户、原角色、新角色、执行者、时刻。

**注册 M1、M2 的扩展点**：

- 工作区成员身份结束：否决者（规则二，只对离开与停用）与订阅者（结束笔记本成员行、无主、可见性）。
- 工作区成员身份恢复：归还无主笔记本、可见性。
- 工作区删除：软删除笔记本、成员行、审计记录，发布笔记本删除事件与可见性变化。
- 权限的笔记本级与本 M 的操作；清理注册表（笔记本排在工作区之前）。
- 新手引导的笔记本一步（id `notebook`）。

**全局加锁顺序**（修订总体设计 13.1 第 5 条）：

- 工作区一支接上笔记本：`users → workspaces → workspace_invitations → workspace_members → notebooks → notebook_members`。
- 笔记本的管理写先锁工作区行（`FOR SHARE`），再锁笔记本行（`FOR NO KEY UPDATE`），然后判定；按笔记本或成员关系寻址的，先不加锁读出所属的工作区与笔记本，锁住之后重读。锁的语句带 `deleted_at IS NULL`。
- 工作区成员身份的结束、恢复、删除已持有工作区行的 `FOR NO KEY UPDATE`，它们的笔记本注册者直接锁笔记本行（多行按 `id` 升序）。
- M4 的页面写入以 `FOR SHARE` 锁笔记本行（总体设计 8.3），不锁工作区行。

**横切约定**：本 M 新建的约定（笔记本级的判定与有效角色、锁工作区行的笔记本写、游标封套、按笔记本的前端 store 与 SWR 键、离开整页之后的焦点），收尾时经审查对照代码核实，补进总体设计第 13 节。
