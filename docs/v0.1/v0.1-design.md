## 0. 背景与目标

### 0.1 产品定位

Nerve Wiki 是一个面向团队的在线笔记系统，单租户、自部署：一个团队部署一套，成员在其中按工作区组织笔记本，笔记本里是有层级的 Markdown 页面。v0.1 只做 Markdown 页面；白板、脑图等笔记形态留给以后的版本。

灵感有两个来源：

- **Obsidian**：笔记就是 Markdown 纯文本，不是自定义的块结构；链接、属性、标签都写在文本里。数据朴素、可携带，对 agent 天然友好。Obsidian 是面向个人的本地客户端，Nerve Wiki 把它的数据哲学带到团队、工作区、个人与共享的在线场景。
- **Karpathy 的 LLM Wiki**：让 LLM 以"原始资料（只读）→ wiki 页面（LLM 维护）→ 约定（AGENTS.md）"三层结构，持续编译和维护一个互相链接的 Markdown 知识库，通过 ingest / query / lint 三种操作运转。目前它靠一个 skill 教 agent 手工维护 index.md、log.md 和目录约定；Nerve Wiki 把其中能机械推导的部分（目录、日志、健康检查、来源是否已消化）下沉为系统能力，用数据库实现。

**产品本身不调用任何 LLM。** 它是一个纯粹的团队笔记平台；对 agent 友好靠两件事：内容是原样的 Markdown，以及一套内置的 MCP 接口。

### 0.2 核心原则

1. **PG 是唯一真相。** 页面正文、目录树、版本、锁、索引全部存在 PostgreSQL 里，写入在一个事务里完成。"文件夹"是笔记本随时可以无损导出的视图，不是存储。
2. **字节保真。** 系统从不改写用户或 agent 写下的 Markdown：不格式化、不做"解析再序列化"的往返。唯一的例外是系统在移动或重命名页面时做的链接改写（4.5），它是确定性的、不改变含义的机械操作，记录在变更集里。
3. **结构写在 Markdown 里，数据库只做派生索引。** 页面类型、摘要、引用的来源、标签、别名写在 frontmatter 和正文链接里；数据库在同一个事务里解析出索引。导出因此无损，agent 只需要会写 Markdown。
4. **权限边界 = 笔记本。** 一个笔记本相当于 Obsidian 的一个 vault，也是 agent 的一个工作集。v0.1 只有笔记本级权限，没有页面级权限；链接也只在笔记本内部解析。
5. **Obsidian 兼容是验收尺子。** 导出的笔记本可以直接用 Obsidian 当 vault 打开，链接、图片、属性都正常；一个 Obsidian vault 可以导入成笔记本。
6. **单写多读。** 同一页面同一时间只有一个写者，人和 agent 遵守同一套锁规则；不做实时协同编辑。
7. **系统维护机械的部分，agent 负责需要判断的部分。** 目录、日志、链接完整性、来源是否已消化由系统计算；摘要、综合、交叉引用由 agent 写成 Markdown。
8. **页面能做的，接口都能做。** 前端只是公开 REST 接口的一个使用方；agent 通过 MCP 使用同一批用例。账户不区分人和 agent。
9. **轻量部署。** 一个可执行文件（内嵌前端）加一个 PostgreSQL。

### 0.3 与 Nerve 的关系

Nerve（团队项目管理系统）是一个独立的兄弟项目，本项目只把它当作参考：

- 它的技术选型和平台层设计（认证、工作区、接口规范、后端架构、测试方法）适合我们的，直接采用，不再重新讨论；不适合的，直接忽略。
- M0 的服务端平台层、M1 的账户认证模块、前端的令牌管理器，以 Nerve 的对应代码为起点**一次性拷贝**，改名、裁剪。之后两个项目独立演进：不同步代码，不维护差异清单，不产生任何运行时或构建时的耦合。
- 工作区模块参照 Nerve 已定稿的工作区设计自行实现，按本项目的需要裁剪。

| 笔记本模式 | 普通模式与 LLM Wiki 模式；来源区、虚拟目录与日志、lint 与健康度面板、LLM Wiki 模板、由 agent 执行的升级流程 |

### 1.2 v0.1 不做的功能

- 实时协同编辑；编辑器的 Live Preview（混合渲染）；Notion 式的块交互（斜杠菜单、块拖拽）
- 评论、@提及、通知；公开分享链接；图谱视图；收藏与最近访问
- 跨笔记本链接；嵌入整篇笔记 `![[页面]]`；块引用 `^id` 的校验
- 邮件发送、找回密码邮件、OAuth / SSO
- 移动端 App、离线使用
- 白板、脑图

以下几项明确留给 v0.2：同步 CLI（`pull`/`push` 本地文件夹，恢复 bash 批量处理能力）、团队认领式的 ingest 队列、按笔记本限定权限的 PAT、S3 兼容存储、版本的保留策略。

### 1.3 关键决策记录

| 决策 | 选择 | 放弃的方案及原因 |
|---|---|---|
| 内容的真相存在哪 | PostgreSQL（全 DB） | 磁盘文件为真相、PG 存元数据：两份真相无法在一个事务里写入，要靠文件监听和对账修补；直接改磁盘的 agent 绕过权限、锁和审计；只能单实例；备份两边不在同一时刻。它唯一的优势（本机 agent 用 bash）只对能登录服务器的人成立 |
| 内容格式 | 原样 Markdown 文本 | 自定义块结构（Notion）：agent 需要理解私有格式，导出有损 |
| 结构放在哪 | frontmatter 与正文链接，DB 派生索引 | 结构存 DB 字段：导出时要反向合成 frontmatter；agent 需要"改正文"和"改元数据"两套工具；两者可能不一致 |
| v0.1 的 agent 通道 | REST + 内置 MCP + zip 导入导出 | Git 通道：需要把 git 仓库和数据库双向对齐；自研同步客户端：冲突处理量大，推迟到 v0.2；WebDAV：挂载体验差，agent 在网络盘上批量读写很慢 |
| 编辑器 | CodeMirror 6 源码编辑 + 独立的阅读视图（Obsidian 的源码模式 + 阅读视图） | 所见即所得的块编辑器（tiptap、BlockNote、Milkdown）：保存时把整篇 Markdown 重新序列化，违反字节保真；Live Preview：工作量最大，v0.1 不需要 |
| 页面组织 | Notion 式的层级页面（`parent_id` 树，每个节点都是页面） | 传统的文件夹 + 文件 |
| 标题与文件名 | 同一个东西 | 自由标题 + 推导的文件名：出现两个名字，链接解析、MCP 路径、lint 都要处理两者的不一致 |
| 个人与共享 | 只有一种笔记本，"个人"是界面分组 | 每人一个固定的个人空间 + 团队笔记本：两套权限和生命周期规则，个人内容无法直接共享 |
| 隐私边界 | 在职成员的私密笔记本谁都看不到（含工作区管理员）；人走后由管理员显式接管 | 管理员全可见：私密笔记本名不副实；绝对私密：离职带走知识 |
| 笔记本模式 | 每个笔记本一种模式，模式是一份确定性契约 | 所有笔记本统一规则：LLM Wiki 的约束会加在人写的普通笔记本上 |
| 升级时对原笔记的权限 | 严格保全：正文一字不改、不许删除 | 允许重组：无法证明"没有丢内容"；重组属于升级之后的日常工作 |
| 移动与重命名 | 默认原子改写链接 | 先问再改；从不改写：来源不可变，来源里的断链将永远无法修复 |
| 前端 | 全新的轻量应用 | fork Nerve 前端：要删掉约 10 万行项目管理代码，笔记界面仍要全新写 |
| 中文搜索 | pg_trgm + ILIKE 兜底 | zhparser 等分词扩展：破坏"只要一个 PG"的部署 |
| 附件存储 | 本地磁盘（存储端口，v0.2 加 S3），按 ID 寻址 | 存进 PG 的 bytea：备份和 WAL 膨胀 |
| 实时推送 | SSE + PG `NOTIFY` | WebSocket：双向通道用不上，推送只需单向 |
| Markdown 解析与渲染 | 服务端（goldmark）是唯一权威：提取与渲染共用同一个解析入口，前端只展示；方言以 Obsidian 的实际行为为准，样例集逐项核对 | 前后端各自解析（goldmark + remark）：M0/P1 的差分测试表明，两个解析器在对抗性输入上做不到完全一致 |
| 数据库 locale | builtin `C.UTF-8`，`LC_COLLATE`、`LC_CTYPE` 同为 `C.UTF-8` | libc 的默认 locale：排序规则会随 glibc 升级而变化；`LC_CTYPE` 为 `C`：pg_trgm 切不出中文 |
| 开源协议 | AGPL-3.0 | Apache-2.0 / MIT：任何人可以闭源改成 SaaS |

## 2. 总体架构

```
          浏览器（Nerve Wiki 前端）                     Agent（Claude Code、Codex…）
     REST（Bearer JWT）· SSE（Bearer）                   MCP（Bearer PAT）
                  └──────────────────┬──────────────────────┘
                                     ▼
        ┌────────────────────── nervewiki（Go，单个进程）──────────────────────┐
        │  /api/v0 REST 接口（OpenAPI 生成）   /mcp MCP 服务   SSE 事件流          │
        │  业务模块（用例 + 领域规则）：每个写操作一个事务                          │
        │    写入管线：权限 → 写入守卫 → 写数据 → 变更集与版本 → 解析索引 → 事件   │
        │  River 后台任务：导入导出、各类清理                                     │
        │  托管前端静态文件（go:embed）                                          │
        └──────────────────┬───────────────────────────────┬─────────────────┘
                           ▼                               ▼
                 PostgreSQL 18                      附件存储：本地磁盘
       （正文、目录树、版本、索引、锁、LISTEN/NOTIFY）     （按 ID 寻址的文件块）
```

### 2.1 运行形态

- 默认部署：一个 `nervewiki` 可执行文件加一个 PostgreSQL 18。需要 HTTPS 时在前面加 Caddy 等反向代理。
- 应用本身无状态；但 v0.1 的附件存在本地磁盘，所以官方只支持单实例部署。
- 不需要 Redis、消息队列、对象存储、独立的前端服务器。

### 2.2 仓库结构

```
nerve-wiki/
  api/          接口契约：按模块拆分的 OpenAPI 描述，打包为 api/dist/openapi.yaml
  server/       Go 后端
  web/          前端（pnpm monorepo）
  e2e/          Playwright 端到端测试
  deploy/       docker compose、数据库角色授权等部署配置

  docs/         设计与过程文档
```

仓库根目录同时是 pnpm 工作区的根，包含 `web/` 下的应用和包以及 `e2e/`。

## 3. 领域模型

### 3.1 层级

```
实例（一次部署）
  └─ 工作区（workspace）          成员与角色、邀请
       └─ 笔记本（notebook）      成员与角色、workspace_access、模式
            └─ 节点树（node）      页面（page）与附件（asset），parent_id 构成层级
```

### 3.2 工作区与成员

照 Nerve 的工作区设计实现，按需裁剪：

- **工作区**：`slug` 满足 `^[a-z0-9_-]{1,48}$`，建好后不能修改；有一份保留名单（前端顶层路由、服务端顶层路径和预留词），由测试保证与路由一致。名称 1–80 个字符。
- **角色**：管理员 `admin`、成员 `member`、访客 `guest`，接口与数据库都用这三个字符串。规则按集合比较；需要比较高低时（3.3 的有效角色）经显式的次序表，从不按取值比较；三个值以外的角色什么都不允许。
- **邀请**：只有工作区管理员能管理。管理员在成员页复制邀请链接自己发给对方，系统不发邮件。邀请令牌不存库：由服务端密钥对邀请 id 做 HMAC 得出，需要时重新计算；令牌只放在链接的片段（`#` 之后）与请求体里，不进任何地址。邀请页公开，未登录的人在页内登录或注册。接受邀请要求登录邮箱与邀请邮箱一致。注册关闭时，持有效邀请、邮箱一致的人仍可注册。邀请从不改变已有的有效成员关系；成员关系结束时，删除发给他的待接受邀请。
- **唯一管理员**：工作区唯一的有效管理员不能离开；停用账户时，他是某个还有别的有效成员的工作区唯一的有效管理员，拒绝停用。移出、离开、停用会连带结束他在笔记本里的成员身份（3.4）：他自己离开或停用时，任何一处会因此失去唯一管理员而那里还有别的成员，就拒绝本次操作；被移出时不拒绝，那些笔记本成为无主。有成员的工作区必须有管理员：唯一的管理员独自停用之后，成员与访客要等管理员回来（或有人接受管理员邀请）才能加入。
- **停用与恢复**：停用账户结束他全部的工作区成员身份；`nervewiki users activate` 只恢复账户，成员身份由 `nervewiki workspaces reactivate-member` 逐个工作区恢复（要求账户已可用）。
- **创建开关**：`workspace.creation_enabled` 为 false 时，只能由服务器管理员用 `nervewiki workspaces create` 建工作区。
- 工作区删除为软删除，连带笔记本、页面、附件在同一个事务里软删除，60 天后物理清除。成员的私密笔记本也随之删除：页面要求输入 slug 确认，并写明这一点。

### 3.3 笔记本与权限

- **只有一种笔记本。** "个人"和"共享"是界面上的分组，不是两种实体。
- **笔记本角色**：管理员 `admin`、编辑者 `editor`、阅读者 `reader`。
- **`workspace_access`**：笔记本对工作区的开放程度，取值 `none` / `viewer` / `editor`，给工作区的正式成员（角色为成员或管理员）一个默认的笔记本角色。访客不享受这个默认权限，只能通过显式加入访问笔记本。
- **有效角色** = 显式的笔记本成员角色与 `workspace_access` 给出的默认角色中较高的一个，高低按显式的次序表 `reader < editor < admin`。
- **界面分组**：`workspace_access = none` 且只有我一个成员的笔记本，归入"我的笔记本"；其余归入"团队笔记本"。个人笔记本加了人就自然成为共享的，不需要搬迁数据。新手引导为新用户创建第一个个人笔记本（一次性创建，不与成员身份的生命周期绑定）。
- **谁能建笔记本**：工作区的成员和管理员；访客不能。
- **笔记本管理员**额外可以：管理成员和访问设置、修改模式（升级与降级）、删除或移动来源、强制解锁、删除笔记本。
- **唯一管理员**：笔记本唯一的有效管理员不能离开，哪怕只有他一人（他可以删除笔记本）；不能改自己的角色，也不能移出自己。他自己离开工作区或停用账户时，若他是某个还有别的成员的笔记本唯一的管理员，就拒绝；被工作区管理员移出时不拒绝，那个笔记本成为无主（3.4）。
- **笔记本名称**：遵守与页面标题相同的规则（3.5，`shared.CheckTitle`），因为导出时它是 zip 的根目录名；同一工作区内不要求唯一。
- **成员**：只能从工作区的有效成员中添加，访客也可以，角色由笔记本管理员决定。

### 3.4 隐私边界

这是产品层面的边界，不是加密层面的：自部署的运维人员有数据库权限，能读到所有内容。v0.1 不做端到端加密；管理命令也不提供"读取某个笔记本"这类后门。

**在职成员的私密笔记本**（`workspace_access = none`）：非成员一律看不到，工作区管理员也不例外。访问返回 404；管理员在任何列表里都看不到它的名字。例外是无主之后：无主清单与审计记录给工作区管理员它的名称，接管或删除要靠它（见下）。将来若有存储占用的视图，只按成员汇总，不列出笔记本（v0.1 不做这个视图）。

**成员离开、被移出或被停用时**：

| 他在这个笔记本里的状况 | 处理 |
|---|---|
| 不是唯一的管理员 | 结束他在这里的成员身份 |
| 是唯一的管理员，还有其他成员 | 他自己离开工作区或停用账户：拒绝，必须先提升别人为管理员。被工作区管理员移出：结束他的成员身份，笔记本变为**无主**，其余成员照常使用（他离职又联系不上时，否则谁都移不掉他） |
| 是唯一的成员 | 结束他的成员身份，笔记本变为**无主** |

**无主笔记本**：没有有效管理员的笔记本。

- 可见性照常按有效角色：剩下的成员、按 `workspace_access` 有默认角色的人照常看得到、用得了；没有人能管理它的设置与成员。私密而又没有成员的，谁都看不到。
- 工作区管理员能看到"无主笔记本"清单：名称、原所有者、成为无主的时刻、大小、最后更新时间。无主笔记本只对工作区管理员可见：别人按 id 处理它，答复与不存在相同（404）。
- 管理员可以**接管**（成为它的管理员，`workspace_access` 不变，私密的保持私密）或**删除**（软删除，60 天后物理清除）。两者都是显式操作，写入审计记录，工作区管理员可以查看。管理员只能接管，不能静默浏览。
- 原所有者回来（重新接受邀请或被重新启用）时，他名下尚未被接管、也未被删除的无主笔记本自动归还给他，同样写入审计记录。

**其他渠道使用同一条边界**：工作区全局搜索和任何列表只包含调用者有权看到的笔记本；MCP 和 PAT 的权限等同于账户本身；链接只在笔记本内部解析，反链不会跨越权限泄露信息。

### 3.5 节点树：页面与附件

**每个节点是一篇页面或一个附件。** 没有"文件夹"这种节点。

- 节点有 `parent_id`，根节点的 `parent_id` 为 null。一篇页面可以同时有自己的正文和子节点。
- 节点的身份是 id；路径由祖先链推算，不存储。
- 兄弟节点的顺序存在 `sort_order`（浮点数，拖拽时计算中间值）。
- **层级深度**不超过 10。
- **子页面列表由界面渲染**在正文下方，不写进父页面的 Markdown。

**标题就是文件名。** 页面的标题导出为 `<标题>.md`；附件的名称就是它的文件名（含扩展名）。规则：

- 写入前统一做 Unicode NFC 规范化。
- 同一个父节点下，页面标题和附件文件名共享一个命名空间，不区分大小写地唯一。比较用的键由应用计算：`NFC(fold(NFC(s)))`，即 NFC 规范化、Unicode 完整大小写折叠，再规范化一次（折叠的结果不一定是 NFC）。链接解析使用同一个函数。键存成单独的列（`COLLATE "C"`），所以唯一性不依赖数据库 locale。
  - 升级 Go 的 Unicode 数据（`golang.org/x/text`）时，折叠结果可能变化，要用 `nervewiki reindex` 重算全部键。
  - 完整折叠比 Obsidian（`toLowerCase`）更严：`Straße` 与 `Strasse` 算同名，导入时按重名处理。
- 长度 1–255 字节（UTF-8，约 85 个汉字）。
- 禁止的字符：`/ \ : * ? " < > | # ^ [ ]`、控制字符，以及行与段落分隔符、双向控制字符（它们能把名称显示成别的样子）。全角字符（`：？／` 等）允许。
- 不能以空白开头或结尾，不能以 `.` 开头或结尾；不能是 Windows 保留名（`CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`COM¹`–`COM³`、`LPT1`–`LPT9`、`LPT¹`–`LPT³`，不区分大小写，带不带扩展名都算；Windows 把上标的 ¹ ² ³ 当作数字）。
- 新建页面默认标题"未命名"，重名时自动加序号（"未命名 2"）。

**树操作**：

- 移动一个节点，它的整棵子树一起移动；移动不能形成环，不能超过层级上限。
- 删除一个节点，它的整棵子树一起进入回收站（3.10）。
- 移动或重命名一篇正在被别人编辑的页面是允许的：编辑者按 id 引用页面，只会看到面包屑变化。只有需要改写正文的页面（4.5 的链接改写）被别人锁住时，操作才会失败。

**导出映射**（与 Notion 导出 Markdown 的方式一致）：

```
项目A.md            ← 项目A 的正文
项目A/              ← 项目A 的子节点
  会议纪要.md
  架构图.png         ← 挂在项目A 下的附件
  需求.md
  需求/
    登录.md
```

- 没有正文、只有子节点的页面，导出时只生成目录，不生成空的 `.md`。
- 导出包附带 `.nerve/meta.json`，记录兄弟节点的顺序等界面信息，供重新导入时恢复；Obsidian 会忽略它。

### 3.6 页面正文

- 正文是原样的 Markdown 文本，逐字节保存（包括换行符风格和 BOM）。必须是合法的 UTF-8。
- 每篇页面有一个 `revision`（每次写入加 1）和 `content_hash`。
- 单篇正文不超过 5 MB。
- 标题不写进正文。页面顶部显示的大标题就是节点的标题。

### 3.7 附件

- 附件是节点树里 `kind = asset` 的节点，有父节点（可以是根）。它不作为子页面出现在侧边栏的页面树里，而是显示在父页面的附件面板中；LLM Wiki 的来源区页面例外，它的附件来源在页面里完整列出。
- 文件本体存在存储端口后面（v0.1 只有本地磁盘实现），按 ID 寻址；PG 存元数据：MIME 类型、大小、SHA-256、上传者。
- 单个附件默认上限 50 MB，可配置。
- 读取用短期签名地址（`<img src>` 无法携带 Bearer 令牌）。图片直接内联显示；svg、html 和其他可能执行脚本的类型加 `Content-Security-Policy: sandbox`，或者以 `Content-Disposition: attachment` 下发；所有附件响应带 `X-Content-Type-Options: nosniff`。
- `![[架构图.png]]` 按文件名解析（4.4），规则与页面链接相同。
- `.md` 文件不能作为附件：Markdown 文件总是页面（上传和导入时都按页面处理）。
- 附件节点被物理清除时，清理任务一并删除它的文件。

### 3.8 变更集与版本

**每一次写入都属于一个变更集。** 变更集就是笔记本的日志，也是撤销的单位。

| 来源 | 变更集的范围 |
|---|---|
| 网页编辑会话 | 从进入编辑模式到离开（或锁超时）为一个变更集；会话中的多次自动保存只更新同一个版本行，一次会话每篇页面只产生一个版本 |
| REST / MCP 的单次写入 | 自成一个变更集 |
| `batch` | 多个操作一个变更集，原子执行，全成或全不成 |
| 导入 | 一次导入一个变更集 |
| 移动或重命名触发的链接改写 | 与触发它的操作在同一个变更集里 |
| 还原、撤销 | 各自产生新的变更集 |
| 升级期间 agent 的写入 | 照常产生变更集，并标记所属的升级会话，回滚时按它整体撤销（5.8） |

变更集记录：执行者（账户）、客户端（`web` / `api` / `mcp:<客户端名>` / `cli`）、类型（编辑、批量、导入、还原、撤销、升级等）、可选的说明、涉及的节点。LLM Wiki 模式下另记本次新引用了哪些原本未消化的来源，据此自动标记为一次 ingest（5.4）。

**版本**：每个变更集对每篇被改动的页面记录一个正文版本；树操作（新建、移动、重命名、排序、删除、恢复）记录前后的 `parent_id`、标题和 `sort_order`。v0.1 保留全部版本。

**还原与撤销**：

- 单篇页面可以还原到任意一个历史版本，产生一个新的变更集。
- 整个变更集可以整组撤销，前提是其中每个节点的当前状态仍然是这个变更集写出来的；只要有一个节点之后被改过，就整体拒绝，并列出冲突的节点。
- 还原和撤销同样经过写入守卫（例如锁），和普通写入没有区别。

### 3.9 编辑会话、编辑锁与写入

**打开页面时默认是阅读视图**，所有人都一样。

**编辑模式与锁一一对应**：

- 点"编辑"或按 `Ctrl+E`：开启一个编辑会话，并申请这篇页面的编辑锁。拿到锁就进入源码编辑模式；拿不到就停在阅读视图，显示"XX 正在编辑"。
- 锁是租约：有效期 60 秒，编辑器每 20 秒心跳续约一次。
- 退出编辑模式、关闭页面（用 `navigator.sendBeacon` 主动释放）、心跳超时，都会释放锁并结束会话。
- 笔记本管理员可以强制解锁；被解锁的编辑者收到通知，切回阅读视图。已自动保存的内容不会丢失。
- 锁存在 PG 里。

**自动保存**：编辑时停顿约 2 秒自动保存；`Ctrl+S` 立即保存。每次保存都带上 `base_revision`，与当前版本不一致时返回 409，编辑器给出差异对比。输入法正在组合输入（拼音尚未确认）时不自动保存，否则会把半截拼音存进正文；组合结束（`compositionend`）后补一次保存。

**瞬时写入**：REST 与 MCP 的写入、阅读视图里勾选任务复选框，都是"瞬时写入"：在一个事务里检查锁、写入、结束。有别人持锁时拒绝（409，附带持锁人）；`base_revision` 不一致时拒绝（409，附带当前版本）。

### 3.10 回收站

- 删除节点：它的整棵子树（包括附件）以同一个 `deleted_at` 软删除，进入笔记本的回收站。
- 回收站列出被删除的子树根节点。恢复时：原父节点已不存在，就放到根下；标题冲突，自动加序号。
- 60 天后由清理任务物理清除。

### 3.11 实时推送

- **一个浏览器一条事件流**（SSE）。事件流面向当前账户，推送它看得到的所有笔记本的事件：页面正文变化（id 与新版本号）、节点树变化、锁变化、链接状态变化、笔记本模式变化。事件只带标识和所属笔记本，客户端收到后自己重新取数。
  - 同一个浏览器的多个标签页选出一个来持有连接（Web Locks；非安全上下文时用 localStorage 租约，与令牌续期相同），事件经 `BroadcastChannel` 分发给其他标签页；持有者关闭后由别的标签页接手。原因：没有 TLS 的部署走 HTTP/1.1，每个源最多 6 条连接，每个标签页各开一条流会把连接耗尽，连普通请求都会卡住。
  - 服务端按连接记下这个账户看得到的笔记本，只转发其中的事件。
- **授权随时间失效**：建立连接时校验访问令牌，令牌到期时服务端关闭连接，客户端续期后重连。账户的可见范围变化（成员身份、笔记本权限、账户停用，由 M3 的可见性事件通知，见 12.4）或退出登录时，服务端立即关闭这个账户的连接，重连时重新计算。
- 写入事务里执行 `NOTIFY`，事务提交后才送达，推送天然与提交一致；每个进程用 `LISTEN` 接收并分发给自己的 SSE 连接，多实例同样适用。
- 每个事务最多发一条 `NOTIFY`：带 `NOTIFY` 的提交在 PG 的全局队列锁上串行，导入、`batch` 这类多节点写入也合并成一条。负载上限约 8000 字节，超出时改发这个笔记本的整体刷新事件。
- 浏览器原生的 `EventSource` 不能带 `Authorization` 头，前端改用 `fetch` 流式读取事件。
- 连接断开后（包括令牌到期的计划内重连），客户端重新连接并刷新页面树和当前页面，不做事件补发。负责 `LISTEN` 的连接断开后自动重连，并向所有连接广播 `reset`，客户端据此整体刷新。
- 服务端每 15–30 秒发送一次心跳注释行，并设 `X-Accel-Buffering: no`，避免反向代理缓冲；Caddy 的默认配置已验证可用。
- SSE（以及 MCP）这类长连接路由豁免请求期限，并在连接上解除写超时（`http.ResponseController.SetWriteDeadline`）；读期限保留，仍约束请求体。平台层的 `httpserver.LongLived` 做这两件事，并在停机开始时取消它们的 context（M0/P3）。

## 4. Markdown 与链接

### 4.1 方言范围

v0.1 支持：

- CommonMark + GFM（表格、任务列表、删除线、自动链接、脚注）
- YAML frontmatter
- `[[页面]]`、`[[页面|显示文字]]`、`[[页面#标题]]`、`[[路径/页面]]`
- `![[附件]]`（图片内联显示，其他类型显示为附件卡片）
- 正文中的 `#标签`
- callout：`> [!note] 标题`
- `==高亮==`、`%%注释%%`（阅读视图中隐藏；注释里的链接照常进索引，重命名时照常改写）
- 代码块语法高亮、KaTeX 数学公式、mermaid 图（按需懒加载）

推迟到 v0.2：嵌入整篇页面 `![[页面]]`（v0.1 渲染为链接）、块引用 `^id` 的校验。

任何不支持的语法都照原文显示、原样保存，不会丢数据。

### 4.2 frontmatter 词汇表

系统只认下面几个键，名字尽量和 Obsidian 原生的一致：

| 键 | 含义 | 系统用它做什么 |
|---|---|---|
| `aliases` | 别名（Obsidian 原生） | 参与 `[[ ]]` 的解析 |
| `tags` | 标签（Obsidian 原生）；正文里的 `#tag` 也算 | 筛选、目录 |
| `type` | 页面类型，自由字符串 | 目录按它分组；LLM Wiki 模式下必填 |
| `summary` | 一句话摘要 | 进目录；LLM Wiki 模式下必填 |
| `sources` | 引用的来源，写成 `["[[raw/xxx]]"]` | 进链接索引，是判断来源"已消化"的依据 |

- 其他键照样解析进属性索引，可以用于筛选，但系统不赋予它们含义。
- 标题就是节点名，不另设 `title` 键。
- frontmatter 写坏了（YAML 解析失败）：不拒绝写入，正文照样逐字节保存；这篇页面当作没有属性，并产生一条 lint。

### 4.3 解析与渲染：服务端是唯一权威

- **唯一的解析入口**：`Parse(原文) → (语法树, 提取结果)`。goldmark 加上我们的扩展解析出语法树；wikilink、嵌入、标签、注释、高亮、callout、数学公式都是语法树上的节点，提取结果（链接、嵌入、标签、frontmatter，带字节位置）从这棵树上取得，不在原文上另行扫描。
  - **提取**：写入时调用。提取只依赖原文，在开启写事务之前完成；事务里只做链接解析与写入，并核对所依据的版本仍是当前版本（不一致就按 409 处理），不在持锁期间解析。
  - **渲染**：读取时调用同一个 `Parse`，再把语法树渲染成 HTML。链接的解析状态（目标节点、是否存在）按字节位置从链接索引取得，阅读视图与反链、链接改写看到的是同一份结果（历史版本没有索引，按当前的节点树即时解析）；任务项带上它在原文中的字节位置。
- 提取与渲染出自同一个 `Parse`，一致性由架构保证。M0/P1 的差分测试表明，两个不同的解析器做不到对任意输入都一致（97.4%），见 [M0/P1](M0-foundation/01-P1-spikes.md) 第 7 节。所以**前端不做 Markdown 的语义解析**：它展示服务端的 HTML，并做交互增强，包括 KaTeX 与 mermaid 渲染占位元素、链接跳转、勾选任务。编辑器里的 lezer 只用于语法高亮、补全、列表续行这类编辑辅助。
- **规范**：样例集 `tools/md-fixtures/`，规则写在它的 README 中，并与真实的 Obsidian 逐项核对；与 Obsidian 不同的地方逐条写明理由。服务端必须通过全部样例；渲染测试断言 HTML 中的链接与提取结果一致。
- 实现要点（M0/P1 的结论）：
  - 解析前把 frontmatter 的字节替换为空格（保留换行），使它不影响正文，偏移也不变。M4 的渲染与 M6 的提取用的是同一个函数，否则 `---` 会被渲染成分隔线或 setext 标题；
  - 行内结构从左到右识别，先开始的优先：wikilink 先于 Markdown 链接，字面自动链接先于它里面的 `[[…]]`；
  - 注释只影响渲染，不影响提取；数学公式按 Obsidian 的规则（开头的 `$` 后面、结尾的 `$` 前面不能是空白）；
  - 引用定义的位置取自语法树（goldmark 的 `LinkReferenceDefinition` 节点）。
- **读取阅读视图**：
  - 响应带上所依据的 `revision`。
  - 不按 `revision` 缓存 HTML：HTML 里有附件的签名地址和链接的解析状态，别的页面新建或改名时，本页的 `revision` 不变，链接状态却变了。v0.1 每次读取都渲染。
  - 别的节点变化导致本页链接的解析结果变化时，推送链接状态变化的事件（M6），阅读视图据此重新读取。
  - 编辑模式切换到阅读视图之前先保存，所以不需要渲染未保存内容的接口。
- **耗时**：100 KB 的页面渲染约 3.5 ms，5 MB 的页面约 330 ms 以上（只计 goldmark 与清洗）。M4 定出渲染与提取的耗时预算，并对病态输入（深层嵌套、超长行、大量未闭合的括号）做耗时模糊测试。

### 4.4 链接解析规则

照 Obsidian 的规则：

- `[[名称]]`：先按节点名匹配（页面按标题，附件按文件名），用标题键（3.5）比较，所以不区分大小写，也不区分 Unicode 的规范化形式；再查 `aliases`。名称以 `.md` 结尾时去掉扩展名再匹配页面（`[[p.md]]` 指向页面 p，与 Obsidian 相同）。
- 匹配到多个时：优先选同一父节点下的，再选路径最短的；同时记一条"链接有歧义"的 lint。
- `[[路径/名称]]`：按路径精确匹配，路径由祖先的标题组成。
- `|` 后面是显示文字；`#标题`、`^块` 作为锚点记录，v0.1 不校验是否存在。
- `![[x]]` 是嵌入，按同样规则解析。
- `[文字](相对路径.md)`：按当前页面导出后的位置解析相对路径。
- frontmatter 里整个值恰好是一个链接的字符串属性，单独记为"属性链接"，并记下属性路径（例如 `sources.0`）；M10 的来源规则按路径判断。
- **解析不到的链接也保留**，记下目标文本。新建、重命名、移动、删除、恢复节点时，在同一个事务里重新解析受影响的链接。
- 链接只在笔记本内部解析；外部网址不进链接索引。

### 4.5 移动与重命名时的链接改写

默认改写，与移动或重命名放在同一个变更集里，原子完成：

1. **入链**：原来解析到被移动节点（含整棵子树）的链接，重新解析一次。仍然指向同一个节点的，一个字都不改；不再指向它的，改写成最短的、没有歧义的形式。例如只把 `foo` 移到别处而 `[[foo]]` 仍能唯一解析到它时，不改。
2. **出链**：被移动的页面（含整棵子树）里的相对路径 Markdown 链接，因为出发的位置变了，一起改写。
3. **锁**：需要改写正文的页面只要有一篇被别人锁着，整个操作失败，返回这些页面和持锁人，不做部分改写。
4. MCP 的 `move` 默认改写，可以传 `update_links=false` 关闭；网页操作总是改写。
5. **系统的链接改写不算修改**：它可以改写来源区里的来源（5.4），也不破坏升级的"内容保全"（5.8）。

改写按字节位置精确替换链接文本，其余字节不动，并保持原来的写法：尖括号或百分号编码、别名与锚点、YAML 的引号风格（单引号里的 `'` 写成 `''`）。规则见样例集的 `rename/`；这部分用样例集和模糊测试覆盖。

### 4.6 渲染安全

威胁是现实的：LLM Wiki 的来源区由 agent 从网上抓取内容；刷新令牌存在 localStorage，一次 XSS 就能接管账户。

- **用户写的原始 HTML**（HTML 块与行内 HTML）在渲染时用 bluemonday 的严格策略单独清洗：只放行排版类的标签与属性，去掉 `id`、`class`、`style`、`data-*` 以及所有事件属性。
- **渲染器自己的标记**在清洗之外由渲染器生成：任务项的字节位置、标题 id、公式与 mermaid 的占位元素、链接的解析状态。用户的 HTML 无法伪造它们。标题 id 加固定前缀，避免与页面上的其他元素冲突。
- **前端依据这些标记发起的操作，服务端一律再核对**：勾选任务时提交 `(revision, 字节位置)`，服务端按该版本的解析结果确认那个位置确实是任务标记。
- KaTeX 以 `trust: false` 渲染；mermaid 用 `securityLevel: 'strict'`。
- 页面设严格的 CSP：内联脚本按哈希放行，请求只能发往本站；`style-src` 要容纳 KaTeX 与 mermaid 生成的样式，具体写法在 M6 确定。
- 附件的响应头见 3.7。

## 5. 笔记本模式

### 5.1 模式是一份契约

**笔记（页面）是数据的最小单位，笔记本是规则的最小单位。** 每个笔记本有一种模式；模式是一份确定性的契约，定义四样东西：

- **写入时的不变量**：每次写入都检查，违反就拒绝。
- **状态检查**：lint 规则，分为阻断与提示。
- **虚拟文件**：由系统生成的只读页面。
- **playbook**：交给 agent 的操作手册，以 MCP prompts 下发。

v0.1 有两种模式：`standard`（普通）与 `llm_wiki`。以后加别的模式（例如日记、项目文档），只是再写一份契约。

### 5.2 两种模式的对照

| 能力 | 普通 | LLM Wiki |
|---|---|---|
| 页面、附件、层级、链接与反链、标签、搜索、版本、变更集 | ✓ | ✓ |
| frontmatter 词汇表 | 识别，不要求 | `type`、`summary` 必填 |
| 通用 lint（5.6） | ✓ | ✓ |
| 有 `AGENTS` 页面就作为 MCP 的说明下发 | ✓（可选） | ✓（必须有） |
| 来源区只能新增、不能修改 | ✗（`raw` 只是普通页面） | ✓ |
| 虚拟的 `index`、`log` 页面 | ✗（目录和日志在界面与工具中查看） | ✓ |
| 未消化来源、ingest 标记、LLM Wiki 专属 lint | ✗ | ✓ |
| ingest / query / lint playbook | ✗ | ✓ |

### 5.3 LLM Wiki 的产品化

| LLM Wiki 的概念 | skill 做法的问题 | Nerve Wiki 的做法 |
|---|---|---|
| raw 原始资料（只读） | 只靠一句"不要改 raw/" | 来源区：系统强制只能新增（5.4） |
| wiki 页面 | — | 普通页面；类型、摘要、引用的来源写在 frontmatter |
| schema（AGENTS.md） | agent 不一定先读 | 根目录的 `AGENTS` 页面，MCP 连接时自动下发 |
| index.md | 每次 ingest 手工更新，是多人并发时的热点文件 | 系统实时生成的虚拟页面（5.5） |
| log.md | 手工追加，格式靠自觉 | 变更集就是日志；虚拟页面由它生成 |
| ingest 一次改 10–15 页 | 分多次写，中途失败留下半成品 | `batch` 原子写入；自动记录消化了哪些来源 |
| lint | agent 读全库找问题，很费 token | 机械规则由 DB 查询算出（5.6）；语义检查交给 agent，系统给出需要检查的范围 |

团队场景下多出来的价值：虚拟目录和日志消除了热点文件，多个 agent 可以同时往同一个 wiki 写；每次写入可以追溯到"谁、通过哪个 agent"；失败的 ingest 可以整组撤销。

### 5.4 来源区

- LLM Wiki 模式的笔记本有一个来源根页面，默认标题 `raw`，是笔记本的一项设置。它的整棵子树都是来源，可以是 Markdown 页面，也可以是 PDF、图片等附件。
- **来源只能新增，不能修改正文。** 删除和移动来源只允许笔记本管理员做。来源根页面自己的正文（说明文字）可以修改。系统的链接改写不算修改（4.5）。
- **"已消化"是推导出来的**：来源区以外只要有页面引用了它（正文链接或 `sources` 属性），它就算已消化。没有状态机，agent 也不用"标记完成"。
- 新放入的来源与已有来源的内容哈希相同时，拒绝放入，并指出已存在的位置。
- 一个变更集如果新引用了原本未消化的来源，它就被标记为一次 ingest，并记录这些来源。

### 5.5 目录与日志

- **目录**由节点树、属性索引和链接索引实时生成：每篇页面列出路径、类型、摘要、标签、更新时间、被引用次数，按 `type` 分组，没有 `type` 的按父页面分组。
- **日志**就是变更集列表，可以按人、客户端、页面筛选。
- LLM Wiki 模式下，根目录的 `index` 与 `log` 是**只读的虚拟页面**：
  - 在网页的页面树中用特殊图标显示；
  - agent 通过 MCP 读 `index.md`、`log.md` 得到实时内容，照任何现成的 LLM Wiki skill 操作都能工作；
  - 试图写入时得到明确的错误："这个文件由系统生成，修改页面后目录会自动更新"；
  - 导出时写成真实文件。
- 在 LLM Wiki 模式的根目录下，`index`、`log` 是保留标题，不能建同名的真实页面。
- MCP 另提供带筛选和分页的 `index`、`log` 工具，页面多时比读整份虚拟文件更省 token。

### 5.6 lint 规则

**通用规则**（两种模式都有）：

| 规则 | 说明 |
|---|---|
| 待建页面 | 被链接了、但还不存在的页面，按被引用次数排序。在 wiki 里这是正常现象，所以称为"待建"而不是"错误" |
| 孤儿页 | 没有任何入链的页面（来源、`AGENTS`、虚拟页面除外） |
| 链接有歧义 | `[[名称]]` 匹配到多个节点 |
| frontmatter 解析失败 | — |

**LLM Wiki 专属规则**：

| 规则 | 说明 |
|---|---|
| 缺类型、缺摘要 | 来源区以外的页面没有 `type` 或 `summary` |
| 未消化的来源 | 没有被任何页面引用的来源 |
| `sources` 指向无效 | 引用的目标不在来源区里，或者不存在 |

- 语义检查（互相矛盾、结论过时）由 agent 负责；系统可以给出范围，例如"最近 N 个变更集涉及的页面"。
- 网页上有健康度面板；MCP 提供 `lint` 工具。

### 5.7 新建 LLM Wiki 笔记本

新建笔记本时可以直接选择 LLM Wiki 模式，系统套用模板：

- 根目录下的 `raw` 来源根页面（带一段说明）；
- 根目录下的 `AGENTS` 页面：LLM Wiki 的约定模板，说明页面类型、frontmatter 写法、ingest / query / lint 的做法，由用户按领域修改；
- 虚拟的 `index`、`log` 页面。

空笔记本天然满足 LLM Wiki 的契约，不需要升级流程。

LLM Wiki 模式下，根目录的 `AGENTS` 页面和来源根页面不能删除；`AGENTS` 页面也不能改名或移动（系统按根目录下的标题 `AGENTS` 找到它），但正文可以修改。来源根页面由笔记本设置按 id 记录，可以改名。

### 5.8 升级流程：普通 → LLM Wiki

升级只能由用户自己的 agent 通过 MCP 执行；产品提供流程、护栏、闸门和人审。**升级只做分类和标注，不做重组**；拆分、合并、改写属于升级之后的日常工作。

```
standard ──管理员发起──▶ upgrading ──agent 提交，闸门全部通过──▶ reviewing ──管理员批准──▶ llm_wiki
   ▲                         │                                        │
   └──放弃：整体回滚─────────┴──────驳回：整体回滚，或退回继续修改─────┘

llm_wiki ──管理员降级（立即生效，不需要 agent）──▶ standard
```

**步骤**：

1. **发起**：笔记本管理员在网页上点"升级为 LLM Wiki"，系统创建一次升级会话，提示用户把 agent 连到这个笔记本的 MCP 并运行升级 playbook。
2. **冻结**：升级期间笔记本对所有人只读，只有发起升级的管理员通过 MCP 发出的写入被允许；其余写入返回 409 `notebook.upgrading`。agent 中途断开可以重新连接继续；管理员随时可以放弃。
3. **agent 执行**：通读笔记本；把每篇原有页面归为"来源"或"wiki 页"；来源移入 `raw`，wiki 页补写 frontmatter；定制 `AGENTS` 页面；按需新建综合页。
4. **自检**：agent 随时可以调用 `upgrade_verify` 获取检查报告，全部通过后调用 `upgrade_submit`。
5. **人审**：笔记本管理员查看升级报告，批准、驳回或退回继续修改。
6. **回滚**：放弃或驳回时，按倒序撤销本次升级的全部变更集。因为有冻结，回滚不会与别人的修改冲突。

**第一道闸：写入时的护栏**（升级期间每次写入都检查）：

- 升级开始时已存在的页面：只允许修改 frontmatter 那一块，正文必须逐字节不变；
- 升级开始时已存在的节点：不允许删除；
- 移动和新建不受限制。

被拒绝的写入附带明确的原因，agent 可以当场纠正。

**第二道闸：提交时的闸门**（任何一项不通过就不能提交）：

1. 根目录有一个正文非空的 `AGENTS` 页面；
2. 来源根页面存在；
3. 根目录下没有标题为 `index` 或 `log` 的真实页面；
4. 来源区以外的每篇页面都有能解析的 frontmatter，且 `type`、`summary` 不为空；
5. 每个 `sources` 引用都指向来源区里存在的节点；
6. 解析不到的链接数不多于升级前；
7. **内容保全**：升级前的每个节点（按 id 追踪）都还在；每篇原有页面的正文（frontmatter 以外的部分）与升级前逐字节相同，差异只来自系统的链接改写。

孤儿页、未消化的来源、链接歧义、待建页面等只作提示，写进报告，不阻断。

**升级报告**包括：移入来源区的数量、成为 wiki 页的数量、类型分布、每篇页面的类型与摘要清单、链接完整性的前后对比、内容保全的证明（例如"312/312"）。

**降级**：LLM Wiki → 普通，由笔记本管理员直接操作，立即生效；`raw` 变为普通页面，虚拟页面消失，frontmatter 原样保留。

### 5.9 playbook

ingest、query、lint、upgrade 四份 playbook 由 MCP 服务以 prompts 的形式提供（Claude Code 等客户端会把它们显示为斜杠命令）：

- 用户不需要另外安装 LLM Wiki skill；
- playbook 与产品一起发版，与护栏、闸门、lint 的规则始终一致；
- 产品本身仍然不调用 LLM。

## 6. 接口

### 6.1 REST 约定

- **路径前缀** `/api/v0`；v0.x 期间允许不兼容的修改，发布 v1 时升级为 `/api/v1` 并承诺向后兼容。
- **先写接口描述，再写实现**：OpenAPI 3.1，按模块拆分在 `api/modules/<模块>.yaml`，公共组件在 `api/common.yaml`，打包为 `api/dist/openapi.yaml`。服务端用 oapi-codegen 生成，TS 客户端用 openapi-typescript + openapi-fetch 生成；生成物提交进仓库，持续集成核对一致。
- **数据格式**：JSON 字段用 snake_case；ID 是 UUID（v7，由应用生成）；时间用 RFC 3339（UTC）。响应里关联别的资源只给 id；例外是成员列表、无主笔记本清单与审计记录内嵌账户的公开资料（显示名；邮箱按调用者的角色给出），因为 v0.1 没有读取别的用户的接口。
- **方法**：GET 查询（无副作用），POST 创建或执行动作，PATCH 部分更新（`null` 表示清空），DELETE 删除（软删除；撤销凭证例外：会话与 PAT 记下撤销时间，行保留，见 13.1 第 6 条）。POST 与 PATCH 返回改完之后的完整资源；认证类接口的例外照 Nerve。携带秘密的读取（预览邀请）用 POST，秘密放在请求体里，不进地址（反向代理的访问日志记录完整的请求行）。
- **路由**：列表挂在父资源下，单个资源用短路径，业务动作用 `POST /资源/{id}/动作名`。例如：
  ```
  GET   /api/v0/workspaces/{slug}/notebooks
  GET   /api/v0/notebooks/{notebook_id}/nodes           节点树
  POST  /api/v0/notebooks/{notebook_id}/pages
  GET   /api/v0/pages/{page_id}
  PUT   /api/v0/pages/{page_id}/content                  带 base_revision
  POST  /api/v0/nodes/{node_id}/move
  POST  /api/v0/pages/{page_id}/edit-session            进入编辑模式，申请锁
  POST  /api/v0/changesets/{changeset_id}/revert
  GET   /api/v0/notebooks/{notebook_id}/events           SSE
  ```
  完整的接口清单在各 M 的设计中确定。
- **错误**：RFC 9457 `application/problem+json`，`code` 是给程序判断用的固定字符串。平台码不带前缀（`bad_request`、`unauthorized`、`forbidden`、`not_found`、`payload_too_large`、`validation_failed`、`rate_limited`、`internal_error`、`server_busy`、`not_ready`）；模块码带模块前缀（例如 `page.locked`、`page.revision_mismatch`、`notebook.upgrading`）。每个操作用 `x-problem-codes` 声明它可能返回的码，测试双向核对。
- **看不到与不能做**：看不到的资源返回 404，不泄露它是否存在；看得到但角色不允许，返回 403。
- **结构在边界，取值在领域**：请求体不合契约（未知字段、缺必填、格式错误、重复键、非法 UTF-8）返回 400；取值规则由领域校验，返回 422，`errors` 一次列出全部字段问题。
- **分页**：游标分页，`?limit=&cursor=`，响应 `{data, next_cursor}`；集合型的小列表（工作区、成员、笔记本）不分页，响应 `{data}`。节点树一次返回整棵树。
- **限流**：进程内令牌桶，公开操作按 IP、其余按凭证计数；登录、注册、改密另有专门的桶；认证之前有失败闸门。超出返回 429 与 `Retry-After`。

### 6.2 认证

照 Nerve 的认证设计：

| 令牌 | 形式 | 有效期 |
|---|---|---|
| 访问令牌 | JWT（Ed25519 签名），只含用户 id、会话 id、过期时间，不含权限 | 15 分钟 |
| 刷新令牌 | `nwk_rt_` + 会话 id、代数、随机密文与 HMAC 标签；数据库只存当前一代密文的哈希 | 从登录起 30 天，续期不延长；每次使用后换新，带重复使用检测 |
| PAT | `nwk_pat_` + 随机串，数据库只存哈希；创建时要求当前密码 | 由用户设定，可随时撤销 |

- 所有调用方统一用 `Authorization: Bearer`，不用 Cookie（没有 CSRF 问题）。
- 权限不放进令牌，每个请求都从数据库读取成员关系与角色，调整立即生效。
- 密码用 argon2id；登录不暴露账户是否存在。密码 8–128 个字符，拒绝常见密码与邮箱前缀，不要求字符组合（M1 设计第 4 节）。
- prod 默认关闭注册，第一个账户由 `nervewiki users create` 创建；没有邮件通道，忘记密码由服务器管理员用 `nervewiki users reset-password` 重置。
- 浏览器端：访问令牌只在内存里；刷新令牌与 `login_id` 存在 localStorage 的 `nwiki.auth`；多标签页用 `navigator.locks`（非安全上下文时用 localStorage 租约）串行续期。

### 6.3 MCP

- 内置在同一个二进制里，Streamable HTTP 传输，PAT 放在 `Authorization` 请求头中认证。使用官方 Go SDK（`github.com/modelcontextprotocol/go-sdk`，M0/P1 验证的是 v1.8.0）。
- SDK 在每个请求开头都会调用"取得 server"的回调，所以这个回调按"笔记本 + `AGENTS` 页面的版本"缓存 server，缓存按 LRU 回收。`?notebook=` 的权限每个请求都判定，而且在查缓存之前：看不到的笔记本返回 404。
- SDK 把会话绑定到账户，拿别人的会话 id 冒用会被拒绝。会话存在进程内：设置 `SessionTimeout` 回收空闲会话（零值表示永不回收）；服务重启后会话失效，客户端需要重新握手（M9 验证 Claude Code 与 Codex 能否自动恢复，并评估 SDK 的无状态模式，它的代价是后续请求拿不到 clientInfo）。
- SDK 默认的回环地址保护会挡住同一台机器上的反向代理，所以关闭它，由 Bearer 认证把关。
- 工具带上 `readOnlyHint` / `destructiveHint` 注解，客户端据此决定哪些调用需要人确认。
- Claude Code、Codex 的接入配置写进接入文档。Codex 的非交互模式默认拒绝需要审批的工具；接入文档说明各审批选项的含义，不一律推荐 `approve`。
- **两种入口**：
  - `/mcp?notebook=<id>`：限定在一个笔记本内，相当于 cd 进去。握手时把该笔记本的 `AGENTS` 页面作为说明（instructions）下发；工具中的路径都相对于笔记本根目录。
  - `/mcp`：面向整个账户。工具需要带笔记本参数；另有 `notebooks`（列出可访问的笔记本）和 `open_notebook`（返回 `AGENTS` 页面与概况）。
- URL 中的笔记本限定只是为了方便，**不是安全边界**：PAT 拥有账户的全部权限。按笔记本限定权限的 PAT 留给 v0.2。
- **路径语义**：页面的路径是 `祖先标题/…/标题.md`，附件是 `祖先标题/…/文件名`，`项目A/` 表示项目A 的子节点。写入一个不存在的路径时，自动补建缺失的父页面。
- **工具**，照 coding agent 熟悉的文件工具设计：

  | 工具 | 用途 | 在哪个 M |
  |---|---|---|
  | `list` | 按路径或 glob 列出节点 | M9 |
  | `read` | 读页面（支持 offset / limit）；读附件时，图片以 MCP 图片内容返回，其他类型返回元数据与短期下载地址 | M9 |
  | `write` | 写整篇页面，带 `base_revision`（新建时不带） | M9 |
  | `edit` | 按"原文 → 新文"精确替换（str_replace 语义），可带 `base_revision` | M9 |
  | `grep` | 正则搜索，可按路径 glob 限定 | M9 |
  | `move` | 移动或重命名，默认改写链接，`update_links=false` 可关闭 | M9 |
  | `delete` | 删除；有子节点时必须传 `recursive=true` | M9 |
  | `batch` | 多个写操作 + 说明，一个变更集原子执行 | M9 |
  | `backlinks` | 某页面的入链 | M9 |
  | `index` | 目录（按类型、标签、父页面筛选，分页） | M9 |
  | `log` | 变更集日志（按人、客户端、页面筛选，分页） | M9 |
  | `lint` | 健康检查结果 | M10 |
  | `pending_sources` | 未消化的来源 | M10 |
  | `upgrade_verify` / `upgrade_submit` | 升级自检与提交 | M11 |

- **prompts**：ingest、query、lint（M10），upgrade（M11）。
- 变更集的客户端记为 `mcp:<客户端名>`，取自 MCP 握手时的 clientInfo。
- MCP 是一种适配器：各模块在自己的 `adapter/mcp` 中注册工具，调用与 REST 相同的用例，不是在 HTTP 外面再套一层。

### 6.4 附件的上传与下载

- 上传：`multipart/form-data` 经服务端流式写入存储端口，同时计算 SHA-256；超过上限立即中止。
- 下载：接口返回短期签名地址（HMAC，按小时取整以便浏览器缓存），由服务端校验签名后下发文件。

## 7. 数据库

### 7.1 约定

- PostgreSQL 18；迁移用 goose（纯 SQL，内嵌进程序）；数据访问用 pgx + sqlc。River 的表与业务表在同一条迁移链上。
- **数据库 locale**：builtin provider 的 `C.UTF-8`，`LC_COLLATE` 与 `LC_CTYPE` 也是 `C.UTF-8`。
  - 建库：`CREATE DATABASE nervewiki TEMPLATE template0 ENCODING 'UTF8' LOCALE_PROVIDER builtin LOCALE 'C.UTF-8'`。用官方镜像初始化时设 `POSTGRES_INITDB_ARGS="--locale-provider=builtin --locale=C.UTF-8"`，之后用默认参数新建的库都继承这个设置；compose、测试容器、持续集成都这样初始化。
  - 排序规则与大小写转换（`lower`、`ILIKE`、正则）由 builtin provider 提供，不随 glibc 或 ICU 变化。
  - pg_trgm 按 libc 的 `LC_CTYPE` 判断哪些字符是字母：`LC_CTYPE` 为 `C` 时切不出中文，也会丢掉 `é`、`ß` 这类字符。这一部分仍然依赖 glibc：换基础镜像、升级 glibc 的大版本之后，对三元组索引执行 `REINDEX`。所以 PostgreSQL 镜像带上发行版名（例如 `postgres:18.6-trixie`），开发、测试、部署用同一个镜像，换发行版视同升级 glibc 的大版本。
  - `nervewiki` 启动时（迁移之后）自检：编码为 UTF8、`datlocprovider = 'b'`、`datlocale`、`datcollate`、`datctype` 都是 `C.UTF-8`、`show_trgm('中文')` 不为空。不满足就拒绝启动，并给出正确的建库命令。`migrate up` 之后同样自检。`pg_trgm` 扩展由第一条迁移创建。
- 用于唯一性或精确匹配的键列（例如标题键）使用 `COLLATE "C"`，键由应用计算。
- **每个模块只建自己的表**，只写自己的查询；sqlc 按模块限定可见的表，跨模块的读取在 `app` 层声明端口。给别的模块的表加列、加约束、加索引的迁移归被改表的模块。
- ID 为 UUID v7，由应用生成，数据库不设默认值。
- 审计字段 `created_by_id`、`updated_by_id`、`created_at`、`updated_at` 由用例显式写入，时间取自用例的时钟；SQL 里不写 `now()`。
- 软删除用 `deleted_at`；唯一约束用部分唯一索引（`WHERE deleted_at IS NULL`）。连带删除在同一个事务里完成，60 天后由清理任务物理删除。
- 默认值、非空、枚举检查、JSON 结构检查都写进数据库；多列 CHECK 显式命名，索引命名 `<表>_<列>_idx`。

### 7.2 表（概念层，详细 DDL 在各 M 的设计中确定）

| 模块 | 表 | 要点 |
|---|---|---|
| identity | `users`、`auth_sessions`、`api_tokens` | 照 Nerve 裁剪：不建 `profiles`（偏好属于设备），已完成的新手引导步骤记在 `users` |
| workspace | `workspaces`、`workspace_members`、`workspace_invitations` | 邀请表不存令牌 |
| notebook | `notebooks`、`notebook_members`、`notebook_audit_events` | `workspace_access`、无主（时刻与原所有者）；审计记录不引用笔记本，随工作区删除。`mode`、升级状态、来源根页面 id 由 M10、M11 加 |
| page | `nodes` | `notebook_id`、`parent_id`、`kind`（page / asset）、`name`（标题或文件名）、`sort_order`；同一父节点下 `name` 不区分大小写唯一（根下同理） |
| page | `page_contents` | 原样正文、`revision`、`content_hash`、`byte_size` |
| page | `changesets`、`changeset_items`、`page_revisions` | 变更集、其中每个节点的树操作前后状态、正文版本 |

## 8. 后端架构

### 8.1 原则

照 Nerve：**模块化单体 + 端口与适配器**，只在组合根接线。

- 依赖方向只能向内：`adapter → app → domain`；`domain` 只依赖标准库和 `shared`。
- 模块之间不能直接 import；需要别的模块的能力时，在自己的 `app` 层声明小接口，由组合根接上。
- 跨模块的副作用通过领域事件，订阅者在同一个事务里被调用。
- 禁止全局可变状态、`init()` 副作用、服务定位器；禁止 `utils`、`common` 这类大杂烩包；超过约 400 行的文件在评审时说明理由或拆分。
- 以上由架构测试（随 `go test` 运行）、sqlc 的模块范围检查和 golangci-lint 的 depguard 强制执行。
- 不做 CQRS、事件溯源，不用依赖注入框架。

### 8.2 目录结构

```
server/
  cmd/nervewiki/            解析命令行、加载配置，交给 bootstrap；打印版本
  configs/                  config.yaml 与 config.{dev,test,prod}.yaml
  migrations/               goose 迁移
  internal/
    bootstrap/              组合根
    platform/               与业务无关的技术基础件：buildinfo、config、logging、postgres、httpserver、
                            ratelimit、clock、jobs（River）、webui、realtime（LISTEN 与 SSE 分发）、
                            mcpserver（MCP 传输、认证接入、工具注册表）、storage（本地磁盘）
    shared/                 共享内核：Actor、领域错误、邮箱的规范化与校验、名称规则（CheckName、CheckTitle）、
                            TxManager 端口、游标封套、Authorizer 端口、工作区与笔记本的角色、有效角色
    modules/
      instance/             实例信息
      identity/             账户、会话、PAT、密码
      access/               权限规则表与判定（实现 Authorizer）
      workspace/            工作区、成员、邀请
      notebook/             笔记本、成员、workspace_access、无主处理与审计记录（模式字段由 M10 加）
      page/                 节点树、正文、编辑会话与锁、变更集与版本、回收站、搜索
      linking/              Markdown 提取、链接/属性/标签索引、解析与改写、反链
      asset/                附件
      transfer/             导入与导出
      wiki/                 模式契约、来源区、虚拟页面、lint、升级流程、playbook
```

每个模块内部：`domain/`（纯规则）、`app/`（一个用例一个文件，端口声明在 `app/ports.go`，多了按主题拆成 `ports_<主题>.go`）、`adapter/{postgres,http,mcp,…}`、模块根（`module.go` 是 HTTP 一侧的入口，没有 HTTP 一侧的模块（access）的 `New` 返回它提供的端口；给命令行与别的模块的入口另成文件，如 identity 的 `admin.go`、`accounts.go`，workspace 的 `invitations.go`）。ID 由标准库的 `uuid.NewV7()` 生成，没有单独的平台包。

### 8.3 写入管线

所有写入入口（网页、REST、MCP、导入、还原、撤销、升级）都经过同一条管线，在一个事务里完成：

```
锁定父行（笔记本行）→ 权限判定 → 写入守卫（锁、模式不变量、升级冻结与护栏）
  → 领域校验 → 写数据 → 记录变更集与版本 → 发布页面领域事件
     （订阅者：链接索引与改写、NOTIFY 推送）→ 提交
```

- 写操作在锁定父行之后才做权限判定；读操作不开事务，直接判定；每个请求都重新读角色，不缓存。
- 锁的粒度：页面写入以**共享锁**锁定笔记本行，与删除笔记本、修改成员、修改模式互斥，页面写入之间互不阻塞；改变树结构的操作（移动）在同一笔记本内串行，防止并发移动形成环。锁模式与全局加锁顺序见 13.1 第 5 条（M2 定下工作区一支，M3、M4 接在后面）。

### 8.4 配置、日志与运维

- 配置照 Nerve：内置的 `config.yaml` 列出全部配置项与默认值，按内置的 `config.{env}.yaml`、`$NWIKI_CONFIG_DIR` 下的 `config.yaml` 与 `config.{env}.yaml`、`config.local.yaml`（仅 dev）、环境变量 `NWIKI_*` 的顺序覆盖；koanf 加载；强类型，启动时逐项校验，未知键报错；密钥只经环境变量或 `*_file` 提供。
- 日志用 slog：prod 输出 JSON，dev 与 test 输出文本。提供 `/healthz` 与 `/readyz`。停机时依次优雅停止 HTTP、River、连接池。

### 8.5 后台任务（River）

| 任务 | 触发 |
|---|---|
| 清理过期会话 | 定时 |
| 物理清除软删除超过 60 天的数据（含附件文件） | 定时 |
| 导入 zip、导出 zip | 事件 |

编辑锁的到期由读取时判断，不需要后台任务；超时的编辑会话在下一次访问或定时清理中结束。

### 8.6 管理命令

`nervewiki` 的子命令直接连数据库执行，服务不用停：

- `serve`、`migrate up`
- `users create | reset-password | set-email | deactivate | activate`
- `workspaces create | reactivate-member`
- `reindex`：重新解析全部页面，重建链接、属性、标签索引

## 9. 前端

### 9.1 技术栈

React + React Router（数据路由，页面按需加载；不用框架模式）+ Vite + TypeScript + Tailwind CSS + shadcn/ui（Radix）+ MobX + SWR；编辑器 CodeMirror 6，只在进入编辑模式时按需加载；阅读视图展示服务端渲染的 HTML（4.3），前端只按需加载 KaTeX 与 mermaid。工具链：pnpm、oxlint、oxfmt、knip、vitest、Playwright（turbo 等到包多到需要任务缓存时再引入）。前端与接口同源部署，不使用任何前端环境变量。多语言只有 `zh-CN` 与 `en`。

### 9.2 界面布局

参照 Obsidian：

- **左栏**：工作区切换、笔记本列表（"我的笔记本"与"团队笔记本"两组）、当前笔记本的页面树（支持拖拽移动与排序）。
- **中间**：面包屑、页面标题（即节点名）、阅读 / 编辑切换、正文、子页面列表、附件面板。
- **右栏**：大纲、反链、属性、页面信息（锁状态、版本记录）。
- `Ctrl+O` 快速切换页面（在前端已加载的页面树上查找）。
- 不做应用内的多标签页，直接使用浏览器标签页。

### 9.3 编辑器

源码编辑模式就是面对 Markdown 纯文本，不做 Live Preview。保留的辅助功能：

- Markdown 语法高亮（标题加粗加大，符号保留原样）；
- 输入 `[[` 补全页面名，输入 `#` 补全标签；
- 快捷键：`Ctrl+B` 包上 `**`，`Ctrl+K` 插入链接，`Ctrl+S` 立即保存，`Ctrl+E` 切换阅读与编辑；
- 列表续行、Tab 缩进；
- 粘贴或拖入图片：上传并插入 `![[文件名]]`；
- 文档内查找与替换。

每一次编辑都是文本编辑，没碰到的部分逐字节不变。

与 React 的集成（M0/P1 的结论）：

- `EditorView` 只创建一次，属性变化通过事务传入：只读用 `Compartment` 切换，回调放在 ref 里。
- 切换页面时新建 `EditorState`（以页面 id 区分），撤销历史不跨页面，否则 `Ctrl+Z` 会把上一个页面的内容撤销进来。
- 同一个页面收到外部更新时，只替换差异部分，并标记为不进撤销历史（`addToHistory.of(false)`）。
- lezer 的语法树只用于编辑辅助（高亮、补全时判断光标是否在代码里、列表续行），不做链接、标签的语义判断。

### 9.4 状态与会话

照 Nerve 的做法，作为长期约定（13.2 第 1 条）：

- `src/session/` 是唯一创建 API 客户端的模块：公开客户端（实例信息、注册、登录）与 `clientFor(loginId)`（挂认证中间件）。浏览器只存 `nwiki.auth`（刷新令牌与 `login_id`），访问令牌只在内存。
- 每个登录会话（`loginId`）一代 `RootStore`：`SessionRoot` 在会话变化时整体重建，`<AppProviders key={loginId}>` 随之重新挂载，SWR 的缓存随代重建，键不带 `loginId`。跨代共用的只有页面一生的 `AppStores`（设备偏好、实例信息、会话）。
- service 从构造函数拿这一代的 API 客户端，没有模块级的带令牌客户端。换代之后，旧一代的客户端不再发出请求，401 也不续期重发（`SessionChangedError`）；已发出的请求，答复头到达时（含续期之后重发的答复）标签页已换代的，不论答复是什么都以 `SessionChangedError` 结束：服务端可能已经做了，旧一代的调用方却不再写回、导航或提示。中间件在答复头到达时核对，读答复体期间才发生的换代截不住；这个窗口极窄，不另加机制。用到这个错误的地方忽略它：`errorText` 不给文案，SWR 不重试，守卫显示加载中。
- 答复整个资源的写经 `oneAtATime` 依次发出（最后答复的就是服务端的状态）；读与写重叠时，读出去之后已有写答复的，丢弃读的答复。
- 一个工作区的数据（成员、邀请，M3 起的笔记本等）每代按工作区 id 各一个 store，`/:slug` 下的页面由工作区的外壳渲染，并随工作区重新挂载（13.2 第 15、16 条）。

| 层次 | 内容 | 做法 |

| 集成测试 | 用例与 SQL | testcontainers，每个测试从模板库复制独立的数据库 |
| 接口契约 | 请求与响应符合 OpenAPI；声明的错误码都被测试返回过 | kin-openapi |
| 架构测试 | 依赖方向、模块边界、sqlc 范围 | 随 `go test` 运行 |
| 前端 | store 逻辑、令牌管理器、编辑器扩展、阅读视图的交互增强 | vitest |
| 端到端 | 每个 M 的用户故事 | Playwright + 真实数据库断言（10.1） |

### 10.1 端到端测试

- 以用户故事为单位，一个故事一个测试文件；每个 M 的设计文档列出本 M 的故事清单，这份清单就是它的验收范围。
- 每个故事在三个层面断言：页面上看到的结果；数据库中的业务数据及附带数据（变更集、版本、索引、审计字段、软删除标记）；异步结果（推送、后台任务），用限时轮询等待，不用固定的等待时间。
- **对等验收**：每个故事都有一个用 PAT 调 REST 接口的版本，调用同一组数据库断言函数，要求落库结果完全一样。例外：发生在取得令牌之前的故事（注册、登录、续期、退出，预览邀请与带邀请的注册），接口版本直接调用公开接口（认证、预览邀请）；只能由命令行或后台任务完成的故事只有那一个版本。M9 起，涉及页面读写的故事另有一个 MCP 版本（由测试中的脚本化 MCP 客户端执行）。
- 被测对象是真正要发布的产物：打包好的 `nervewiki`（内嵌前端）、Postgres 18、本地附件存储。
- 每次提交 PR 都运行完整的端到端测试；完成一个 M，要求本 M 与之前所有 M 的故事全部通过。

## 11. 部署与运维

- **环境**：设 `NWIKI_ENV=prod`。prod 默认关闭注册、不在启动时自动迁移（先 `nervewiki migrate up` 再 `serve`）、必须提供 Ed25519 签名私钥文件。
- **反向代理与 HTTPS**：公网部署加 HTTPS；配置 `server.trusted_proxies` 后才从 `X-Forwarded-For` 取客户端 IP。反向代理不要缓冲 SSE（3.11）。
- **CSP**：页面带严格的 CSP，前端与接口必须同源。
- **单实例**：v0.1 官方只支持单实例（附件在本地磁盘）。
- **Docker 镜像**：M0 起每次构建产出（`deploy/Dockerfile`）：distroless，只有 `nervewiki` 一个程序，以 uid 65532 运行；附件目录挂载为卷（M7）。
- **备份**：先 `pg_dump`，再复制附件目录。附件按 ID 写入后不再修改，而物理清除要等 60 天，所以按这个顺序得到的备份，数据库里引用的附件都在。恢复时先恢复数据库，再放回附件目录。
- **数据库角色**：迁移与服务可以分用两个角色，服务角色需要的权限逐表列在 `deploy/runtime-grants.sql`，由测试守住完整。

## 12. 分期路线

### 12.1 切分原则

1. **按用户能感知的能力纵向切。** 每个 M 同时交付后端、接口、前端与端到端故事，做完就能用、能验收。
2. **写入链路的地基一次打牢。** 变更集与版本从页面诞生的 M4 起就同时记录树操作与正文；之后的历史、撤销、MCP、升级回滚都只是读取和复用。
3. **高风险技术点放在 M0，用小实验先验证。** 结论可能改变后面 M 的设计，越早知道越好。
4. **规模有上限。** 参照 Nerve 的实测（测试代码量约为估计的 2.3 倍），某个 M 的设计超过约 20 个接口操作或 15 个故事时，先拆分再开工。
5. **完成标准不依赖后续的 M。** 故事只覆盖本 M 已有的能力；前端不出现调用尚不存在接口的入口。
6. **跨 M 的交互只走扩展点表（12.4）与长期约定（13）。** 后面的 M 只能注册扩展，不改写前面 M 的用例；handoff 只用于计划外的发现（见[文档约定](../README.md)）。

## 13. 长期约定

所有 M 都要遵守的横切约定。在第一个用到它的 M 里一次做完整，之后的 M 照做，不为它写 handoff。新的横切约定出现时，由产生它的 M 补进本节。

### 13.1 后端

1. **每个写操作一个事务**，并且**所有写入入口都经过写入管线**（8.3）：新增一个写入入口（新的接口、MCP 工具、导入、还原、升级）不能绕过权限、写入守卫、变更集与领域事件。
2. **变更集归属**：每个写入都能追溯到执行者与客户端。
3. **权限**：判定经 `shared.Authorizer.Authorize(ctx, actor, action, target)`，由 access 模块按规则表（`access/domain/rules.go`）实现：每行是级别加允许的角色集合，角色按集合比较，不按取值比较。
   - 操作名在所属模块的 `domain/actions.go` 声明（`<资源>.<动词>`，如 `workspace_member.update`），由模块根的包级 `Actions()` 列出；组合根的 `TestTheRuleTableIsTheModulesActions` 核对各模块 `Actions()` 的并集正好是规则表的键，新模块把自己的 `Actions()` 加进这个并集。
   - 每个需要判定的新操作在规则表里加一行。不经规则表的有三类：只涉及调用者自己的、不指向某个资源的（列出自己的工作区、创建工作区、检查 slug）；按所持凭据判定的（接受邀请：令牌与登录的邮箱）；服务器管理员的命令（命令行的组合不构建 access）。判定时没有规则的操作是内部错误，一律拒绝。
   - 判定返回的 `Grant` 带锁下读到的角色，用例拿它做比较两个人的检查（如唯一的管理员），不另读。
   - 新的判定级别（M3 的笔记本级）带自己的事实端口，声明在 `access/app`，由拥有那些表的模块以只凭连接池的包级构造实现（如 `workspace.NewMemberships(pool)`），不改已有的级别。
   - 权限矩阵覆盖每个操作，豁免的写明理由（13.4 第 6 条）。
4. **看不到的一律 404**：判定答 `shared.ErrNotVisible`（不带码），用例以 `errors.Is` 认出，换成自己资源的 404 码（按成员关系寻址的操作答 `workspace.member_not_found`，不答工作区的码）；看得到而角色不允许的答 403 `forbidden`。按地址寻址的值（如 slug）不合格式时答 404、不查库。写操作的码依次是 404 → 403 → 422 → 409：取值的检查与冲突都在锁与判定之后，避免泄露资源是否存在。
5. **父行锁先于判定；全局加锁顺序**：写事务先锁父行，再判定权限；判定，以及依赖它的计数（唯一的管理员），都在锁下进行（先判定、后加锁时，两位管理员互相降级会让工作区一个管理员都不剩，由 M2 的交错 2 守住）。全局加锁顺序从账户行开始，之后分两支：凭证 `users → auth_sessions → api_tokens`（M1）；工作区 `users → workspaces → …`（M2、M3）。工作区行是它之下一切行的总闸：邀请、成员、笔记本、笔记本成员（M4 起还有节点）只在持有工作区行的锁时才加锁（工作区与成员关系的变化持 `FOR NO KEY UPDATE`，笔记本的管理写持 `FOR SHARE`），所以它们之间的先后不会成环，实际的次序随路径而变（成员身份结束的否决者先锁笔记本，订阅者再写邀请、成员与笔记本成员）；笔记本一支之内是 `notebooks → notebook_members`，M4 起的行接在笔记本之后，并补进本条。笔记本的管理写先以 `FOR SHARE` 锁工作区行，再锁笔记本行，然后判定：工作区行把它们与工作区成员关系的一切变化串起来（M3 总设计第 4 节）。
   - **第一条语句**：多条语句的写事务，第一条语句锁它在这个顺序中最先要锁的那一行。跨父行锁同一张表的多行时，按 `id` 升序在一条语句里取完（`ORDER BY id … FOR NO KEY UPDATE`，如停用的 `LockWorkspacesOf`）；同一父行锁下的多行写入已由父行串行，不另排序。
   - **父行的锁模式**：改父行本身或它下面的成员关系与角色的（改名、删除；接受邀请、改角色、移出、离开、`reactivate-member`）取 `FOR NO KEY UPDATE`；彼此可以并行、只需挡住前者的（创建、删除邀请）取 `FOR SHARE`，先后由唯一索引决定，之后要改的子行用 `FOR UPDATE` 锁住重读（`LockPendingInvitation`）。锁前读到的子行一律在锁下重读，以锁下的为准。
   - **锁父行的语句带 `deleted_at IS NULL`**：等锁期间提交了删除的，PostgreSQL 在新版本上重新判断条件，读到 0 行，用例答 404。
   - **增长路径**：让账户获得新访问的事务，第一条语句是账户行的 `FOR SHARE`（第 18 条），在锁任何工作区之前就与停用串行。
   - **停用**在两支之间交替：账户行（`FOR NO KEY UPDATE`）→ 他的工作区（`id` 升序）→ 写账户行 → 会话 → 邀请 → 成员。不会成环：凭证一支的行只由先锁了同一账户行的事务、或只碰一行的单条语句锁住；在工作区一支里等账户行的只有增长路径，它们手里还没有工作区的锁。
   - **外键检查**：写入引用账户的列（`created_by_id`、`updated_by_id`、`user_id`）时，PostgreSQL 只对被引用的行取 `FOR KEY SHARE`：它与 `FOR NO KEY UPDATE` 不冲突，也越过排在后面等独占锁的事务，所以工作区一支从不等停用。改有唯一约束的列（`users set-email` 改 `email`）取 FOR UPDATE 级的行锁，会挡住这些检查；改邮箱只碰账户与会话，从不等工作区一支的锁，所以只是等待，不成环。让改唯一列的写进入工作区一支，或者订阅者写引用别的账户的列时，要重新核对。
   - **其余**：只碰一行的单条语句（续期、退出、撤销 PAT、改显示名）不持有别的锁；读操作不加锁（8.3），给别的模块的不加锁读取（如 identity 的目录）可以在调用方的事务里执行，但不取锁；清理与尽力而为的写入（如 PAT 的 `last_used_at`）用 `SKIP LOCKED`，从不等待，不进入这个顺序。
   - 新的写路径与已有路径的交错由确定性的并发测试守住（13.4 第 4 条；M2 的 14 个在 `bootstrap/interleavings_*_test.go`）。
6. **软删除与清理**：软删除用 `deleted_at`，唯一约束用 `WHERE deleted_at IS NULL` 的部分唯一索引。连带软删除的行（工作区与它的成员、邀请，以及订阅者的行）在同一个事务里、用同一个时刻，订阅者以事件带来的时刻作为自己的 `deleted_at`。成员关系的结束（`ended_at`）不是软删除：行保留，供恢复使用。
   - **登记**：新表如有 `deleted_at`，同一次改动向清理注册表登记：模块提供包级的 `Purgers(pool) []jobs.Purger`，每个清理器是表名，加上"删一批 `deleted_at` 早于某个时刻的行"；组合根 `bootstrap/registrants.go` 的 `purgers(pool)` 从叶到根排列，引用别的模块的模块排在前面。
   - **清理器**：一条语句按批删（`DELETE … WHERE id IN (SELECT … WHERE deleted_at < $1 LIMIT $2 FOR UPDATE SKIP LOCKED)`），跳过别的事务持有的行。父行的删除不经 `ON DELETE CASCADE` 连带删除子行：同一模块之内，父表的清理器只删已经没有子行的行（`NOT EXISTS`，如 `PurgeWorkspaces`），子行被跳过时父行随它推迟到之后的运行，从不等锁，同一张表里的父子（M4 的页面树）同理；跨模块时，父表的清理器看不到子表（第 24 条），所以指向别的模块里被清理的表的外键用 `ON DELETE RESTRICT`，每一行只由它自己模块的清理器删除，父行仍被引用时这一批删除失败、清理停下（第 23 条），由之后的运行在子行清掉之后完成，子行被另一次清理持有时父表的外键检查会等它提交。行背后有文件的（M7 的附件），先删文件、再删行。
   - **测试**：`bootstrap/purge_test.go` 的 `TestEverySoftDeletedTableHasAPurger` 核对每张有 `deleted_at` 的表恰好有一个清理器，`TestPurgersComeBeforeTheTablesTheyReference` 核对外键的先后；自引用的外键不在后者之内，有这种外键的表另写测试。
   - 撤销凭证不是软删除：会话与 PAT 记下撤销时间，行保留（续期据此拒绝旧令牌，列表不显示撤销的 PAT），不登记清理；会话过期之后由会话清理任务删除。
7. **迁移归属**：改哪个模块的表，迁移就归哪个模块。
8. **错误码**：可预期的失败返回 `*shared.Error`：模块的错误码带模块前缀（例如 `page.locked`），字段错误码只用 `shared` 的封闭集合（与接口描述中 `FieldError.code` 的枚举相同）。新的错误码先写进操作的 `x-problem-codes`，再在本模块 `adapter/http` 的测试中经 `apitest.CheckResponse` 答出一次（这个包的 `TestMain` 是 `apitest.Main(m)`）。
9. **时间**：用例从注入的时钟取时间；需要"时间流逝"的测试推进时钟，不真的等待。一个操作只读一次时钟，连带写入的行与交给订阅者的值用同一个时刻；"同一个时刻"要用每读一次就前进的时钟才测得出（workspace 的 `app` 测试的 `firstTick`）。e2e 在 SQL 里比较 `timestamptz`（JS 的 `Date` 只到毫秒）。
10. **日志**：从不记录密码、令牌、令牌哈希、`Authorization` 头、页面正文与邮箱；账户、会话、令牌只记 id（`user_id`、`session_id`、`token_id`），另可记客户端 IP、限流的桶、错误码与执行者（`by`：`self`、`cli`）。邮箱只出现在管理员命令写给自己终端的标准输出里。认证失败的原因是固定的文本，不带解析库的错误（伪造的令牌里的字符串会进日志）。由用例的日志测试（如 `TestRegisterLogsTheAccountButNoSecret`）与 `TestUsersPrintAndLogNoSecret` 守住。业务资源同样只记 id（`workspace_id`、`member_id`、`invitation_id`），另可记不含个人信息的取值（角色、加入的方式）。由调用者的凭证发起的操作，`user_id` 是调用者，对象是别人的成员关系时另记它的 `member_id`；命令行的操作，`user_id` 是被操作的账户，另带 `by=cli`。邀请令牌、被邀请的邮箱与派生的密钥从不记录，由用例测试的 `assertNoAddressOrToken` 与 `TestWorkspacesLogNoAddress` 守住。
11. **模块入口**：模块只经模块根接入。`New(Deps)`（没有依赖时 `New()`）装配 HTTP 一侧，`Register(router, api)` 挂载接口；组合根需要的其余部分由方法提供：`PublicOperations()`、`RequestTimeouts()`（按路由缩短的期限）、`Jobs()`，identity 另有 `Authenticator()`。命令行用包级的 `NewAdmin(AdminDeps)`。给别的模块的窄端口与注册者用只凭连接池的包级构造（如 `identity.NewAccounts(pool)`、`workspace.NewMemberships(pool)`、`NewInvitationCheck(pool, key)`、`NewDeactivation(pool, …)`），扩展点的类型在模块根以类型别名公开，它的值的常量（如 `EndCause` 的取值）有使用者时一起公开。没有 HTTP 一侧的模块（access）的 `New(Deps)` 返回它提供的端口（`shared.Authorizer`），组合根先建它，再交给别的模块的 `Deps`。组合根的一致性检查与注册表所需的东西由模块根的包级函数与常量提供：`Actions()`、`Purgers(pool)`、`Reserved()`、派生密钥的 info（如 `InvitationKeyInfo`）。两个模块同形的值（`identity.Deactivation` 与 `workspace.Deactivated`、`identity.Profile` 与 `workspace.Profile`）在组合根逐字段转换（`bootstrap/registrants.go`、`directory.go`），不为它们在 `shared` 里建公共类型。只有组合根导入模块，而且只导入模块根；同一模块的适配器互不导入，在 `app` 的端口处相遇（archtest）。模块需要的外部能力在 `app/ports*.go` 声明端口，由组合根接线。
12. **平台与共享内核**：平台包之间互不导入（`config` 除外），也不导入模块、组合根与 `shared`；`shared` 只依赖标准库。两者之间要用的类型由平台声明小接口，`shared` 按结构满足，组合根用编译期断言固定。`domain`、`app` 与 `shared` 只用标准库，唯一的例外是 Unicode 规范化（`golang.org/x/text/unicode/norm`：密码规则判断的是哈希器哈希的 NFKC 形式）。依赖方向、模块的分层与生成代码的导入范围由 `internal/archtest` 守住。
13. **接口先行，生成物入库**：先写 `api/modules/<模块>.yaml` 并在 `api/openapi.yaml` 登记，写法由 `apitest` 的规则测试检查（例如每个操作显式声明 `security` 与 `x-problem-codes`）；再 `make gen`，生成物随改动一起提交，持续集成用 `make gen-check` 核对，不手改；生成代码只被所属适配器导入。
14. **逐路由中间件与长连接路由**：接口操作经生成代码挂上平台的逐路由中间件，顺序固定为：请求信息（经可信代理认出的客户端 IP、User-Agent）→ 请求期限 → 请求体上限 → 失败闸门与认证 → 限流 → 请求体结构检查（`API.Middlewares`；认证与限流对调、结构检查移到认证之前，都有测试失败）。保持响应的路由（SSE、MCP 流）用 `httpserver.LongLived` 包装、直接挂在根路由器上：它豁免请求期限，同时绕过上面全部中间件（`RequestMetaFrom` 在那里是零值）。第一个挂载它的 M 由平台导出一个复用这些部件的入口（请求信息、失败闸门、`Authenticator`、按凭证的限流、请求体上限），不在模块里重写。
15. **配置**：新的配置项写进内置的 `config.yaml`，带默认值与注释；在 `platform/config` 中是强类型的一节，校验写在 `validate`，并在日志表示（`LogValue`）中显式列出，机密整体脱敏。未知键、空值、越界值启动即失败。组合根把配置交给模块的 `Deps`，模块不自己读配置文件或环境变量。test 配置把限流的桶调到用不完、argon2 降到最低（`TestBuiltInProfiles` 核对），限流本身的测试另起小桶的服务。同一个量在前后端各有一份时（续期的 8 秒：`config/validate.go` 的 `webRefreshTimeout` 与令牌管理器的 `REQUEST_TIMEOUT_MS`），两边的注释互指，各自的测试钉住这个值，服务端的配置校验保证自己的期限在它之内。
16. **迁移**：纯 SQL，内嵌进二进制，文件名 `NNNNN_<归属>_<说明>.sql`；每条都有 Down，全部回滚后 schema 为空，重新迁移的结果不变（由测试守住）。新迁移里的表与序列，在同一个提交中写进 `deploy/runtime-grants.sql`（逐表的 DML，不给 DDL）；`bootstrap` 的运行时角色测试以恰好这些权限运行服务与命令，缺了就失败。River 的迁移由 `rivermigrate` 逐字导出，升级 River 另写一条迁移（`migrations/river_test.go` 核对）。
17. **默认拒绝与两种凭证**：接口操作都要求 `Authorization: Bearer`。公开操作只由模块的 `PublicOperations()` 声明，契约中同时写 `security: []`；`TestPublicOperationsAreTheContractsPublicOperations` 在接好线的应用上逐个核对。需要令牌的操作同样接受会话的访问令牌与 PAT（`TestEveryOperationAcceptsAPersonalAccessToken`）。用例经 `shared.RequireActor` 取调用者，不区分凭证，除非规则本身与凭证有关（例如改密码时保留调用方的会话）。401 只表示调用方的凭证无效，前端的令牌管理器据此续期或结束会话；业务上的失败另用码：当前密码不对答 422，账户停用答 403。
18. **账户行锁**：签发或改变凭证的事务（登录、改密码、创建 PAT、停用，以及管理员的命令），第一条语句以 `FOR NO KEY UPDATE` 锁账户行（它不挡外键检查的 `FOR KEY SHARE`）。由调用方的凭证发起的，锁下再核对这个凭证仍然有效（`CredentialLock`）：核对的是其间的变化（撤销、停用），期限按请求的时刻判断，与认证中间件一致，等锁期间到期的凭证照样完成这个请求。让账户获得新的工作区访问的事务（增长路径：创建工作区，经接口与 `workspaces create`；接受邀请；`reactivate-member`；以及之后的同类路径），第一条语句是 `identity.Accounts.ShareActiveAccount`；命令行按邮箱指定账户时用 `ShareActiveAccountByEmail`（等锁期间邮箱被改走，答 `account_not_found`）。它取 `FOR SHARE`，与停用串行；在事务之外调用即报错（事务之外的 `FOR SHARE` 随语句结束）；交回锁下读到的邮箱（接受邀请据此比较）；账户已停用时答 403 `identity.account_deactivated`，调用它的操作在 `x-problem-codes` 中声明这个码。笔记本一侧的增长（建笔记本、添加成员、接管）不取账户行：它们持工作区行的 `FOR SHARE`，而停用先以 `FOR NO KEY UPDATE` 锁住他全部的工作区，两者已经串行（第 5 条）。让别人加入工作区的增长路径，在工作区的锁下还核对规则三（3.2）：没有有效管理员时，非管理员的加入答 409 `workspace.no_admin`。密码在事务外按快照校验，锁下核对哈希（登录另核对邮箱）仍是快照；变了就对新值再校验一次。依赖账户状态的规则（新密码不能由邮箱构成）在锁下按锁住的行再判断一次，判断便宜，不必重算哈希。这些交错由确定性的并发测试守住（13.4 第 4 条）。
19. **事务里只有锁、比较与写**：密码哈希（argon2 有并发名额，拿不到答 503 `server_busy`）与随机令牌的生成在事务之前完成；提交之后没有会失败的步骤。
20. **限流**：平台的桶：公开操作用 `anonymous`（按客户端 IP），其余用 `authenticated`（按凭证 `session:<id>`、`pat:<id>`）；认证之前另有按 IP 的失败闸门 `auth_failure`（先预留，凭证失败才消耗）。模块需要专门的桶（登录、注册、校验当前密码的操作）时，在配置的 `ratelimit` 节加一个，经平台的 `ratelimit.Limiter` 取，拒绝时答 `shared.RateLimited`。429 带 `Retry-After`；`rate_limited` 只写在契约顶层的 `x-problem-codes`。按 IP 计数用 `RequestMeta.IPKey`（IPv6 按 `ratelimit.ipv6_prefix_len` 的前缀）；客户端 IP 只采信 `server.trusted_proxies` 转发的 `X-Forwarded-For`。平台的桶的拒绝记 debug（访问日志已有 429），模块的桶记 info（撞库的信号）。
21. **扩展点与注册者**：
   - **形状**（照停用）：值与接口在建立它的模块的 `app/extension.go`，模块根以类型别名公开，注册者经 `Deps`（命令行经 `AdminDeps`）交进去。否决者在锁住相关的行之后（多行按 `id` 升序）、任何写入之前同步调用，返回 `*shared.Error` 时整个操作回滚并答出它的码；订阅者在写入之后、同一个事务内调用，任何错误都整体回滚。事件的值带时刻与执行者，订阅者用这个时刻写自己的行。一个扩展点由多条路径触发时（成员身份结束：移出、离开、停用），各路径调用同一组注册者，值里带原因。
   - **建立扩展点的 M** 在模块根上（接好线的模块与真实数据库）用测试替身证明以上各点（如 `identity/deactivate_test.go`、`workspace/extension_test.go`）；分发循环按登记的顺序调用每一个、第一个错误即停，由两个注册者的测试守住（`identity/app/deactivate_test.go`、`workspace/app/registrants_test.go`）。
   - **注册者**只凭连接池构造，可以带上它转调的、同样只凭连接池构造的注册者（`workspace.NewDeactivation(pool, vetoers, subscribers)`）；构造函数不叫 `New`（组合检查把模块根的 `New` 当作 HTTP 一侧）；语句经 `postgres.DB(ctx, pool)` 进入调用方上下文里的事务。
   - **组合在一处**：注册者在 `bootstrap/registrants.go` 组合（`deactivationRegistrants(pool)`、`workspaceRegistrants()`），serve 与命令行（`Users`、`Workspaces`）都从那里取，`archtest/composition_test.go` 断言各入口都到达它们。
   - **否决者的码**写进每个被扩展的操作的 `x-problem-codes`，在该操作所属模块的 `adapter/http` 测试中答出（`apitest` 按模块的描述核对），并加进前端的文案表；命令行打印同一个原因。写进否决者可能拒绝的那些操作：例如工作区的规则二写进 `deactivateMe`，笔记本的规则二写进 `leaveWorkspace` 与 `deactivateMe`，不拒绝移出，所以 `removeWorkspaceMember` 不加。
   - **行为测试**：第一个注册者所在的 M，在整个程序上经每条触发路径（接口与命令行）各有行为测试：组合检查只证明静态可达，把注册者换成空列表它照样通过。
22. **管理命令**：`nervewiki <名词> <动词>` 与 `migrate` 一样加载并校验整份配置，只组合连接池与模块的 `NewAdmin`，不构建模块的 `New`、HTTP、限流与后台任务；新命令的入口加进 `archtest/composition_test.go` 的起点列表。机密（密码）只从标准输入读，终端不回显，不收参数与环境变量。结果一行写到标准输出，日志写到标准错误并带 `by=cli`；失败时打印 `nervewiki: <原因>`、退出码 1，字段错误用命令行的名字（如 `--email`）。只在状态真正变化时触发扩展点。命令共用 `bootstrap/commands_admin.go` 的 `openAdminCommand`、`printResult` 与 `cliFieldName`；组合只有连接池、模块的 `NewAdmin`、只凭连接池的端口（如 `identity.NewAccounts`）与注册者。服务器管理员的命令不经规则表；审计列记被操作的账户本人（命令行没有自己的账户）。让账户获得访问的命令以 `ShareActiveAccountByEmail` 开头（第 18 条）。
23. **后台任务**：模块经 `Jobs()` 提供 River 的任务，worker 与定时任务放在模块的 `adapter/river`；River 只由 `platform/jobs` 与模块的 `adapter/river` 导入（archtest）。serve 在没有待执行的迁移之后才启动任务；停机顺序是 HTTP → 后台任务 → 迁移器 → 连接池。清理类的任务按批 `FOR UPDATE SKIP LOCKED`。软删除的清理是平台的定时任务（`platform/jobs` 的 `PurgeJob`，kind `platform.purge_soft_deleted`，serve 启动时运行一次，之后每隔 `jobs.purge_interval`）：模块不为它写 worker，只提供清理器（第 6 条）；它按登记的顺序运行，每一批各自提交，任何一个清理器失败就停下，由 River 重试。由请求投递的任务（M7 起）用只投递的客户端，在请求的事务里投递（见 M7 的移交）。
24. **SQL 与约束**：查询只写在模块的 `adapter/postgres/queries/*.sql`，经 sqlc 生成；`sqlc.yaml` 每个模块一条，只看得到本模块的迁移（`sqlc_test`）；模块的其余代码不直接执行 SQL（`rawsql_test`）。约束违反在仓储里按约束名翻译成领域错误（如 `users_email_key` → `identity.email_taken`），约束与索引的名字由 `migrations/schema_test.go` 列出。
25. **派生的密钥与令牌**：需要 MAC 一类密钥的地方（刷新令牌、邀请令牌，M7 起的签名地址），都由组合根从 identity 的签名私钥经 HKDF 派生：`SigningKeys.Derive(info)`，info 是带用途与版本的常量（`nervewiki <用途> mac v1`），各不相同，由需要它的模块根导出（如 `workspace.InvitationKeyInfo`）。签名私钥由组合根先加载（`identity.LoadSigningKeys`），派生的密钥只经 `Deps` 交给使用它的适配器（如 `workspace/adapter/mac`），不进 app 层、配置与日志。令牌带前缀（2.3），先核对总长再严格解码（一个令牌只有一种拼法：Go 的严格解码仍跳过 `\r`、`\n`），以 `hmac.Equal` 比较，在任何查询之前核对；不存库的令牌由密钥随时重新算出。换签名私钥或改 info，由它派生的令牌一起失效，所以派生出的密钥由已知答案的测试钉住（`TestTheInvitationKeyIsPinned`）。
26. **顶层路径与保留名单**：服务端根路由器上新的顶层路径（如 M9 的 `/mcp`）与前端新的顶层路由段，同一次改动写进工作区 slug 的保留名单（`workspace/domain/reserved_slugs.txt` 的 `[server]`、`[app]`），由 `bootstrap/reserved_test.go` 与前端的 `reserved-slugs.test.ts` 核对。新段优先取 `[reserved]` 里已有的名字（从那里移过去）；名单之外的新名字可能已经是某个未删除工作区的 slug，它的地址会被遮住，起名的 M 在设计里写明怎样处理（M2/P1 3.6）。

### 13.2 前端

1. **会话与分代**（9.4）：只有 `src/session/` 创建客户端；每个 `loginId` 一代 `RootStore`，`AppProviders` 随之重新挂载，SWR 的缓存随代，键不带 `loginId`；跨代共用的只有 `AppStores`。旧一代的请求以 `SessionChangedError` 结束：发出之前、答复头到达时（不论答复是什么）、续期之后重发的答复头到达时都核对，用到它的地方忽略它。浏览器写不进存储时（已满或被阻止）不能保持会话：写入以 `SessionStorageError` 失败，标签页注销这个会话并回到登录页，而不是停在加载中。没有 `navigator.locks` 时的租约只能尽力串行，严格串行要 HTTPS。同一资源的写在一个标签页里依次发出：经 `oneAtATime`，或由发出它的控件在发送中不接受新的操作（表单的按钮禁用、角色菜单 `aria-busy`）；改同一列表中不同项的写可以并行。store 的每个写在答复之后经同一个 `changed()` 计数并改列表，读出去之后已有写答复的读被丢弃。把一项加进列表的写（创建、接受、邀请）先按 id 去掉列表里已有的那一项：读可能已经含它。删除类的写（删除、离开、移出、撤回、撤销 PAT）答本资源的 404 时当作已完成，从列表移出；答 403 时保留并说明原因。这些由各 store 按写表格驱动的交错测试守住。
2. services 只调用接口，stores 只管理状态，组件不直接调用接口。
3. 以生成的 TS 类型为准，不写转换层。
4. 新增文案时 `zh-CN` 与 `en` 一起加，键保持一致。
5. 类型检查、knip 为零；oxlint 零警告。
6. **接口客户端**：只有 `services/` 导入 `@nervewiki/api-client`（类型与调用，不含 `createClient`），只有 `src/session/`（与测试）创建客户端；stores 与组件连类型也从 service 取。oxlint 默认禁止、按目录放行，不放宽规则。service 把非成功的答复转成 `ApiError`（保留 `problem` 与 `Retry-After`），调用方按 `code` 分支。依赖方向：services 只导入 `@nervewiki/api-client` 与 services 自己，不导入 `app/`、`stores/`、`pages/`、`components/`、`onboarding/`；stores 不导入 `app/`、`pages/`、`components/`、`onboarding/`。oxlint 按目录检查（`.oxlintrc.json`）。
7. **加载与重试**：页面用 SWR 驱动加载（`useSWR(key, () => store.x.load())`），store 保存结果。重试由 `app/retry.ts` 决定：`SessionChangedError` 不重试；带 `Retry-After` 的（429、503）按它等，最多 5 次；其他 4xx 不重试；5xx 与断网指数退避。表单从不自动重新提交。每个由 SWR 加载的页面或区块，失败时经 `app/not-loaded.tsx` 说明原因并给出"重试"，不当作加载中；它的测试包括"读不到时说明原因、重试之后加载"与"再读一次时显示别处的变化"（P5、P6 的审查两次发现这两类缺口）。
8. **页面与 CSP**：页面在 `routes.tsx` 中按需加载。页面的 CSP 固定为同源、没有内联脚本；需要放宽时，同时修改 `webui` 的 CSP 与 e2e S2 的断言。
9. **控制台**：vitest 与 e2e 中任何未声明的控制台错误或警告都让测试失败。vitest 中预期的输出用 `mockImplementation` 显式声明；e2e 中刻意引起的输出（例如 4xx 在 Chromium 留下的 "Failed to load resource"）用 `pageWatch.expectConsole` 按顺序声明（`failedToLoad(status)`）。
10. **路由与守卫**：除登录、注册与邀请页外，所有页面都要登录，不存在的路径也先登录再显示 404；新页面挂在 `Onboarded` 之下。去向只由守卫（`app/guards.tsx`）与工作区的外壳（第 16 条）决定：页面在登录、注册、退出、停用、删除或离开工作区之后，只改变会话或 store，不自己跳转。`next` 只接受 `safeNextPath` 认可的本站路径。新的顶层路由段写进保留名单（13.1 第 26 条）。
    **公开页面**：邀请页 `/invitations/:id` 的令牌只在地址的片段里（3.2），而守卫会把片段编进 `next`，所以它挂在 `GuestOnly` 与 `SignedIn` 之外，因而也不在 `Onboarded` 之下。它经 `useSession` 按会话自己显示；页内的登录、注册、退出同样只改变会话，页面停在带片段的地址上。接受不是会话的变化，之后由页面 `replace` 进入工作区，还没完成引导的由 `Onboarded` 先带进引导。再有公开页面时照此写，并在这里列出。
11. **错误的文案**：problem 码与字段码到文案的映射在 `app/problem-messages.ts`，两种语言。vitest 读 `api/dist/openapi.yaml` 核对：契约中每个操作声明的码都有文案，只列出页面不显示其错误的例外（续期、退出）。没有文案的码显示通用的错误与码本身。字段码的文案先找 `field.<字段>.<码>`，没有时用 `field.<码>`；按字段的文案是全局的，不分操作（`field.email.not_allowed`、`field.email.duplicate` 现在只有邀请答出）。别的操作对同一字段答出同一个码而意思不同时，要么改写文案让两处都适用，要么到那时给 `formErrors` 加按字段码换说法的选项：第 12 条的 `texts` 只换 problem 码。
12. **表单**：所有表单经 `app/form.ts` 的 `useForm` 发送：本地检查不通过就不发，发送中按钮禁用；服务端的字段错误显示在字段下方（`onField` 可以把个别 problem 码也放到字段下方，例如当前密码不对），其余显示在表单上方（`role=alert`）；失败之后焦点移到第一个 `aria-invalid` 的字段；成功的提示放在一直挂载的 `<output>` 里，只换文字。答复回来之后改写字段（去空白回写、清空、标记已保存）的表单记编辑次数，发出之后字段被编辑过就保留用户的草稿（`DisplayNameForm`、`RenameForm`、`InviteForm`）。标签必须有 `htmlFor`（oxlint）。同一个 problem 码在个别页面另有说法时，页面把 `texts`（`ProblemTexts`：已有文案的 problem 码 → 不带占位符的文案键，写错不能编译）交给 `useForm` 的第二个参数 `{ onField, texts }`、`ConfirmDialog` 或 `CredentialsForm`；它作用于表单上方、`onField` 的字段下方与对话框里的原因，没有列出的码照常经 `errorText`（如停用对话框的 `workspace.sole_admin`、邀请页注册被拒的 `identity.signup_disabled`）。不能撤回的操作经 `ConfirmDialog`：发送中不能关闭，拒绝留在对话框里；要先输入确认词的（删除工作区要输入 slug）用 `typedConfirmation`。
13. **只显示一次的秘密**（PAT；邀请链接不是：它由服务端随时重新算出，管理员可以随时复制，接受还要求邮箱一致）：只放在显示它的对话框组件的 state 里，不进 store、存储、地址、控制台与日志；对话框关闭即卸载，迟到的答复什么也不显示。列表只持有不含秘密的字段。由 A10 的页面版本核对。
14. **日期**：日期与时间经 `i18n/format.ts`（`Intl.DateTimeFormat`，按界面语言与浏览器时区）格式化，不引入日期库。vitest 的时区固定为 UTC（`vite.config.ts`），测试在任何宿主时区下结果相同。
15. **按工作区的数据**（M2）：一个工作区的列表（成员、邀请，M3 起的笔记本等）各是一个 store，每代按工作区 **id** 缓存一个：`RootStore.membersOf(workspace)`、`invitationsOf(workspace)` 经 `once`，渲染中取用是幂等的；store 带着 slug 去请求。页面的 SWR 键带工作区 id（`["members", workspace.id]`），别处要它重读时用同一个键。按 id 而不按 slug：同一代里删掉一个工作区、再用它的 slug 建一个，不会看到前一个的数据。每个这样的 store 有两种测试：同一工作区同一个 store、别的工作区与新的一代是新的（`root.store.test.ts`）；从一个工作区的页面直接到另一个的，各读各的（`members-page.test.tsx`）。
16. **工作区的外壳**（M2）：`/:slug` 下的页面由 `WorkspaceLayout` 在这一代的工作区列表（SWR 键 `workspaces`）里找到工作区之后才渲染，经 `useWorkspace()` 取当前工作区，不另请求。外壳按工作区 id 重新挂载子页（`<Outlet key={workspace.id}>`）：React Router 换参数时复用组件，前一个工作区的表单状态不能带到下一个，页面不必自己处理换工作区。让当前工作区消失的操作（删除、离开）由 `WorkspaceStore` 记下这一代去掉的 slug（`wasRemoved`），外壳对这些 slug `<Navigate replace to="/">`，对其余找不到的显示 404；页面自己跳转的话，外壳会在跳转之前先显示 404。`/` 由纯函数 `landingPath` 落到本设备最后访问的工作区（`nwiki.workspace`，只存 slug）、按名称的第一个，或创建页。
17. **列表与行内控件**：同一页有几个列表时，每个列表都有名称（`aria-label`）。行内控件的可访问名称以可见文字开头并带上对象，看得到邮箱时带上邮箱（"复制链接：bob@…"、"移出 Bob（bob@…）"，WCAG 2.5.3）。删除、移出、撤回成功之后，触发按钮随行消失，焦点经 `ConfirmDialog` 的 `focusAfter` 移到这一节的标题（`tabIndex={-1}`）；就地的变化（改角色）焦点回到触发按钮。让整页离开的操作（删除、离开工作区，接受邀请进入工作区）之后的焦点，在 M3 与页面树一起设计。

### 13.3 Markdown

1. 系统从不改写正文，唯一的例外是 4.5 的链接改写。
2. Markdown 的语义以 `tools/md-fixtures/` 为准，提取与渲染都经过服务端同一个 `Parse`；新增方言特性时先加样例，并用 `tools/md-fixtures/obsidian/` 与 Obsidian 核对。

### 13.4 测试

1. 测试针对行为；Go 用标准库 `testing`，表格驱动。新的门禁、规则或契约检查，先用反向对照证明它会失败。
2. 需要数据库的测试用 `pgtest` 从已迁移的模板库复制一个独立的库（`-short` 跳过）。开发库、测试容器、端到端测试与镜像冒烟用同一个带发行版名的 PostgreSQL 镜像与同一组建库参数，由测试核对。
3. **端到端测试**（10.1）：一个故事一个文件，放在 `e2e/stories/<分组>/`，从 `e2e/fixtures/test.ts` 取 `test`、`expect` 与 fixture；被测对象是 `make build` 的产物，构建参数与镜像相同。`page` fixture 从第一次导航之前就受监视，测试通过时要求它安静：没有未捕获的异常、CSP 违规，控制台没有错误与警告，除了用 `pageWatch.expectConsole` 声明的；另一个账户的标签页用 `anotherPage(tokens)`：同样从第一次导航之前受监视，测试通过时要求安静，测试结束时关闭（M3/P5）。页面发出的接口请求由故事自己断言。登录状态由 `signedInPage(tokens)` 注入，令牌经接口取得；完成引导的账户用 `registerOnboarded`，它记录前端注册表的全部步骤；管理员完成引导的团队用 `newOnboardedTeam`。需要别的配置的服务用 `nervewikiWith`；命令行用 `fixtures/admin.ts` 的 `nervewikiUsers`、`nervewikiWorkspaces`，期待失败的用 `…Fails`（退出码 1、没有输出、最后一行是原因）。有业务数据的故事另有 PAT 接口版本，两个版本调用 `e2e/fixtures/assert/<模块>.ts` 中按表组织的同一组断言（M1 建立 `identity.ts`，M2 建立 `workspace.ts`；时刻的精确比较在 SQL 里做）；页面版本准备的数据要让这些断言有东西可断（如删除工作区时另有成员与待接受的邀请）。故事之间不共用数据：邮箱与 slug 由 `emailFor`、`slugFor` 按测试与重复次数派生（worker 的库在它的测试之间共用），全表计数只用于同一测试内前后比较"没有新增"。页面操作用 `<动作>With(page, …)` 夹具做一次，返回那个请求的答复（`answerTo`）；页面请求可能带秘密时，故事收集完整地址，断言秘密不在其中（W6）；取得令牌之前的故事，接口版本直接调认证接口；只能由命令行或后台任务完成的，只有那一个版本。异步的结果用 `expect.poll` 等，不用固定的等待；与时间流逝有关的故事（到期）经数据库把状态推到边界之后，不靠墙钟的窗口，精确的边界由注入时钟的单元测试守住。
4. **并发与交错**：锁与交错的测试在真实数据库上用 `pgtest.WaitForLockWaits`（按表计数用 `WaitForLockWaitsOn`）确定地等到对方在等锁，不靠 sleep；持锁一方的握手与释放都有期限，出错立即失败。时间用 `clocktest.Fixed`（并发安全）推进。交错测试在 `bootstrap` 里经接好线的应用发出请求，或在进程内运行命令，不给用例加测试用的接缝：测试先持有双方都要的那一行（`interleaveOn`），等第一个请求在等它时再发第二个，然后放开；PostgreSQL 按到达的先后交出行锁，所以结果是确定的。凡有两种先后的各跑一次（`orders`）。等唯一索引上的插入者用 `pgtest.WaitForKeyWaitOn`；要让先插入的一方停在写之后、提交之前，在测试库里用触发器去等测试持有的一行（M2 的交错 7）。
5. **整个程序的测试**：由契约推导的测试自动覆盖新操作，新模块只需接进组合根：路由正好是契约的操作；公开操作；需要令牌的操作都接受 PAT；参数与请求体的破坏答 400；problem 响应声明两个头；绑定任意字符串的路径或查询参数取 NUL 与非 UTF-8 时不答 5xx（`TestFreeTextParametersDoNotAnswer5xx`，由 `apitest.Operation.TextCases` 推导）。
6. **权限矩阵**：`bootstrap/permission_matrix*_test.go` 在接好线的应用与真实数据库上经 HTTP 断言"操作 × 身份"的每一格：状态码与 problem 码，行还可以核对回答的内容。工作区一级的列是管理员、成员、访客、从来不是成员、已结束的成员、已删除的工作区；M3 加笔记本角色、`workspace_access` 与无主的列，不另起框架。读的格共用一份准备好的库，写的格（行标 `write`）各用一份 `pgtest.NewDatabaseFrom` 的副本；数据由 SQL 写入，覆盖检查要在准备之前知道每行指向的 id。`TestThePermissionMatrixCoversEveryOperation` 要求契约中每个操作都有行，或者在 `matrixExempt()` 里按类写明理由（整个模块不判定、公开、按所持凭据判定、路径参数不指向某个资源）；路径参数必须指向本列的工作区或其中种下的行。每种缺口在 `TestMatrixViolationsCatchesEachGap` 各有一个反例。

### 13.5 工程

1. Makefile 是唯一的命令入口：`*-go` 只需要 Go，`*-web` 只需要 Node。新的门禁同时加进 Makefile 与持续集成：`make check` 加 `make gen-check` 对应 server、web 任务，`make e2e`、`make image-smoke` 对应 e2e、image 任务。
2. 版本精确固定：Go 由 `toolchain` 固定；Node 包不写范围，pnpm 由 `packageManager` 锁定，新版本满一天才解析；actions 按提交 SHA、基础镜像按摘要引用，注释写明对应的标签。Node 本身按大版本（`.node-version`）。
3. `.dockerignore` 排除的正好是 `.gitignore` 忽略的，改一个时同步另一个。
4. 语言：Go 与 TS 的注释、标识符、日志与错误信息用英文；Makefile、YAML、Dockerfile、shell 脚本等配置与脚本的注释和提示用中文；文档用中文。
