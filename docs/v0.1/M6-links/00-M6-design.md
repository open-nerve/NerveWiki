## 1. 目标

M6 结束时：

1. **方言**：`[[…]]`、`![[…]]`、`#标签`、callout、`==高亮==`、`%%注释%%`、数学公式在阅读视图里按 Obsidian 的样子显示（总体设计 4.1）。
   - 它们是 `Parse` 的语法树上的节点，提取与渲染出自同一次解析；
   - 样例集 `tools/md-fixtures/` 的提取期望（链接、标签、属性链接）第一次由 Go 测试全部核对。
2. **索引**：每条写入路径都在同一个事务里维护链接、标签、属性与别名的索引，并按总体设计 4.4 解析链接：
   - 新建、改名、移动、删除节点（连同子树），改写正文（含改了别名），都重新解析受影响的链接；
   - 阅读视图按索引显示每条链接是否解析到页面，链接状态变了的页面经事件流重读。
3. **改写**：改名或移动一页（连同子树）时，按字节位置改写受影响的链接，与改名或移动在同一个变更集里原子完成。
   - 需要改写的页面里只要有一页正被编辑（包括本人在编辑），整个操作答 409，列出全部这些页面与编辑者。
4. **接口**：反链、标签、标签下的页面、页面属性、补全用的链接目标；`nervewiki reindex` 重建全部索引。
5. **前端**：
   - 阅读视图：链接与标签在应用内跳转（包括普通 Markdown 的本站链接）；点未建的页时，写者确认之后新建；
   - 数学公式用 KaTeX，`mermaid` 代码块用 mermaid，都按需加载；
   - 编辑器：`[[` 补全页面与别名，`#` 补全标签；
   - 页面的右栏：大纲、反链、属性。

## 2. 范围

做：

- 服务端：Obsidian 方言的语法扩展；链接索引模块 `linking`；链接解析与重新解析；链接改写的参与者；链接状态变化的事件 `links`；反链、标签、属性、链接目标的接口；`nervewiki reindex`。
- 平台：
  - `==` 加进加固过的强调游程，由选项打开；
  - 表格包一层可滚动、可聚焦的区域（M4 留下的宽表格）；
  - frontmatter 的标量带字节位置，交给扩展；属性表给扩展一个写属性值的钩子；
  - 解析预算移到平台，由组合根共享；写入路径只带提取结果，不带语法树。
- 前端：
  - 阅读视图的链接跳转、标签页、KaTeX、mermaid；
  - 改名与移动被拒时的说明；
  - 编辑器的补全，编辑器扩展可以带自己在编辑器 chunk 里的代码（第 4.13 节）；
  - 右栏。
- 样例集：
  - 补上解析样例 `resolve/`，以及树与路径的改写样例 `rename/`；
  - 渲染的期望（注释、callout、公式、高亮）写在 `obsidian/render_test.go` 的表格测试里；
  - 解析与改写各有自己的核对脚本（`obsidian/verify-resolve.mjs`、`verify-rename.mjs`），与 Obsidian 1.12.7 核对（收尾修订：设计时写的 1.13.7 是 M0 的版本，隔离的实例报告的是 1.12.7）。

不做：

- 嵌入整篇页面（v0.1 显示为链接，总体设计 4.1）。
  - 附件的嵌入属于 M7，渲染的接缝也由 M7 建立（第 8 节，收尾修订）；
  - M7 之前没有附件节点，`![[x.png]]` 显示为解析不到的嵌入。
- 块引用 `^id` 的校验、锚点是否存在的校验（总体设计 4.4）。
- "没有链接的提及"（Obsidian 反链面板的 unlinked mentions）与关系图。
- 编辑器接收正文的外部更新：被锁的页不改写（第 4.6 节），编辑器用不到。
- 歧义链接的 lint：M6 在索引里记下歧义，lint 本身属于 M10。
- 编辑时的大纲（第 4.12 节）。

## 4. 关键决定

### 4.1 方言在平台里：`platform/markdown/obsidian`

**放在哪里**

- 语法扩展是纯粹的语法：wikilink、嵌入、标签、callout、注释、数学公式与高亮的渲染。
  - 它放在 `platform/markdown/obsidian`，与 M5 的 `platform/markdown/tasks` 并列；
  - goldmark 仍然只在 `platform/markdown` 之下导入，archtest 的 `markdownLibrariesStayInMarkdown` 不必改；
  - 它用 `platform/markdown` 导出的 `inLinks` 变换与 `Linker`（P3 B），处理"链接文字里的 wikilink"（样例 030、040）：两条链接都计入，渲染时里面那条不做成 `<a>`，避免嵌套的链接。
- 需要数据库的部分不在平台里：渲染时按页取链接状态的 `Fetch` 由 `linking` 模块给出，组合根把它交给 `obsidian.Extension(…)`，照 `markdownExtensions()` 登记。

**高亮**

- 分隔符式的 `==` 加进 `internal/harden/emphasis.go` 的游程，配对规则与 `~~` 相同。它是平台的改动，扩展做不到（M4/P3 移交第 2 项）。
- 只有 obsidian 经 harden 的选项打开时才识别，`markdown.New(nil)` 与差分测试里的实例照旧。
- 高亮的节点种类由 harden 定义，渲染函数（`<mark>`）与 `Markup` 归 obsidian。
- `=` 成为触发字符之后，goldmark 会在它后面尝试 GFM 的 linkify，`a==www.example.com` 会变成自动链接（GFM 规定 `www` 之前只能是空白或 `*_~(`）。所以 harden 的 `linkify` 包装在前一字节是 `=` 时不识别；`==www…==` 加进样例，`pieces()` 加入 `=`、`==`。
- wikilink、标签、`%%`、`$` 的节点之后同样会触发 linkify（goldmark 在代码段之后本来就这样），由 P1 的样例定。

**注释**

- `%%` 注释只影响显示，不影响提取（样例集规则 6）。语法树照常解析注释里的内容，一个变换把注释范围里的节点标为隐藏，渲染时跳过。
- 块注释按原文的行界定，语法树按 CommonMark 分块，两者会交叉（一个段落里只有中间几行在注释里；注释里不闭合的围栏延续到文末）。P1 写明隐藏的粒度：
  - 隐藏到行内节点为止；
  - 块与注释交叉时只隐藏落在注释里的那部分；
  - 与 Obsidian 不同的写成 `nerve-defined` 的渲染样例。

**数学公式与 callout**

- 数学公式是原始内容（规则 4、5），解析器整段吃下。
  - 行内 `$` 的结束位置按段落预先算一遍，保持线性；
  - 渲染为带 TeX 原文的占位元素，前端用 KaTeX 渲染。
- callout 是一个变换：把第一段以 `[!type]` 开头的引用块改成 callout 节点。
  - 带 `-`、`+` 的可折叠，渲染为 `<details>`；
  - 其余渲染为 `<div>`，类型写在 `data-callout`。

**渲染与样例**

- 每种节点都有渲染函数；元素、属性与 class 登记在 `Markup`（`nw-` 前缀），由 `CheckHTML` 核对。
- **样例先行**（13.3 第 2 条）：语法细节以 `cases/` 为准，P1 的 Phase 文档逐条列出实现与规则的对应。
  - 渲染的期望（注释、callout、公式、高亮）在 `obsidian/render_test.go`；
  - "HTML 里的链接与提取结果一致"（总体设计 4.3）扣掉注释里的链接，以及链接文字里那层 wikilink。

### 4.2 提取结果

`obsidian` 扩展的 `Extract` 给出：

- **链接**：`{Kind, Target, Anchor, Display, Key, Range}`，与样例集 JSON 的字段一一对应（README"提取结果的格式"）。
  - `Kind` 是 `wikilink`、`embed`、`link`、`image`；
  - 属性链接的 `Key` 是属性路径（`sources.0`），正文里的为空。
- **标签**：每一次出现，`{Name, Range}`；frontmatter 的 `tags` 由索引从属性里取。

两处要平台给出新的位置：

- **属性链接**要字节位置，现在的 YAML 解析没有保留位置（`yaml.go`），`Extract(root, content)` 也拿不到 frontmatter。改为：
  - `Frontmatter` 带一张标量表：属性路径、值、字节范围、引号风格；只收写在一行之内的字符串标量；
  - 范围从 `yaml.Node` 的起点按标量风格扫出：单引号的 `''`、双引号的转义；go-yaml 的列按字符计，换算成 UTF-8 字节；
  - 别名展开出来的值（`b: *x`）不在表里，不算属性链接（"同一段字节只出现一次"）；
  - `Extract` 改为 `Extract(Tree)`：语法树、正文与 frontmatter 一起给出。这是改 M4 扩展点的签名（总体设计 12.1 第 6 条的例外），M5 的任务项随之改一行；
  - 样例 060 守住。
- **Markdown 链接与图片的目标范围**：现在由核心的 `marks` 渲染，`ast.Link` 不带目标的字节位置。改为在 `internal/harden/links.go` 做链接时记下目标的范围，引用式链接的范围取自定义（规则 8，`LinkReferenceDefinition`）。
  - 范围不能存成节点的属性：goldmark 的 `renderLink` 会把 `data-` 开头或在 `LinkAttributeFilter` 里的属性写出来，差分测试就不再逐字节相同；
  - 所以存在一张旁表里（按节点），P1 定写法。

### 4.3 链接索引：`linking` 模块

**模块与表**

新模块 `server/internal/modules/linking`（总体设计 7.2），布局照现有模块：

- `domain`：解析规则、最短写法、改写的字节替换；
- `app`：索引的观察者、改写的参与者、查询；
- `adapter/postgres`、`adapter/http`。

表（linking 的迁移 00020–00024，一张表一个，P4 的 00025 给 `page_links` 加 `aliases`，P5 的 00026 加反链的索引；page 的 00019 给 `nodes` 加 `(notebook_id, name_key)` 的索引。都是派生数据，没有 `deleted_at`；P3 的定稿见 [P3 文档](03-P3-index.md) 3.2）：

| 表 | 列（要点） |
|---|---|
| `indexed_pages` | `node_id`（主键）、`notebook_id`、`revision`（索引所依据的正文版本）、`extractor`（提取规则的版本）、`frontmatter_valid` |
| `page_links` | 主键 `(source_id, range_start)`；`notebook_id`、`kind`、`property_key`、`target`、`anchor`、`display`、`range_end`、`target_key`、`target_alt_key`（目标最后一段的标题键，去掉 `.md` 与原样的两种，用来找候选；长于 1024 字节的不记）、`resolved_id`、`ambiguous`、`aliases`（属性链接写在 `aliases` 的值里，P4） |
| `page_tags` | `source_id`、`notebook_id`、`tag`（第一次出现时的写法）、`tag_key`（标题键）、`count` |
| `page_properties` | `source_id`、`notebook_id`、`position`、`key`、`value`（`jsonb`） |
| `page_aliases` | `source_id`、`notebook_id`、`alias`、`alias_key` |

上限（收尾修订，[M6 收尾审查](reviews/M6-closeout-review.md) A-I1）：一页至多记前 10,000 条链接（`domain.MaxLinks`）、1000 个标签与别名（`domain.MaxNames`），之后的不进索引；阅读视图对索引里没有的链接即时解析，改名、移动时不改写它们（改写按索引找链接）。

**外键与删除**

- **不带外键**（P3 定稿）：指向 `nodes`、`notebooks` 的外键与清理器的两条规则冲突（没有 `deleted_at` 的表不许有清理器，指向被清理表的外键又要求一个排在前面的清理器），照 `edit_sessions` 的先例不带。"只指向活着的节点"由整个程序的不变式 `checkLinks` 核对。
- 索引行只指向活着的节点：
  - 删除子树时，删掉被删页面自己的行；指向被删节点的链接在同一个事务里重新解析；
  - 删除笔记本不经写入单元（M4/P3 移交第 10 项）。linking 注册笔记本删除事件，在同一个事务里删掉这些笔记本的全部索引行；
  - 所以页面的清理不会被挡住，linking 不需要清理器。总体设计 12.4"笔记本删除事件"的注册者加上 M6。
- 恢复（M8）要为每一页带解析结果，经观察者重建索引（给 M8 的移交，第 7 节）。
- 新表写进 `deploy/runtime-grants.sql`；`sqlc.yaml` 加一条。

**索引的可用性**

- 索引不是权威，可以随时重建（第 4.10 节）。
- 读取时，以 `indexed_pages` 的 `revision` 与 `extractor` 判断它是否可用（第 4.7 节）。
- 改了提取规则的发布要提升 `extractor`，并在说明里要求 reindex。

**linking 读 page 的数据：端口**

sqlc 按模块限定范围，linking 的 SQL 不能 JOIN page 的表。page 的模块根经组合根给出这些读端口，都在调用方的事务里：

- 按标题键找节点（含种类、父节点、深度），节点的祖先链与子树；
- 页面的正文与 revision（改写与反链的上下文）；
- 一组页面上活着的编辑会话与持有人（显示名由 identity 的目录给，照 M5 的 `lock` 成员）；
- 重算标题键（reindex）。

### 4.4 解析

解析规则是 `linking/domain` 的纯函数：输入链接、出发的页面与候选节点，输出解析到的节点与是否有歧义。P3 用 `resolve/` 样例与 Obsidian 1.12.7 逐条核对（真实的 Obsidian，以及从它的安装包里只读地取出的 `MetadataCache.getLinkpathDest`）之后定稿，细节见 [P3 文档](03-P3-index.md)第 2 节。导出的位置照总体设计 3.5：页面 `A` 是 `A.md`，它的子节点在 `A/` 下。一条链接的**出发文件夹**是出发页的父节点（根下的页是笔记本根）。

**先定写法**：最后一段以 `.md` 结尾（不分大小写）的，笔记本里任何地方有去掉 `.md` 的那个名称的页时，读作去掉 `.md` 的；没有时读作原样（标题以 `.md` 结尾的页）。之后每一步只用这一种。

**次序**：前一步找到就停。

1. **相对路径**：以 `./`、`../` 开头的，从出发文件夹起，`..` 每个上一层（到根为止），再按段往下。找不到就解析不到。
2. **从根起的完整路径**：以 `/` 开头的，或者恰好是某个节点从笔记本根起的路径的（单个名称也算：`[[note]]` 先找根下的 `note`），就是它。这一步保证每个节点至少有一种只指向它的写法。
3. **名称与路径后缀**：名称按标题键比较；带 `/` 的按路径的后缀匹配，按整段对齐。匹配到多个时：
   - 先选在出发文件夹的整棵子树里的，文件夹自己的页也算（导出时 `A.md` 与 `A/` 并排）；
   - 再选路径短的：导出路径的字符数，按 JavaScript 的 `String.length`（UTF-16 码元），与层数无关；
   - 再按 id，并标记歧义（Obsidian 这时没有稳定的次序）。
4. **别名**：只对不带 `/` 的名称，以 `.md` 结尾的先按去掉 `.md` 的别名、再按原样的，多个时同第 3 步。Obsidian 不解析别名，这是总体设计 4.4 有意的差异（样例标 `nerve-defined`）。

**与 Obsidian 的不同**（都写进样例，标 `nerve-defined`）：别名；标题键用 Unicode 的完整大小写折叠（Obsidian 用 `toLowerCase`）；路径一样长时按 id；Obsidian 用小写路径的 `startsWith`、`endsWith` 比较子树与后缀，相对路径找不到时还按算出的路径找后缀，这里按整段、找不到就解析不到。

**其余**：

- 链接只在笔记本内部解析；只解析到页面，附件（M7）照 Obsidian"最后一段带 `.` 的先找这个文件名的文件"并入"先定写法"。
- 新建、删除（以及 M8 的恢复、M7 的导入）同样可能改变别的链接的指向。例如在出发页的父节点下新建同名的页，或删掉一页之后指向另一处同名的页。这些写不改写别的页面，只重新解析，与 Obsidian 一致。只有改名与移动"保住指向"（第 4.6 节），因为它们是用户对已有页面的操作，用户期待链接跟着走。

### 4.5 何时重新解析：索引的观察者

linking 注册为页面领域事件的观察者（12.4"页面领域事件与写入单元的参与者"），每个写入单元在提交之前调用一次，拿到合并后的全部变更（`Event.Changes`）：

1. **正文变了的页**（`Change` 带 `Revision`）：按提取结果替换它的链接、标签、属性与别名行，并解析它的每条链接。
2. **路径变了的节点**与**别名变了的页**：重新解析可能受影响的链接。
   - 路径变了的节点：新建的；改名、移动、删除的连同整棵子树。改名的变更只带被改名的那一个，观察者经 page 的端口取它的子树，因为改名一页就改了它全部后代的路径。
   - 候选是：目标的标题键是这些节点旧名、新名或别名的；解析到这些节点的；出发页在这些节点里的（相对路径与子树的偏好会变）；以及这些节点上每个别名的键（别名之间同样按路径取舍：P3 的性质测试发现）。
   - 路径的长度看名称，所以改名到同一个键而长度不同的（`Straße` → `STRASSE`）也算改名。
   - 不移动任何节点、只写正文的单元，只到它写的页自己的链接与它增删的别名的键：正文写不改任何页的路径（P3 审查：此前每次自动保存都在锁里重新解析这一页的全部反链）。
   - 只调兄弟次序的移动（父节点与名称都没变）跳过。
3. 只更新解析结果真的变了的行（解析到的节点变了；只有歧义变了的也更新，但不算"状态变了"）。在同一个事务里发一次 `links` 事件（第 4.8 节），带两组页面：
   - 链接状态变了的出发页，不含本单元正文变了的页，它们已在 `pages` 事件里；
   - 反链变了的目标页，包括本单元正文变了的页的新旧目标，它们的上下文行变了。

不读整个笔记本的树：按候选的标题键查节点，再查它们的祖先链。前后都空的变更（M9 的批量里建了又删的节点，[M9 移交](../M9-mcp/handoffs/M4-P2-unit-merge.md)第 2 项）不做任何事。

**并发**：

- 同一笔记本的两次正文写只持笔记本行的 `FOR SHARE`，可以同时进行。例如一页加了别名 `x`，另一页同时写了 `[[x]]`，两个事务都看不到对方，索引会停在"解析不到"。
- 所以观察者在开始时取 linking 自己按笔记本的一把锁，同一笔记本的索引维护串行。在 READ COMMITTED 下，后来者等到先来的提交之后，它的语句能看到先提交的行。P3 定为事务级的 advisory lock：`pg_advisory_xact_lock(int4 'link', int4 fnv32a(笔记本 id))`，两个整数的键与 goose、River 的 bigint 键不在一处；两本笔记本的哈希相同只多等待。
- 这把锁是单元最后取的锁，在页面正文的行锁与笔记本行之后，不会成环。reindex 同样先取笔记本行（`FOR NO KEY UPDATE`）再取这把锁；反过来会与持着笔记本行 `FOR SHARE`、等在正文行上的正文写死锁（P3 的交错测试）。外键检查只取 `FOR KEY SHARE`，与改名、软删除的 `FOR NO KEY UPDATE` 不冲突。树的单元本来就持笔记本行的 `FOR NO KEY UPDATE`，与正文写串行。
- 代价是同一笔记本的自动保存在提交处串行（给 M12 的性能移交）。

**多操作的单元**：参与者靠索引找候选与旧的指向，索引在单元结束时才更新。所以参与者要求单元开始前的索引是新的：

- M5 之前的单元都只有一个写操作；
- M9 的批量与 M7 的导入在一个单元里做多个写，要让观察者逐操作运行，或在改名、移动之前不做别的写（给 M9、M7 的移交）。

### 4.6 改写：参与者，被锁时整个拒绝

linking 注册为写入单元的参与者，在改名与移动之后调用（`Participate(ctx, Step, Appender)`）。

**1. 保住原来的指向**

改名或移动之后，凡是解析结果会因此改变的链接，都改写成仍指向原来节点的写法。包括：

- 指向被移动或被改名子树的入链；
- 子树里出发、因位置变了而指向别处的出链（相对路径、出发文件夹的子树的偏好）；
- 本来指向别处、改名或移动之后会被这个子树里的节点"抢走"的链接。

这比总体设计 4.5 第 1、2 条更宽：4.5 原来只说了入链与相对路径的出链，"被抢走"的链接按同一条原则一起处理（总体设计随之修订）。原来解析不到、改名之后解析到了的链接，不改写。

**2. 写法**

- wikilink 照 Obsidian 的 `fileToLinktext`：名称在笔记本里只有这一页（或它在根下）时写名称，否则写从根起的完整路径（第 4.4 节第 2 步总能唯一解析到它）；不再依次试路径后缀，原来的写法不保留（P4 文档 3.1）。
- Markdown 链接：普通的同 wikilink 加 `.md`；`./`、`../`、`/` 开头的保持，重新算路径（P4 文档 3.2）。
- 锚点、引号风格照 `rename/` 样例的规则保留；显示文字与链接文字的跟随、经别名的加显示文字照 P4 文档 3.1、3.2。
- 只在指向会变（解析到别处、解析不到、新有歧义）或只改大小写的改名时改写；`aliases` 的值、索引过时的出发页不改写（P4 文档第 2 节）。
- 写出之后整页读回：链接一条不少、改写的指向原来的页、页的别名不变；不成立就只改目标，再试只改正文（属性链接不改，逐条记日志）；都不成立或都超过一页的上限就不改这一页，记日志（P4 文档 3.1、3.4）。

**3. 字节替换**

- 只替换 `Range` 那一段（总体设计 4.5"按字节位置精确替换"）。
- 同一页有几条要改写时，合成一次追加的写，从后往前替换。
- 替换之后的正文经 `Parse` 得到新的提取结果，随追加的正文写交给守卫与观察者。

**4. 锁**

- 先算出需要改写的页，一次查出其中活着的编辑会话。
- 有一页被锁，整个单元答 409 `linking.pages_locked`，problem 带 `locks: [{page_id, user_id, display_name}]`，列出全部页面与编辑者（M5 的 `lock` 成员只能带一页）。
  - 这个错误由 linking 定义（它的领域错误实现平台的"附加成员"接口，照 M5 的 `lock`）；
  - 契约的 `Problem` 加 `locks`；
  - `renameNode`、`moveNode` 声明 `linking.pages_locked` 与 `server_busy`。
- 本人的锁同样拒绝：本人在别处编辑的那一页如果被改写，编辑器里的正文就过时了，下次保存会冲突。
- 被改名、移动的那一页自己的正文也可能要改写（指向自己的链接、移动时它的相对链接）。它正被编辑时同样拒绝。只有它自己的正文不需要改写时，改名、移动照常（负责人的决定，第 11 节第 1 项）。
- 开启、接管、强制解锁都取笔记本行的 `FOR SHARE`，排在改名之后，与预检之间没有窗口。心跳不取笔记本行：
  - 一个读时钟早于会话到期、提交晚于预检的心跳，会把预检看作已过期的会话续活；
  - 之后编辑锁的守卫在追加的写上答 `page.locked`。参与者收到它时重查一次会话，改答 `linking.pages_locked`；重查时会话已经结束的，照守卫给出的锁答（P4 审查 r2-4）。
- 预检只查要改写的页（P4 审查 r3-1、r2-1）。

**5. 次序与一致性**

- 改名、移动是树的单元，持笔记本行的 `FOR NO KEY UPDATE`，正文写在它提交之前进不来。
- 追加的写以当前 revision 为 base，按节点 id 升序（`unit_content.go` 的约定）。

**6. 关闭改写**

`Options.UpdateLinks` 为假时（M9 的 `move update_links=false`），参与者什么都不做，锁的预检也跳过，只由观察者重新解析。网页总是改写。

### 4.7 解析预算与内存

**写入路径只带提取结果**

改写一次可能追加很多页的正文写。现在每个写入路径把完整的语法树（`*markdown.Document`）放在 `Change.Parsed` 里，直到单元结束交给观察者，同一单元的语法树会同时占着内存（最坏约正文的 300 倍）。改为：

- 写入路径解析之后只保留提取结果：`Parsed` 是 `markdown.Facts`（frontmatter、各扩展的提取结果，不含语法树与原文）；
- 预算在提取之后只留提取结果那一份（约为正文字节的十分之一，`Facts.Limit` 的三百分之一，P2 审查 M1），到单元结束；
- 任务项的勾选在写之前要用提取结果，照旧。

**预算移到平台**

- 解析预算从 `page.Module` 移到平台（`platform/markdown.Budget`），由组合根建一个，交给 page 与 linking。
- 平台不能导入 `shared`（archtest 的 `platformIsBusinessFree`），503 `server_busy` 的转换留在各自的适配器。

**参与者在持锁时解析**

- 正文写在开启事务之前解析（总体设计 4.3、13.1 第 19 条）；参与者不同，它在单元里、持着笔记本行解析。
- 若照写入路径排队等预算，就与锁倒置：正文写先取预算再等笔记本行，改名持着笔记本行再等预算。逐页各等 2 秒，几十页还会超过请求的期限。
- 所以参与者不在持锁时排队：逐页不排队地取（`Budget.TakeNow`，有排队的也不插队），取不到立即答 503；解析、提取之后照 `KeepFacts` 只留实际的那一份，到单元结束（P4 文档第 5 节）。
  - 原定一次取够（最大的一页加各页提取结果那一份的上限）：那个上限按 YAML 的最大值算，每页至少约 13.7 KB，默认 8 MiB 时六百来页的改名永远取不到。逐页取之后平台不需要给这个上限。
  - 默认 8 MiB 留得住约 80 MB 被改写的正文的提取结果；先到的是请求的期限（P4 文档第 12 节）。
- 总体设计 4.3、13.1 第 19 条与 13.3 第 3 条随之修订（P2）。

**阅读视图的一致性**

- `markdown.Page` 加 `Revision`（page 的 `PageRef` 同样），`Fetch` 知道这次渲染的是哪个版本。
- `Fetch` 在一条语句里读出 `indexed_pages` 与这一页的链接行。
- 索引的 `revision` 与 `extractor` 都与这次渲染相同时，按字节位置取状态；不同时（读正文与读索引之间有写，或提取规则改过），按当前的树即时解析。
- 在索引里找不到范围的链接逐条即时解析。
- 即时解析不在事务里：几条语句各读一个快照，其间的移动可能让这一次的答案过时，下一次重读更正；其间删掉的页不算错误（P3 B）。
- 历史版本（M8）同样即时解析（总体设计 4.3）。

### 4.8 链接状态的事件 `links`

**服务端**

- 照 [M5 的事件移交](handoffs/M5-events.md)第 1–3 项注册：
  - 按笔记本过滤；
  - 载荷 `{pages, targets}`，都是页 id 的数组，多于 20 页时为 `null`（照 `pages` 的退化）；
  - 在观察者里、调用方的事务中发布。
- 这个类型按笔记本过滤，不是工作区级的，所以移交第 4 项（不发 `access` 的路径）与它无关。

**前端**

- `eventHandlers` 加 `links`：
  - 重读 `pages` 里各页的阅读视图与属性，以及 `targets` 里各页的反链；
  - `null` 时重读这个笔记本里挂着的全部阅读视图、属性与反链。
  - P3 B 先只重读阅读视图（列出的各页一律重读，不比版本）；属性与反链随 P5–P7 加上。
- `pages` 的处理同时重读写了正文的页的属性，以及这个笔记本的标签与标签页。这是改 M5 的处理（12.1 第 6 条的例外）。
- 事件只为读过的页请求重读（缓存里有它的键）：refresher 为每个请求过的键留一项，点名笔记本里所有页的事件不能让它一直长（[P7 文档](07-P7-editor-panel.md)第 11 节）。
- 补全的数据不经事件：每个 `[[` 或 `#` 读一次（P7 文档第 3 节）。
- 连上时的整体刷新（`refreshedOnConnect`）把属性、反链加进阅读视图那一层，标签加进树那一层。

### 4.9 渲染：地址由前端给

**链接的标记**

- 链接节点渲染为 `<a>`（[P3 文档](03-P3-index.md) 6.2）：
  - 解析到的带 `data-nw-node`（节点 id）；锚点带 `data-nw-anchor`，是锚点的最后一段按标题 id 的同一个函数算出的 `nw-` id（去重的后缀算不出，指向同名标题里的第一个；块引用 `^b` 不带）；
  - 解析不到的带 `class="nw-unresolved"`、`data-nw-target`；
  - Markdown 链接与图片的链接若指向笔记本里的路径（根路径也是），同样按是否解析到带 `data-nw-node` 或 `nw-unresolved`，不写地址；
  - 嵌入照链接渲染，另带 `nw-embed`；解析不到的嵌入只说明不存在，不提供新建；
  - 只有锚点的 `[[#h]]` 写同一页的 `href="#nw-h"`，Markdown 的 `[t](#h)` 同样（百分号解码之后经同一个函数，P6 A）；块引用 `^b` 与空的锚点只写文字；链接文字里的 wikilink 与标签是没有状态的 `<span>`：一个链接里没有链接，用户写的 `<a>` 围着渲染成链接的节点时也丢掉；
  - 计数的标签是 `<a class="nw-tag" data-nw-tag="名">`，`名` 是这一页的写法（去掉末尾一个 `/`），`getTag` 在服务端算键；不计数的标签与标签 `/`（`getTag` 的路径叫不到）是 `<span>`（P6 A）；
  - 属性表里指向页的属性链接同样渲染为链接，文字是链接显示的文字，经核心属性表的钩子 `Properties`（第 4.2 节、第 8 节）。表按每个字符串值在文档里的次序对齐，不按路径，`{"a.b": …, a: {b: …}}` 的歧义在表里不存在（P6 A）。

**地址与跳转**

- `href` 由前端的增强设置：服务端不知道工作区的 slug（`markdown.Page` 只有笔记本与页面），而阅读视图的 HTML 只给前端用。
  - 增强按 `ReadingContext` 的工作区、笔记本写出应用内的地址，点击经路由跳转；
  - 修饰键与中键照浏览器的默认行为，地址是真的；
  - 普通 Markdown 的本站完整地址同样经路由跳转（[M4/P3 移交](handoffs/M4-P3-markdown-extensions.md)第 11 项，P6）；解析不到的笔记本内路径不当作本站链接。
- 解析不到的链接由增强给 `role="button"`、`tabindex="0"` 与 `aria-haspopup="dialog"`，键盘可以聚焦与触发（Enter 按下时，空格在同一条链接上抬起时；P6）：
  - 能写的人：问"新建页面「x」？"，点击时由服务端用同一个解析器算出落点（第 11 节第 2 项），确认之后在那里新建并打开；没有落点的（目标不合法、不是合法标题、路径的父页不存在、太深、新建之后也解析不到），说明页面不存在。落点不写进 HTML：它变了不改任何解析、不发事件，写进去会过时（P3 B）。落点的接口 `getLinkLanding` 只给写者（`link_landing.read`，读者 403），规则见 [P6 文档](06-P6-reading-view.md)第 2 节；
  - 只能读的人：说明页面不存在。

**P1 到 P3 之间**

- P1 还没有 `Fetch`：wikilink、嵌入与标签渲染为不带状态的 `<span>`（`nw-wikilink`、`nw-tag`），显示文字，不是链接。
- P3 有了 `Fetch` 之后改为 `<a>`，同一个 Phase 带上设 `href` 与经路由跳转的最小增强、定位到锚点，以及 `links` 事件只重读阅读视图的处理。

**KaTeX、mermaid**

- 数学公式的占位元素由增强用 KaTeX 渲染，`mermaid` 代码块由增强用 mermaid 渲染。两者都是单独的 chunk，用到时才加载。
- 二者往阅读视图里写库生成的标记，是总体设计 13.2 第 23 条"增强不加未经检查的标记"的例外，信任边界写进那一条：
  - KaTeX 以 `trust: false` 渲染，设 `maxSize`、`maxExpand`；
  - mermaid 用 `securityLevel: 'strict'`，设 `maxTextSize`、`maxEdges`；
  - 超出或出错时显示原文。
- 这些上限不够（P6 B 的审查与修复核对，[P6 文档](06-P6-reading-view.md)第 10 节）。几十个字节的公式就能让读者的标签页卡住几十秒或崩溃，所以另有：
  - 定义宏的公式不排（`maxExpand` 只数展开的次数）；
  - KaTeX 打补丁，限住 `alignedat` 的列数；
  - 排出的元素至多嵌套 150 层（Chromium 的布局约 800 层崩溃，远在这之前布局已要几秒）；
  - 每个任务排 50 毫秒，连布局一起算；每个公式在流外单独布局，视图的公式布局至多 1 秒（缩放、打印时它们一起重新布局），之后的显示原文；
  - 重读时视图排过的公式立即放回，高度不变：工作区的侧栏不作窗口的滚动锚点之后，锚点在页面里，重读前后高度一变就会把读者看的移开；
  - mindmap 至多 150 行（它的布局比节点增长得快；行按 JavaScript 的行尾数）；
  - mermaid 标签里的公式经同一道拦截与选项（`guardLabels`），标签的 HTML 不留 `id`、`data-*`。
- mermaid 只能在主线程渲染：图在可见时才渲染，各视图一共同时一张。换主题时图在原来的包装里重画（`ReadingContext.onThemeChange`），视图不重新增强。
- CSP 现在的 `style-src 'self' 'unsafe-inline'` 与 `font-src 'self' data:` 已经容纳它们：P6 在生产的 CSP 下实测，不放宽 `script-src`，CSP 不改，结果写进总体设计 4.6。

**宽的内容**

- 表格、块公式与属性表由渲染器包一层 `<div class="nw-scroll">`（P6 A），横向滚动从整个阅读视图移到这一层（P6 B）。没有自己一层的宽内容（用户自写 HTML 的表格、行内很长的公式）仍在文章里横向滚动；文章溢出时可以聚焦，并裁掉公式画到外面的部分（P6 B）。
- mermaid 图由增强包同样的一层。
- 服务端不写 `tabindex`：不知道是否溢出。溢出时由前端的增强给 `tabindex`、`role` 与可访问的名称，可聚焦的代码块一起补（M4 收尾的修复核对 MN-3；P6 B）。

### 4.10 `nervewiki reindex`

**命令**

- 子命令照 `workspaces` 的样板，经 `bootstrap` 组合，不起 HTTP 与后台任务。
- 可选 `--notebook <id>`；不带时逐个笔记本处理。

**做法**

- 每个笔记本一个事务，持笔记本行的 `FOR NO KEY UPDATE`（与改名同级，正文写在此期间等待）。
  1. 按当前的 Unicode 数据重算节点的标题键（总体设计 3.5）。同一父节点下有两个节点撞键时，报告这些节点，这个笔记本不做，命令以退出码 1 结束。
  2. 删掉这个笔记本的索引行，逐页取预算、解析、写索引（只插入）。
  3. 解析全部链接。
- 每个笔记本完成之后发一条 `links`（`pages: null`、`targets: null`），开着的阅读视图随之重读（13.1 第 30 条：命令行的写照常发布）。
- 撞键的笔记本，以及别的原因重建失败的笔记本，原样保留，在标准错误上连同原因列出，其余照常，命令最后以退出码 1 结束（P3 审查：此前第一个失败就停下）。
- README 写明：在没人写的时候、最好在 `migrate up` 之后启动服务之前执行；reindex 期间这个笔记本的写在等待，一万页的笔记本约十秒，等不到的保存答 500。

**什么时候运行**

升级到 M6 之前已有的页面没有索引。开发库与负责人冒烟用的库在升级之后运行一次（写进 README 的开发一节）。v0.1 还没发布，没有要迁移的生产数据。

### 4.11 接口

见第 5 节。

**反链**

- 一项是一个出发页：`{id, count, contexts}`；不算这一页自己的链接，有歧义、解析到它的算。
- 按出发页的 id 分页（游标是 id，13.1 第 27 条、13.2 第 19 条）；出发页在索引上一步一个地找，不读它们的链接。
- `count` 是这一页里指向它的链接数，至多数到 1000（一千或更多）。
- 名称由前端取自已加载的树。
- 上下文：按位置取前 10 条链接，同一行只留一处，是链接所在的那一行；长于 240 字节的行取含链接起点的至多 240 字节（在 UTF-8 字符的边界上，从链接之前约 80 字节起），截掉的一端加 `…`。
- 没有上下文的出发页：两次读之间写过或删了、索引的提取版本不是当前的、这次请求已读过 32 MiB 的内容（[P5 文档](05-P5-api.md)第 3 节）。

**补全的数据** `GET …/link-targets`：

- 每个节点给出它的标题、种类、别名（前 1000 个），以及 `link`；
- `link` 是 P4 写法（[P4 文档](04-P4-rewrite.md) 3.1）的三种里第一个从笔记本任何地方都只解析到它的：名称唯一时的名称、完整路径、完整路径加 `.md`。总是存在；不试路径的后缀，所以不总是最短；
- 它与改写用同一个函数（`domain.Linktext`），前端不重算标题键（JavaScript 没有完整的大小写折叠）。

**属性**

`getPageProperties` 给出每个属性的值，以及属性链接的解析结果（属性路径到节点 id），右栏据此显示可以点击的链接。`key` 是属性的完整路径（列表的项是 `sources.0`），解析不到的也给出，`node_id` 为 `null`。

### 4.12 右栏

- 页面的外壳在宽屏上加一栏 `<aside>`，窄屏时排在正文之下，各节可以折叠。
- **大纲**：阅读视图的标题（`h1`–`h6` 的 `nw-` id），至多列 1,000 个，点击滚动到那里。编辑时隐藏：编辑器里的标题要另做解析，v0.1 不做（给 M12 的打磨）。
- **反链**：链接到这一页的页面，每页给出链接所在的那一行作上下文，分页；重读读已读的页数（P7 文档第 9 节）。
- **属性**：这一页的 frontmatter 属性（索引里的值），属性链接可以点击。
  - 阅读视图顶部 M4 的属性表照旧；
  - 右栏在编辑时也显示，那时正文里的 frontmatter 是原始的 YAML。

### 4.13 编辑器的补全

**扩展点的契约要改**

- 现在的编辑器扩展（`editor/registry.ts`）同步返回 CodeMirror 的扩展，注册表与它登记的模块由 `main.tsx` 静态导入，只许引用 CodeMirror 的类型。
  - M5 的三个扩展都只经 `controls` 做事，所以不受影响；
  - 补全却要构造运行时的对象（`autocompletion`、`syntaxTree`）。一导入，`@codemirror/*` 就进了主 chunk，构建检查让构建失败（`build/editor-out-of-main.ts`，P6 B 起是 `build/out-of-main.ts`，编辑器、KaTeX、mermaid 一起查）。
- 所以 `EditorExtension` 可以带 `load: () => import("…")`：
  - 它指向的模块在编辑器的 chunk 里，可以导入 CodeMirror 的运行时值；
  - 编辑器在创建视图之前等这些模块载入，再组合；
  - 这是改 M4 扩展点的契约（12.1 第 6 条的例外）。
- 加一个经组合根、构建检查仍通过的测试。

**补全**

- 编辑器扩展 `linkCompletion`，经组合根的 `editorExtensions` 登记（12.4"编辑器扩展管线"）。
  - `@codemirror/autocomplete` 改为直接依赖，只在编辑器的 chunk 里。
- `[[` 之后补全页面（标题与 `link`）与别名：
  - 选页面插入 `[[link]]`；
  - 选别名插入 `[[link|别名]]`，与 Obsidian 相同。
- `#` 之后补全标签，规则与标签的识别一致（样例集规则 9），在代码里不弹出（lezer 判断）。
- 原始 HTML、链接的地址、转义的 `[[` 里不弹出；frontmatter 里只有引号之后的 `[[`；表格里别名的分隔写 `\|`（P7 文档第 4、5 节）。
- `EditorContext` 加笔记本的补全数据（[M4/P6 编辑器移交](../M5-collab-editing/handoffs/M4-P6-editor.md)第 5 项）。

**输入法**

- 组合进行中不弹出、不接受补全（CodeMirror 组合中不把按键交给键位，不另写键位：P7 文档第 6 节）。
- 输入法清单加第 16–18 步：中文标题的 `[[` 补全、中文标签的 `#` 补全、组合中按回车不误选。

- 核心属性表的钩子 `Extension.Properties`（P6 A）：写表时按文档的次序把每个字符串值交给扩展，扩展答属性与文字，或不管；`markdown.Scalar` 带不导出的序号；
- `markdown.Linker` 改为按节点问的 `RendersLink() bool`（P6 A）：渲染成 `<span>` 的节点不让净化丢掉用户围着它的 `<a>`；
- `WriteAttrs` 写进 `markdown.Writer`（渲染器的缓冲与属性表的缓冲都是）；`AnchorID`、`DecodeURI` 从 obsidian 移进核心，核心另加 `ShownText`（链接与图片显示的文字），`PlainText` 导出（P6 A）。

## 9. 测试策略

- **样例集是规范**（13.3 第 2 条）：
  - `cases/` 的提取与渲染、`resolve/` 的解析、`rename/` 的改写，各有一个读样例的 Go 测试；
  - 样例与 Obsidian 的核对用 `verify.mjs`（提取）、`verify-resolve.mjs`（解析）、`verify-rename.mjs`（改写）。它在独立的数据目录启动 Obsidian，不碰本机已有的库。
- **成本**：新语法的病态输入，全部经应用实例的 `CheckCosts`：
  - 不闭合的 `[[`、`==`、`$`、`%%`；
  - 深层嵌套的 callout；
  - 很多的标签与嵌入；
  - 每行一个 `$` 的长段落。
- **模糊测试**：
  - `FuzzParse`、`FuzzRender` 加带扩展的实例；
  - 改写的随机测试（4,000 个固定的种子）：随机的多层、带重名的树，随机的改名与移动；不变量是第 3 节第 4 条。`FuzzParse`、`FuzzRender` 是真正的模糊测试。
- **性质测试**：随机的操作序列之后，增量维护的索引等于从头重建的结果（第 3 节第 3 条）。它不靠"候选选全了"的推理，专门抓候选的遗漏。
- **交错**（13.1 第 18 条的做法）：
  - 场景：改名与正文写；改名与心跳（会话在需要改写的页上）；两次改名；两次正文写（别名与链接）；删除与正文写（链接指向被删的页）；
  - 每个交错结束时核对索引的不变式 `checkLinks`：索引的 revision 与正文一致，`resolved_id` 不指向已删的节点（"索引等于重建的结果"由性质测试 `TestTheIndexIsItsRebuild` 核对，`checkLinks` 不重建）。
- **最后一跳**（13.1 第 21 条）：
  - 索引、改写、事件、扩展、补全、事件处理各有一个经组合根的测试；
  - 组合根交空时失败。
- **e2e**（L 系列）：
  - L1：wikilink 跳转，解析不到的显示为未建；改名之后链接仍然跳到那一页；
  - L2：写者点未建的页，确认之后新建；读者只看到说明；
  - L3：改名时引用它的页被别人编辑，改名被拒，并说明是谁在编辑哪一页；
  - L4：标签跳到标签页；数学公式与 mermaid 渲染出来；
  - L5：`[[` 与 `#` 补全；
  - L6：右栏的大纲、反链、属性；另一个会话（接口）加了链接，反链实时出现。
  - **对等验收**（收尾修订，[M6 收尾审查](reviews/M6-closeout-review.md) C-I6）：L1–L6 各有接口版本，两个版本调用 `e2e/fixtures/assert/links.ts` 断言索引（页按当前版本索引、它的链接与指向、标签、别名）。例外（总体设计 10.1）：只在浏览器里发生的只有页面版本：L1 的应用内跳转与焦点，L2 的对话框与键盘，L4 的 KaTeX 排版、mermaid 画图与它们的上限，L5 的补全列表、按键与输入法，L6 的大纲、焦点与右栏的布局，以及 L4、L6 的大页故事。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 解析规则与 Obsidian 不一致，导入的笔记链接解析不到 | P3 的 `resolve/` 样例与 Obsidian 核对（次序、路径后缀、相对路径、Markdown 链接的路径）；有意的差异写明理由 |
| 改写一个被很多页引用的页面很慢：同一事务里逐页解析，持笔记本的锁 | 逐页不排队地取预算（`TakeNow`，收尾修订：设计时写的是一次取够），取不到立即 503；逐页只保留提取结果；P4 测量一次改写 500 页的耗时与内存，写进 Phase 文档；超出时考虑分批（v0.1 不做） |
| 改名被锁挡住的频率 | 负责人已接受（第 11 节第 1 项）。409 列出全部编辑者，管理员可以强制解锁，闲置 30 分钟也会释放 |
| 候选漏了某种情形，索引悄悄过时，或改名之后链接指向别处 | 性质测试"增量等于重建"；改写的随机测试以"原来解析到的都不变"为不变量 |
| KaTeX、mermaid 卡住正文或带来不安全的标记 | 单独的 chunk 按需加载；设大小与复杂度的上限，超出显示原文；mermaid 可见时才渲染；P6 在 CSP 下实测 |
| Unicode 数据升级改变标题键 | `nervewiki reindex` 先重算标题键，撞键时报告并停下 |
| 同一笔记本的正文写在 linking 的锁上串行 | 锁只持到提交；P3 测量自动保存的延迟；给 M12 的性能移交 |

- 本人的锁同样挡住改写（第 4.6 节第 4 项）。
- 被改名、移动的那一页自己的正文需要改写时，它正被编辑同样答 409（指向自己的链接，移动时它的相对链接）；不需要改写时照常。这是第 1 项决定在这种情形下的读法。
- 改名、移动时"被抢走"的链接也改写，保住原来的指向；新建、删除只重新解析，不改写别的页面（第 4.4、4.6 节）。
