## 主持者的决定

负责人可以改判（[00 号文档](../00-M9-design.md)第 11 节记为第 56–66 条）：

1. **上下相套的回收站项照旧拒绝**（实施的偏离 1、未决项 1；审查 A）：一个变更集的两个回收站项上下相套时，M8 的 L 把它们读成一组（`readReverted.topOf` 沿删除之前的父节点、只要也被这个变更集删除就一直往上找顶），外面那一项只有它自己的成员，撤销答 409 `page.revert_conflict`（`changed`），什么都不写。审查 A 核对过没有一个接口做得出这种形状：batch（它的规范化、B3）、REST 的删除、撤销与撤销的撤销、回收站的恢复、导入、编辑会话、后台任务与 M8 的数据。设计 3.21.2 的那一行改为这个拒绝（以 SQL 种下的变更集）；domain 的构造的测试（`TestARestoreWaitsForTheGroupItGoesUnder`）留着。M8 的 L 不改。
2. **(T1) 的判断留着，构造的测试是它的反向对照**（偏离 8、未决项 2）："临时改名两次"在合法的状态里到不了；3.17 的"名称取计划开始时的"同样（审查 C-N5）：只有防御的第 3 条后备够得着它们。各有一个构造的测试（`TestAFallbackRenamesANodeAsideOnce`；`TestTheThirdFallbackMovesAPlaceOffTheRoot`）。第 2 条后备也只取待放回的节点（审查 A-N2，`TestTheSecondFallbackMovesOnlyANodeToPlace`），先取 id 最小的（审查 C-N1）。
3. **一页的两份正文在最小的预算下解析**（审查 B-M1，修复一轮；修复核对 B 的 N1、N2，修复二轮）：在 `MinParseBudgetBytes`（5 MiB）下，撤销一页被 batch 写过、再删除的页（两份正文都近 5 MiB）每次重试都答 503：第二次取放不下第一份留着的份额。`decidedAll`（`DecidedAll` 与 `DecidedContents` 共用）现在在一次取放不下本次调用留着的份额（在预算的大小之内）时先还掉它们，事实留着、不再计入，同 S1 的 `ParseSession`。别人的份额挡着时照旧等、答 `server_busy`。M8 的撤销、回收站的恢复与任务的批碰不到这个条件（最小的预算下至多约 4.45 MiB；审查 A、B 核对过）。页模块的端口加 `ParseBudget.Takes` 与 `BudgetHold.Held`，用 S1 的平台的部件。3.18.4 随之改。
4. **空的主干照页的名称**（审查 A-N1，修复一轮）：`numbered` 里 UTF-8 的截断留不下主干的一个字符时（附件的扩展名很长），名称照页的名称编号，同 3.17 说的。这也改了 M7 的 `Numbered`：M7 的导入经 `CheckTitle` 去掉编号的名称首尾的空白，从来没有以空格开头的名称存下：存下的名称一个也不改，只有很少见的新名称造法不同。
