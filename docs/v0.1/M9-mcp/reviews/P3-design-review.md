**3.7.1：为什么不用合并的改动、不只比去向，与原型**

为什么不用合并的改动：`A → B → A` 合并成 `A → A`，`Relocation` 什么都不搬（`linking/domain/change.go:32-37`、`:68-80`），参与者在 `rewrite.go:49` 就返回；而"先把 A 改名 B、再改 P 写下 `[[B]]`、再把 B 改名回 A"在分开调用时第三次会把 P 的 `[[B]]` 改回 `[[A]]`（审查 A-I3）。从这一页最后一个正文操作算起，它看到的改动是 `B → A`，就照分开调用改写。为什么不只比"那一项时去向"与"最后的树上的去向"（审查 A-I3 的第一种做法）：那样会改写这一页里在那之后被新建、删除或别名改了去向的链接，即便之后没有改名或移动（"写 W 带 `[[X]]`（那时只有 F/X）、再在根下写 X"，分开调用时新的 X 拿走 `[[X]]`，只比去向会把它写回 `[[F/X]]`），还要另立一条 `update_links` 的规则；以这一页自己的改动走今天的 `Relocation`、`Affected` 与 `spread`，碰不碰得到、`update_links` 与 `Recased` 都是今天的规则。在 `f1733403` 的 linking 上以原型核对过（`scratchpad/m9/p3/exp/`，`zz_p3_test.go`：每种情形一本 batch、一本分开调用，同一组内存里的假的端口）：审查 A 的三个改名再改回的情形、新建之后拿走链接的情形、新建再移动而抢走链接的情形（写了的与没写的页各一个），与分开调用写出的字节相同；31 个情形里不同的只有五个（前面的新建、删除改了去向之后再改名，各一个；一个节点先以真、再以假改名；batch 前面加上或去掉的别名，各一个）。（第一轮复核更正：原说它们"都是 4.11 的规则写明的"，照第一轮的写法对写了的页不对；那时原型的每页的改动带着被移动的节点之下的节点，设计没有，A2-I1、A2-M1。）
