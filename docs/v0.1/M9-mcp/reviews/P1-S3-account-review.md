## 主持者的决定

负责人可以改判：

1. **说明的缓存存副本**（A-I1）：缓存 `strings.Clone` 之后的正文，"每项至多 32 KiB、256 项至多 8 MiB"由此成立；S1–S3 别的长存的值都审过，名称的 LRU 同样复制；堆的测试照 A 的方法。
2. **名称照 B 的方向**（B-M1、B-M2、C-M2）：说出的名称（清理之后不空）总是为它的 PAT 缓存，标"还不知道在行里"；标没设时之后的调用再记下；写了一行，或读到行里就是它，去掉标；热行的规则保住（已知在行里的同一个名称不写也不读）。要的是：说过名称的会话从不记成更早的名称；不报名称的调用用缓存着的说出的名称，从不用过时的记下的名称。
3. **"最后一个换行"的截法不改**（A 的存疑 1）：进 M12 的打磨移交，带 A 的数。
4. **`nervewiki reindex`**（A 的存疑 2）：查过，它在一个事务里改键，握手看不到中间的键，M12 没有要做的。
5. **只由看不见的字符组成的名称照 shared 现有的名称规则**（B-N2）：进 M12 的打磨移交，与 shared 的规则一起，现在不改。
6. **组合根两份的界线不再动**（C-N4）：S3 已移一次（`^Test([A-D]|E([a-u]|very[A-R]))`，S2 的决定 7）；01-P1 6.1 的规则改为取每份单独跑两次的平均。
7. **MC1 加最后改动与附件的计数，不加非管理员的角色**（C-N2）：角色由 Go 的矩阵与"列表等于逐项读取"逐列核对。
8. **镜像的交错只改设计的那一句**（修复核对第一轮 B 的 N-1）：两个客户端在同一刻用一个 PAT 报不同的名称时，进程与行可以停在不同的名称上，直到报出缓存之外的名称（例如行里的那个再报）、这一项被挤出或进程重启；不加按令牌的锁。
9. **客户端在名称的语句里走了记 warn**（B 带过来的存疑）：进 M12 的打磨移交，现在不改。
10. **组合根的任务的等待与竞态那一份的 CI 时限**（修复核对第一轮 C）：`endedJob`、`awaitImports`、`awaitExports`、`awaitBackground`、`endedBackground` 与竞态那一份的时限在主持者另开的只改测试的分支 `m9-job-waits` 里改，不进 S3（合并 `0c934bb9`：`jobWait` = 60 秒，竞态那一份的时限 20 分钟）。

## 接受与推后的

- **接受**：
  - 镜像的交错里两个客户端的名称在竞态之后仍可不同（主持者的决定 8）；几个进程共用一个数据库时各自的 LRU 不作废（v0.1 是一个进程）。
  - 标没设时每次调用至多一次记下与一次读：行一直被持着时 1,000 个同时的调用是 1,001 次记下与 1,001 次读，行空出来之后一次写、之后什么也没有（修复核对第一轮 B）。生产里行只在一条语句（`last_used_at` 的写、撤销）或短的凭证事务里被持着。
  - 等价的变异：C5（缓存的键不带笔记本：节点 id 全局唯一）。
  - `errNoNotebookFits` 由名称的界线到不了，留作防御的内部错误；两个同形的 LRU（`mcpserver.tokenLRU` 与 `page/app` 的说明的缓存）在架构里没有共同的家（平台不能导入 `shared`，app 不能导入平台）；`open_notebook.go` 的 `kindOf` 与 `list.go` 的 `"attachment"` 两处说同一个映射，琐碎（C）。
  - `FirstChildren` 读根下的全部节点再取前 101 个（没有 `sort_order` 的索引）：一个根下 10 万个节点时 10–18 ms，对读树的 66 ms（B），不在守卫里。
  - 流程（照实写下）：
    - B 一次在 `heavy.sh` 之外跑了 `go test -count=1 ./internal/modules/page/...`（变异之前一次多余的探查），其中的 `page/adapter/postgres` 不带共用的锁起了一个 testcontainers 的 PostgreSQL，跑完由 reaper 删掉；C 开头直接跑了 `notebook`、`identity`、`workspace` 的 `go test`（各起 testcontainers 约 7 秒，Ryuk 收掉，没碰别的容器与进程）。两人都在报告里写明，之后的 Docker 运行都经 `heavy.sh`。
    - 别人留下的 14 个空转的 `python -I -c "while True: pass"`（孤儿进程，2026-10-18 03:01–03:16 约 15 分钟，占 18 个核）让组合根两份的一次运行作废（469 与 343 秒），并让其中已有的 `TestABackgroundRestoreLeavesASearchItsHits` 失败一次（"the job … is still running"）；那次丢掉，它在别的运行里都通过；没人动那些进程。
    - 修复一轮第一次 `make test-go` 在 M8 的 `TestABackgroundRevertOfAnImportThroughServe` 上失败（`endedJob` 等 1,501 页的导入 15 秒，负载 8.9，Docker 的虚拟机 225% CPU、另一个构建在链接），单独在竞态下 10.99 秒通过，整个重跑通过；这一轮不碰导入与任务（主持者的决定 10）。
    - 实施者的计划变异的命令把输出重定向进文件，变异的帮助脚本报 FAILED(unnamed)：实施者的 `mutlogs/` 留着每个计划变异的失败行，C 的副本打到控制台、以点名的测试失败。
    - CI 由实施者以 curl 每两分钟读一次。
- **推后**：
  - [M12 的打磨移交](../../M12-release/handoffs/M5-polish.md)第 30 条：截在最后一个换行可能远低于 32 KiB（A 的数）；只由看不见的字符组成的名称，与 shared 的名称规则一起；客户端在名称的语句里走了记 warn（主持者的决定 3、5、9）。
  - [M12 的性能移交](../../M12-release/handoffs/M4-performance.md)第 18 项：`open_notebook` 的计数读这本笔记本的全部活的节点、最后改动读它的全部变更集（概况的守卫：10 万个节点、10 万个变更集上本机的中位数是树 51–100 ms、计数 6–10 ms、最后改动 4–8 ms，约低 9 倍）；`FirstChildren` 读根下的全部节点；`notebooks` 逐个工作区一条语句。
  - 组合根的任务的等待与竞态那一份的 CI 时限：在 S3 之外的只改测试的分支 `m9-job-waits` 里改，S3 合并之后合并（`0c934bb9`，主持者的决定 10）。
  - 组合根两份在 P2 再量：CI 上第二份的 go test 一步到过 7:54（`go test` 的 15 分钟的约 53%），P2 的写的矩阵多半落在第二份。
