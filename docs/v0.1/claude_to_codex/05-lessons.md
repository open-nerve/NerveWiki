# 经验教训（M0–M10）

每一条都出过真问题，出处在各 Phase 的审查记录里。按主题排。

## 1. 测试能不能失败

- **每个新的断言都要证明它会失败。** 写一个变异去跑它。见过的失败方式：
  - 一个假的排版器写的是文本节点，`> :first-child` 从来匹配不到；
  - 比较两个空集合；
  - 夹具的 Markdown 没有扩展，任何正文都解析成同样的事实（M10/P1/S1 的 A-M3）。
- **先在没改过的树上跑一遍变异的命令。** 有一次一个测试从第一次就失败，十个变异都是对着它量的。
- **"等价的变异"要在审查者的语料上核对。** 有一个只有在另一处修好之后才不等价。先用一个对照变异（例如让那一块恒为空）证明这些格看得见差别，"没抓到"才算等价的证据（M11/P2/S3 的 B-I1）。
  - **等价要写出依据：实现这个接口的只有谁，造出这种值的只有谁。** "认标记时只看类型、不看方法的值"活下来，依据是仓库里实现 `TxCommitFailed() bool` 的只有 `commitError` 与测试的替身、都答 `true`；"去掉任务那一种凭证"活下来，依据是 HTTP 的认证只造会话与 PAT 的 actor。逐个列出实现者或调用者，并写明多一个什么（答 `false` 的实现、经得到事件流的任务）就不再等价（M12/P3/S1 修复第 1 轮的 b-m1-mark、c-m1-job）。
- **性质测试的下限**要数"变异会显出来的那种情形"出现的次数，不是"规则触发了"的次数；生成器要真的到得了它要的形状；换几组种子再信它。
  - **生成器偶尔造出的形状不算测到。** 后台撤销的性质测试里，"单独删的项套在另一个单独删的项下"每 2,000 次 0–6 次、没有计数，`-short` 常常一次也没有：让这些项同一时刻的变异（分时刻的装载要挡的正是它）在 `-short` 上活下来。要靠的形状，造它的那一支要稳定地造，并给它一个计数与下限（M12/P3/S2 的 P3S2B-M1，决定 480）。
  - **生成器的随机数用法一变，下限照约定全部重算。** 多抽一次签、多建一个节点（id 也取随机数）都挪动之后所有的抽签，每个计数都变：只降几个，"最少次数的三分之二"就不再成立，有的还该升（M12/P3/S2 修复第 1 轮：降 9、升 18，决定 479）。"照样抽签"的变异也挪动了 id 的随机数，别的计数照样小变。
  - **别的种子基也会找出测试自己的毛病。** 回滚的性质测试里的 agent 边走边删，往上的路经过已删的节点就读不到，56,000 次里 15 次留下真库没有的孤儿；测试自己的 2,000 个种子一个也没有（M12/P3/S2，量下限时找到）。
- **一个反例只钉住一种形状。** 模板的段落对应一开始只有"块数"的反例，标题级别、列表项数、围栏、段落行数各要一个（M10/P1/S1 的 A-M1）。
- **投影的测试：夹具里每个标量互不相同，整个答复与写死的期望比。** 夹具里两个成员同值、或只断言几个成员，把一个成员写成另一个（或写成常量）的投影照过；按成员点名、按成员补，一轮轮核对总找到下一处（M11/P2/S2 的 C-M4、M5、M6）。按投影收尾：布尔排成几行、每一列互不相同，`count_capped` 之类有真有假、与值无关，再以对调与常量的变异核对。投影之外，跨模块的逐字段转换（组合根）同样要有一格让每个成员取不同的值：两边的单元各自钉住，中间这一跳整个程序的格里成员同值，写错照过（M7）。
- **整个程序的测试要走到最后一跳**：把组合根交的注册者换成空，测试必须失败。
- **错的结局是一条开着的流时，先看状态、读一帧就判。** 事件流处理器的 429 一格在答 200 时 `io.ReadAll` 那条流：变异让它答 200，整个包挂到 10 分钟的超时，变异表跑不下去（M12/P3/S1 的 S1-12、x7）。
- **自检的样例证明的是检查的函数，证明不了遍历真的读到了文件。** e2e 的门禁把内置样例直接交给 `check()`，遍历只读 `e2e/stories`、或根算错一个文件也没读到时，样例照绿、门禁照过，只有手做的探针抓得到；要另断言读到了一个已知的文件（帮手的模块），并对遍历本身做变异（M12/P1/S1 的 `e3059737`，审查 C 的门禁变异）。
- **日志检查只读自己子测试开始之后的行。**
- **测试准备不能超过 4 秒的请求期限**（CI 的竞态检测下约慢 1.7–2 倍）；大的种子用 SQL，或用生产的期限。
- **计时守卫的界高于请求期限时，判它的是期限。** M10 来源的恢复与撤销的界是 7.6 秒，测试配置的请求期限 4 秒在它之下：7763 上撤销一直只比期限少 3–18%，碰上一台慢的 runner 就在 4 秒答 500，测不到用时。只提高期限还不够：测试的 `client()` 5 秒就放弃，期限提到 15 秒之后，它会先于界来判。界高于测试配置的期限时，只给这个用例提高期限（M10 决定 150、160，M12 决定 359），并断言界低于期限、客户端等得比期限久。期限要由界推出，再与起应用的配置对证，不要拿配置去验它自己：自指的断言让"别的形状仍是 4 秒"没有钉子（M12 旁支 `m12-p1-source-revert-deadline`，审查 B 的 M1）。
  - **传进帮手的界，要有一格证明它真被读到。** M10 的单个 REST 改名把 11 s 传进 `ingestAdditionalRewriteCost`，帮手只在 batch 一支读日志的 `unit_ms`；REST 改名不记单元，自 `6d1549fc` 起这一格从没断言过它，判它的一直是 4 s 的期限，一台慢了 2–3 倍的 9V45 就在 4 s 答 500。便宜的反向对照：把传进去的界改成必然过界的值（例如 1 ms），每个传了它的格都要红；沿代码走，在 `5154e0de` 上这一格会照绿（没有跑；M12 旁支 `m12-ingest-request-deadline`，审查 B 的 IDB-M1、C 第 4 节，决定 580）。
  - **修了一格，查同一个帮手、同一个 Makefile 目标里的同类，把清单写进记录。** 决定 359 的旁支只查了来源的守卫；这一格当时（`ad0bf40c`）就在同一份 guards-sources 里，4 s 对 11 s，三天后在 `main` 上红了（同上，决定 583）。
- **限时的测试**：不要库的、按时间判的测试在 `-short` 下跳过，在 `test-go-costs` 或 `test-go-guards` 里有它自己的一行（带 `-v`）。界线取本机的三倍，并对照 CI 在竞态下的时间。
- **按比值判的计时守卫，一阵争抢会让它偶发地红：过界时在同一个测试里再量一次，两次都过界才红，界不放宽，失败的信息带两次的读数。** 编辑器解析的守卫轮流量"没有扫描"与"有扫描"各七次、各取最快，以为机器的快慢两边一起受；一阵约 2 倍的争抢恰好从第一个"有扫描"的样本起、持续到这一格结束，"没有扫描"那一边只有第一次干净，比值约 2，一次就红。负载下 134 次里两次到了界的 0.96、0.97（M12/P4/S5 审查 B 的 M2）。不用测试框架的重试：它在第二次过了时丢掉第一次的读数，两次都失败时只报最后一次，也重跑了整个测试。再量之前核对两次之间没有让第二次偏快的共享状态（强制每格都量两次，第二次的比值与第一次相同），并确认撤了修复的变异两次都过界。
- **偶发的测试，等得更久治不好：先看失败时缺的是哪一种结局。** `TestTheMCPCallStopsWhenTheClientGoes` 的两个等待从 2 秒推到 10 秒照样失败，10 秒里一行也没等到：客户端走的那一刻，SDK 可能先把答复写进已断的连接，"答复没写出"那一行就不会来；平台两种结局都对，测试只认其中一种，负载越重越常失败（M11/P2/S2 的 C-M1；M9/P1 在单元里已照两种结局改过）。
- **设计写"之后可以做 X"，就要有一个测试真去做 X。** 升级的回滚的变更集，设计写"之后可以在网页上撤销"，从没有测试撤销过；收尾的探针一撤销，最常见的形状（新建的文件夹收着原有页又收着新页）就答 `page.revert_conflict`（M11 收尾的 A-M1，决定 302）。
- **没有一次运行走到的分支等于没测。** e2e 的帮手在没有 Web Locks 时看租约，全量里一次也没读到它：把租约恒当作空、或改了它的键，全部故事照过。每一支要有一格只走它、去掉它就红；插一行计数看各支在全量里各走了几次，能找出这种分支（M12/P1/S1 的 P1S1B-M1）。
- **模糊测试的种子要盖住每一处边界检查。** Unicode Path 字段的"截断"种子截在 CRC 里，被"字段至少 5 字节"那一判先挡掉；其后两处边界（尺寸越过余下的字节、越界时截到余下的）去掉或放宽，普通的 `go test` 跑种子照绿。每一处边界给一个恰好截在它上面的种子；截在哪里要算到字节：截在名字的一个字中间，读出的不是合法 UTF-8，照样被后面的检查挡掉，"截到余下的"抓不到（M12/P3/S3 的 P3S3B-M1 与核对第 1 轮 B 的 C1-N1）。

## 2. 替身（fake）

- **替身要在真东西会失败的地方失败**：拒绝表的检查会拒的行（M10/P1/S1 的 A-N2）；失败时答零值；签名器签它真会签的东西。
  - **设计说"这一格抓这个变异"，先在那个替身下看它红；替身拒的连码与文字也照真的。** `linking/app` 的路径检查的替身收下真的会拒的 `"/"`，设计点名抓"`parent:"/"` 被拒"的 "the root" 一格在变异下照绿，只有调用次序的一格抓到；替身改成拒尾随的 `/` 之后三格都红。替身对 `"/"` 答的码又与真的不同（`invalid_format` 对 `required`），今天没有测试断言它，照样改成一样（M12/P3/S1 的 P3S1A-M2、A-C1-N1）。
  - **反过来，替身也不能拒真东西收下的；照规范推出的解析，要在真的解析器上逐个写法核对。** 网页的替身照 CommonMark 推：任何 `- [ ]:` 勾上都成链接引用定义（答 422），任何 `- [x]:` 都不是任务项。服务端（组合根的 `tasks`、`obsidian` 两个扩展）只在冒号之后是单个目的地、其后只有空白时才成定义：`- [ ]: a b c`、`- [ ]:` 勾上照写，`- [x]: a b c` 是任务项，替身却答 422、或不给复选框。审查 B 把十七种写法交给真的解析与 `ToggleTask` 的判法，替身的自测照这张表逐行断言视图里的复选框与切换的结果（M12/P2/S2 的 P2S2B-M1、C-N6，决定 585）。
- **测试文件不要导入它要测其注册的东西**（图片编码器会注册解码器）。
- **`vi.fn` 会给它返回的 promise 挂处理器**，未处理的拒绝因此不会冒出来。要探查时用普通的函数。
- **一个值里混着替身的时钟与真实的期限时，断言由同两个时刻算出的精确值，照生产的先后取时，再断言先后本身。** 提交的用例把"期限减提交的时刻"记进告警行的 `timeout_ms`：期限可以是请求的（`WithTimeout`，真实时钟），时刻来自假时钟。测试在造替身时就读了钟，晚一步才 `WithTimeout`，又只断言常量的界 ≤ 50：两次取时之间停 1 ms 就过界（CI 上停了约 3 ms，记 53），界还放过了记 0。
  - 断言精确值，由测试自己读的时刻与请求的期限算：偶发与记 0 都治了，但读钟的先后反了它也照绿。
  - 替身在 `Execute` 的前一行读钟（生产先由中间件定期限，第一个事务才读钟）：记下的值才落在生产的范围里，`SubmitTimeout` 这个同样真实的期限也才从提交开始算。
  - 先后另断言：比较钟自己的读数（不截、带单调读数）与期限，读在 `WithTimeout` 之前就红，不必等停顿。按整毫秒比，要停 1 ms 才红，又是原来的偶发。
  - 更稳的写法是 grep 的测试：`WithDeadline` 传一个确定的时刻，假时钟从同一个时刻推出，二者之差在构造上精确（`page/app/grep_test.go`）。
  - 出处：M11 的 `TestTheSubmissionsDeadline`，M12 的旁支 `m12-submit-deadline-log`（00-M12 决定 564–566）。

## 3. 交错与锁（PostgreSQL）

- **交错用确定的办法逼出来**：持住双方都要的行，等对方在等锁（`pgtest.WaitForLockWaits`），再放开。不用 sleep。
  - 两个请求之间的先后，要在一个共用的日志里断言，否则交换它们的变异能活下来。
  - "等到 N 次读"不是"流已连上"的信号：用一个直通的路由先挂住流，等放过的读都答完。
- **等锁的帮手要认出等的是谁。** `pgtest.WaitForTableLockWaits` 数这个库里任何在等这张表的后端；在跑着的服务里，服务起来之后几秒之内（本机量到 0.4–3.4 秒）River 跑 `RunOnStart` 的清理，它的五条语句也等 `page_revisions`。测试数到它，就在读走到快照之前写下 R：P3/S1 的 `TestTheLogReadsOneMomentAcrossARevert` 在 CI 上红过一次，本机没有负载时约 250 次一次（M12 的旁支 `m12-lockwait-by-statement`）。两种做法：按 sqlc 的语句名认出读停下的那一条（`WaitForTableLockWaitsBy`；名字写成它之前或之后的一条，都在时限上红）；或者持锁之前先 `awaitJob` 等完启动的任务（`transferTeam`，M7/P5A 起，P3/S1 的测试没照它做）。用一个先等上锁的普通 `SELECT` 作外来者，可以确定地造出这个红：改前 100 格红 98–100 格。去掉过滤还照绿的格，要问它的先后靠什么：M10 的 `rename_snapshot` 靠的是改名（一次 MCP 调用）比读慢，不是靠等待。审查里"只会假红"的怀疑，也要先逼出来再接受：P3/S1 的审查 B 当时就疑到这一点，没有复现、记成接受，之后在 CI 上红了。
- **持有者在提交时才放的行锁不排队**：一个新请求可以在等着的工作之前拿到它。
- **唯一的持有者从不排在等待者之后。** 同一事务里重入一行的锁不会等。所以 M10/P1/S1 的那个子测试钉住的是 PostgreSQL 的行为，不是我们的锁序。
- **`SKIP LOCKED` 的语句的测试要有上下文的期限。** 等 `ctx.Done()` 的测试要给等待设界，并断言是谁停下的；否则一个变异会挂住整个包。
- **两个时限各从自己的起点算，不要推断一个到了另一个也到了。** 提交的时限（`database.commit_timeout`，默认 2 秒）从提交开始算，请求的期限（15 秒）从请求开始算。设计写"提交跨过时限时请求的期限也已过"，只在提交开始得晚时成立；更常见的是提交先超时、请求还活着，走的是另一个分支、答另一句（M12/P3/S1 的 P3S1B-M1，决定 483）。两种都以探针造一遍（审查 B 用 `go test -overlay`，不碰工作树）。
- **锁外先判一次、锁下再判一次的，锁下那一次要有一格只有它拒。** 后台的恢复与撤销按人的上限先在锁外数、再在队列锁下数；所有的格都被锁外那一次拒了，锁下那一次不传人照样全绿。替身在锁外的计数之后、锁下之前给他加一个任务，锁下那一次才是唯一拒他的（M12/P3/S3 的 P3S3C-M1）。

## 4. PostgreSQL 的计划与代价

- **pgx 的语句缓存让服务端在第 5 次之后换成通用计划**，之后 `SET LOCAL enable_*` 不起作用。引导计划的测试要设 `plan_cache_mode = force_custom_plan`，并核对计划真的被采纳了。要确定地看计划模式，可以查 `pg_prepared_statements.generic_plans/custom_plans`。
- **`pg_stat_get_xact_*`** 累计一个连接的事务，约 1 秒才上报一次。在事务里取两次读数的差。
- **PG18 的 B-tree 跳跃扫描会用非前导列**：钉住索引的定义（`pg_get_indexdef`），不要只看名字。
- **不到 30,000 行的表会被整表分析**，计划是确定的；在这样的测试里关掉这张表的 autovacuum，"没有统计"的状态才保得住。
- **改一个计划要量多种形状**：几种数据分布（含一个文件夹占了大部分行），乘三种状态（没有统计、分析过、清理过），再乘自定义与通用两种计划，然后才选。
- **全局的库设置**（比如为一条语句关掉 JIT）要在每条热路径上量过再定；数据显示只有几条语句需要时，取窄的改法。
  - 加一个启动参数会弄坏连接池，改用连接之后 `SET`。
- **代价的界线只盖住列为"病态"的那些输入。** 每个节点都会调用的帮手要有它自己的密集输入。
- **判计划的规则，每个子条件都要有一格反例：去掉任一子条件，短测试都要有一格失败。** 每个子条件先各做一条变异（去掉它，或放宽成只看索引的名字），确认判计划的短测试有一格红，再信这条规则；按索引的名字放行的一支要连条件一起判，没有条件的主键扫描按键序读整张表。P1/S2 对 `page_contents` 补过这一种（S2A-N4），P3/S1 的批准守卫对 `nodes` 又漏了，短测试的六个子条件各自去掉都照过（M11/P3/S1 的 P3S1B-M1）。
- **计划在语句第一次真跑之前、在同一连接上判，不在写过之后判。** 写过之后表的大小与索引变了（没有统计时规划器按当前的页数估行数），判的不是生产那一刻的计划。在 tracer 的 `TraceQueryStart` 里、语句真跑之前 `EXPLAIN` 它（自定义带它的参数，通用经 simple protocol），`EXPLAIN` 的用时从计时里减。批准守卫原在删基线之后判，实测 84 条里 2 条与真跑时不同（M11/P3/S1 的 P3S1B-M2）。

## 5. 上限与解析

- **上限要在它要防的工作之前检查**，不是在一次本该被它阻止的读之后。
- **约束库真正收到的东西**（它的输出，或它清洗之后的标签），不是源文本：每一个只看文本的检查都被绕过过。
- **给一个库做预读，要与它的读法一模一样**（例如 archive/zip 的 zip64 检查），并把它拒绝或试探的那部分也算进读的上限。
- **照抄库的一段（正则、判断）来抢在它之前接手，差分要有能让每一处标志与界红的样本。** 编辑器照抄了 lezer 的电子邮件正则（带 `i`、每节至多 63 个字）；2 万篇随机文档与 57 篇手写文档里 `<?` 之后没有大写字母，也没有 63 个字的一节，去掉 `i` 或把一节收严一个，差分都照过。逐个标志、逐个量词的上界各写一篇恰好走它的（大写的本地部分与域名，第一节与点之后的一节各 63 个字），再以变异核对。只交回、由库再判一次的写法，变宽是等价的，要钉的是变严（M12/P4/S5 审查 B 的 M1）。
- **手写一个库的非标准读法会追着越来越罕见的形状跑**（YAML 扫描器跑了三轮以上）。改为设一条安全的边界：宁可不做（只漏、不写错），并以审查者对着真库做的差分为证据。
- **V8 对 ≥16,383 字符的字符串按长度哈希**，许多长的不同键的 Map/Set 在 Chromium 里是平方级的，在 Node 里却不是。要在 Chromium 里计时。

## 6. 前端

- **焦点**：
  - Chromium 在下一次渲染时才做 HTML 的焦点修正，把禁用的焦点元素交给 `body`；Firefox 与 WebKit 让焦点在禁用的元素上留一阵（M12/P2/S1：至少到扣住的答复放开）；jsdom 从来不做。判"焦点丢了"要连 `:disabled` 一起认（`lib/focus-leaving.ts` 的 `focusLost`），按钮还禁用时 `focus()` 它不起作用；
  - Safari 不让点过的链接与按钮获得焦点，`focus()` 的滚动也在下一次渲染；Playwright 的三种引擎（WebKit 在内）都给点过的链接与按钮焦点（M12/P2/S1 的探针），Safari 的样子只有 jsdom 的格与人工核对守得到；
  - WebKit 不滚到靠近文档顶部的标题，裸页面上也这样（M10/P4/S3）：`takeArrivalFocus` 补了一次滚动；
  - 焦点与滚动的修复要在三种 Playwright 引擎里探查，全部故事只跑 Chromium，三种引擎的只有配置里 `threeBrowsers` 列的几条；
  - jsdom 没有布局，`window.scrollY` 恒为 0，比较它的断言不可能失败。滚动放进 e2e；
  - 一处改了焦点的规则会波及别处：对照空闲退出、未读的内容、portal 里的对话框逐一核对。
  - Radix 的 `FocusScope` 的监听随它的 passive effect 才拆：卸下的那次提交里，layout 清理给出去的焦点会被拉回将卸下的菜单项，要在 passive 清理里给（M12/P2/S1 的 16.1）；
  - Playwright 的 `toBeFocused` 判过一次就不再看，之后才被抢走的焦点它看不见；延后的抢夺要靠 vitest 的格（M12/P2/S1 的 23.16：在 `setTimeout` 里把焦点给 Alert 的变异，A10 照过）。
- **SWR**：默认的比较对相等的数据保留旧对象，按答复挂的计时器因此不动了，用 `compare: Object.is`；挂上之后约 5 秒内焦点触发的重读被节流。
- **SWR 2.5.1**：带 `provider` 的 `SWRConfig` 卸下会删掉这份缓存的全局状态（在飞的请求与订阅），要让它随这一次进入一直挂着；React 18 起卸下的 hook 的回调照样调（只比键），不能靠"卸下就不调"（M11/P2/S3，推翻了设计审查时的一个前提）。
- **MobX**：每个 action 一个 reaction，加上 React 的合批，只有最后一条通知会渲染出来。把一轮的通知经 `setTimeout(0)` 合起来。
- **可读的名字**：
  - jsdom 会去掉 `sr-only` 里开头的空格，真的空格放在它外面；
  - Playwright 给块级的子元素补空格，后缀用括号起头，例如 `raw (source area)`；
  - 可读的名字在 Chromium 里由 e2e 按确切的名字核对（M10/P1）。
- **e2e 的"安静的控制台"能抓到事件驱动的读与登出的竞态。** 不需要流的故事就把流挂住。
- **并行 worker 下 WebKit 警告入口模块"预加载了没用上"**，只跑 Chromium 时看不到，放到 WebKit 才随机红（M10/P4/S3）。放行的条件要窄：只这个引擎、只 `/assets/`、只这句原文。
- **控制没有失败，先怀疑控制本身。** 改故事做变异时确认改到了哪一段：同一文件里常有两段相同的行，`replace(..., 1)` 改到的是上面那段，下面的故事照过，看起来就像断言没用（M10/P4/S3）。
- **`page.unroute()` 去掉一页的最后一个路由会关掉拦截**，正在那一刻发出的请求就挂住了。保留路由，用 `fallback`。
- **审查者不要在 `node_modules` 链回仓库的副本里跑 pnpm 或 vitest。** 给他们一个自己的副本，`pnpm install --frozen-lockfile --prefer-offline`。
- **`goto` 之后的否定断言不等页面加载就过。** 先等页面上一个肯定的东西，再断言"没有"。不然这条什么也没查，下一个 `goto` 还会打断在途的续期：令牌丢了，会话被撤销，在 CI 上偶尔跳回登录页（M10/P4/S2 的 LW6）。要复现这种竞态，把答复延后，不要靠重复跑。M12/P1/S1 起换文档经帮手 `goto`、`reload`，它先等在途的请求与续期，门禁守着（`e2e/fixtures/navigation.ts`）；断言之前等一个肯定的东西照旧。
- **"没有读、没有请求、没有出现"这类断言，要在同一个文档里、等那次本会触发它的事答了再断言。** 例如批准之后"重连不再读升级"，要等重连之后的最后一层读答了；换了文档、或不等就断言，断言是空的，什么改坏都照过。UP7 在 `page.goto` 换了新文档之后才放开流（SWR 的缓存每个文档一份，新文档从没装过升级页），UP8 放开之后不等就断言，一个卸下之后仍在重连时读升级的变异（审查 B 的 `leak`）两处都照过（M11/P3/S3 的 P3S3B-I1）。e2e 在放开之前登记 `waitForRequest`、等它的 `response()`，再看放开之后的请求；vitest 用事件流与重连（发 `mode`、断开再连），看假服务端的请求记录。
- **前面的早退会盖住后面的检查。** e2e 的帮手先看会话的记录，没有就交回"不用等"，走不到其后的锁：在这个文档里登录时，答复读完、令牌在锁里写进记录之前的那一段，帮手就换了文档，新文档落到登录页。几样检查串着做时，每一样都要问它在前面的早退之下还该不该成立，并有一格造出"早退的条件成立、后面那样也该等"的状态（M12/P1/S1 的 P1S1A-M1）。
- **"先看 A、再读 B，B 空就放行"之间页面在跑。** e2e 帮手看在途的请求为空之后读页面里的锁与令牌，读的 12.7 ms 里页面发出一个读，帮手照样换了文档（M12/P1 的帮手的旁支，LW3 在 CI 上）。两样要在同一轮里都空：读完 B 再看一次 A。
- **开了拦截（页面上有任一路由）时，Playwright 要等浏览器暂停了请求才报 `request`，可能晚于同时发出的 `page.evaluate` 的答复。** "读完页面再看在途的请求"隔一个轮询再看能少漏（240 次漏 3 次对 210 次 0 次），消不掉（M12/P1 的帮手的旁支，审查 A）。
- **按 `requestfinished`、`requestfailed` 记在途的请求，要在新文档提交时清掉旧文档的。** Chromium 只在页面读完答复的体时报 `requestfinished`；体没读完、或被路由扣着时文档走了，两样都不报。Firefox 对下一个文档请求之后才发出的请求也不报。留下的请求让下一次等满时限（M12/P1 的帮手的旁支）。认新文档用主框架的导航请求与它地址的提交；同文档的 `pushState` 不清。
- **一问接一问的闸门，只要有一问既不答也不失败，链就停了：每一问各自发**（Firefox，M12/P1 的帮手的旁支，A15 第 3 格）。
- **有意在加载中离开的故事，先等应用拿齐路由模块。** 被下一个文档打断的 `import()` 在 Firefox 里失败，应用把它记成路由错误，控制台就不安静（M12/P1 的帮手的旁支）。
- **自己的动作还在飞时，服务端的事件可能先于答复到达，事件带来的重读不能改写还开着的对话框身后的页面。** 批准在提交之后发 `mode`、答复在记日志之后才写，三种浏览器里都是事件先到：重读升级答 404，"正在批准…"的对话框后面写着"没有进行中的升级"。动作发出时记一个标记，记着时照旧显示上一份；成功时留到页面卸下，在答复时就清会在跳转之前闪出那句（M11 收尾的 B-N1）。
- **Chromium 不总是把浏览器自己开出的标签页报给 Playwright，不要等它。** 带修饰键点链接，标签页开了、载入了页面，可它的文档没有 `Page.frameNavigated`、且 `Page.getFrameTree` 答的是 url 为 `""` 的初始文档（不是 `about:blank`）时，Playwright 1.63 等一个没有时限的承诺、不报这个页，`context.waitForEvent("page")` 等满测试的时限（本机的 headless shell 约 25 次一次，同一修订的完整版 Chromium 200 次 0 次；1.65 alpha 同样地等；M11 决定 277，M12 的旁支 `m12-e2e-l1-new-tab`）。应用该负责的，在点击那一刻核对：在 window 上挂一个只用一次的冒泡监听器，它在应用的监听器（都在容器上）之后最后拿到点击，读 `defaultPrevented`、修饰键与 `closest("a").href`，再 `preventDefault()`，浏览器就不开标签页；地址在故事自己开的标签页（`anotherTab`）里 `goto`。**不能挂在捕获阶段**：它先于应用拿到点击，它的 `preventDefault` 让应用的处理器早退，"没被取消"恒真，Ctrl 走路由、Ctrl 点击被吞掉的变异都照过（旁支的审查 C）。
- **改了文字，断言旧文字的地方要找全，每种改了的语言都要有格读它。** M12/P2/S2 改了 en 22 个、zh-CN 27 个键的文字：
  - 找旧单位的 grep 用了词边界（`\bKB\b`），升级报告一格的断言里大小与后面的文字连着（`2 KBCreated`），没找到，8 号提交在干净的工作树里才红。找旧文字用不带边界的子串，或直接跑全量。
  - 只改了中文的键，改回旧文字照过的有五个：读它们的格都只用英文。逐个键、逐种语言改回 `main` 的文字（变异），活下来的就是缺格（M12/P2/S2 的第 10 个提交，审查 C 的建议）。

## 7. CI

- **新的推送会取消同一分支上正在跑的 CI**（concurrency group）。等最新的那次跑完，不要连着推。
- **作业日志要认证才能读**；失败的作业的 annotations（`/check-runs/<job id>/annotations`）与每一步的时间是公开的。Playwright 在 CI 上用 `github` reporter，e2e 的失败因此读得出来。
- **testcontainers-go 在 `go test ./...` 的所有包之间共用一个 Ryuk 会话**；一次连接失败会让后来的包丢掉 Postgres。所以 CI 的 Test 一步设了 `TESTCONTAINERS_RYUK_DISABLED=true`。
- **CI 的 Linux 回环在套接字缓冲小于 64 KiB 的 MSS 时被限到约 3 MB/s。** 只在 Linux 上失败的测试，在与 `go.mod` 的 `toolchain` 同版本的 golang 镜像里复现（`--cpus=2`、`-race`）。
- **同一棵树上，CI 的同一份测试可以差三成**（第一份 4:59–7:39）。判断挪不挪分份界线时，取两次运行的平均。
- **CI 的 lint 失败会盖住数据库变异归到哪个测试**：变异的分支也要过 lint（例如 `_ = x`）。
- **`make image-smoke` 会因为只被用户的全局 gitignore 忽略的文件报 `modified=true`。** 先看 `git -c core.excludesFile=/dev/null status --porcelain`。
- **setup-go 的缓存键由 runner 的系统与架构、Go 的版本、`cache-dependency-path` 所列文件（默认 `go.sum`）的哈希组成，工作流之间、矩阵的各份之间共用；键归先存下的那一份，存下就不再改。竞态与不带竞态的编译结果不共用。** S2 改了 Go 与 `go.sum`，`main` 的新键会由最先跑完、不带竞态的 `short` 存下（之前的键碰巧是 `bootstrap-1` 存的），分支上又先被 `vuln.yml` 一分钟跑完的一项占了：组合根每份从头编译，Test 一步多约 50 秒，看起来像是 Go 升级让竞态的份变慢，包的 `ok` 行的时间其实没变。只让要用的那种构建取存缓存；判份的慢之前先拆开 Test 一步里的编译与包的时间，再看缓存是哪一份存的，不看大小（M12/P1/S2）。
- **pnpm 12 的 `update` 对传递依赖不记版本**：`pnpm update -r <包>@<版本>` 对不是直接依赖的包报错；在上一级声明的范围之内修，写不带版本的 `pnpm update -r <包>`，它取满 `minimumReleaseAge` 的最新；范围之外的写 `overrides`（M12/P1/S2）。
- **Make 的配方里，拒绝的判断与干活写在同一个 shell 行。** 判断单独一行时，`make -i` 或环境里的 `MAKEFLAGS=i` 忽略它的失败、接着跑下一行（M12/P1/S2 审查 C 的 M1）。
- **量整个进程的 `TotalAlloc` 的守卫，会量到 pgx 的后台读取器。**
  - **原因**：pgconn 在每次 flush 前后挂一个 15 ms 的计时器（`enterPotentialWriteReadDeadlock`）。发查询的 goroutine 在那一段被挂起，pgx 就起后台读取器（`bgreader` 的 `bgRead`），把结果读进新的 8 KiB 缓冲，直到 goroutine 回来，多则整个结果，可以与要防的复制一样大，调界分不开。
  - **本机少见**：16 个 `yes` 占满 8 核时 240 次里 3 次第一次调用里出现 8 KiB 块，形状同注入的停顿（没有剖面，推断是后台读取器）；钉核没有出现。CI 的竞态一项在同一个 run 里连红三次。
  - **复现**：给连接包一层 `net.Conn`（`AfterNetConnect` 或 `DialFunc`），在被量的调用里每次写完停 17–20 ms（读一部分或全部）或 50 ms（读完整个结果）。
  - **定是谁分配**：每次调用记 `MemStats.BySize` 各类的 `Mallocs` 差；或者 `MemProfileRate=1`，前后各取一次 `runtime.MemProfile` 按栈求差，每次取之前三次 GC（一次分配在它之后第二个周期才公布）。
  - **改法：按 pgx 的分配形状配对减去，不整类减去。** 8 KiB 块与 `iobufpool` 每新建一块都带的 24 字节 `*[]byte`，取两者中少的那个块数；整类减去时，一个每行 `Grow(8 << 10)` 的暂存缓冲藏得住 67 MB 的复制。再取几次里最小的，防备别的偶发来源。
  - **写出盲区**：每块之外再分配一个 24 字节对象的复制；不是每次调用都有的复制。**随 pgx 的版本核对**块的大小与 `*[]byte`。**读得碎时第一层不够**：减去之后还剩每次读约 90–160 字节的簿记。
  - 出处：M12 旁支 `m12-p1-prepared-alloc`（00-M12 决定 357），审查 B 的 ALLB-I1。
- **通过的运行不打印守卫量到的数**（CI 的竞态一项不带 `-v`），红了才看得见一个点。守卫的失败信息要写出能分辨来源的数，例如按大小类拆开（M12 旁支 `m12-p1-prepared-alloc`）。
- **同一型号的 runner 也会整台慢一截。** 7763 上有一次在 38 次里每一项都最慢：
  - 计时的新建、移动、恢复、撤销比中位慢 9–25%；
  - 不计时的种子与准备慢约 18–20%；
  - 编译慢 16%。

  同一棵树半小时之后在另一台 7763 上重跑，撤销回到 3.54 秒。判"代码变慢了"之前，依次看：同一作业里别的用例与编译；同一型号的别的运行；别的 CPU 前后有没有台阶。

  读重跑过的运行，要指明 attempt：`gh run view <run> --attempt 1 --log-failed`；`gh run view --job <attempt 1 的 job>` 给的是后来那次 attempt 的日志（M12 旁支 `m12-p1-source-revert-deadline`，审查 A 的 Q1）。
- **失败日志里的 UUIDv7 读得出现场的时间，要配合记下的值。** Go 标准库的 `uuid.NewV7` 取墙上时钟：前 48 位是毫秒，`rand_a` 的 12 位是 1/4096 毫秒。
  - 同一个 1/4096 ms 里连着造的 id 取上一个加一，只说明先后；隔得开的 id，时刻准到约 0.24 µs。
  - 先查清每个 id 在代码的哪一步造。两个 id 圈出的是一段窗口，不是两次读钟本身；要配合记下的值，才定得出停顿在窗口的哪里。
  - 这一次对得上，是因为记下的 `timeout_ms` 也按墙上时钟算：`first.at` 经 `UTC()`、`Truncate` 去掉了单调读数。两边都带单调读数时 `Sub` 只用单调时钟，墙上时钟一跳就对不上。
  - 这一次 `newCheckFake` 与 `newSubmit` 的 id 相隔 3.27 ms，配合记下的 53，定出两次取时相隔 3.00–3.32 ms：停顿的位置与长度成了核实的，原因仍是推断。
  - 只适用同一进程里标准库造的 id；SQL 的 `uuidv7()` 没有核对。
  - 出处：M12 的旁支 `m12-submit-deadline-log`，审查 B 的 SDB-N1、N3。

## 8. 流程

- **修复的核对每一轮都要做，做到干净为止。** M5–M7 里，核对一再找到上一轮修复自己引入的回归（焦点、锚点、滚动）。
- **删掉一个"看不出效果"的守卫之前，先试交错**：双击、按住的键、失败的路径。M4 删过一个，结果它是看得出的。
- **日志写事实（大小、计数），不写推断出的原因。** 同一个结果可以有相反的原因。
- **审查者的探针**（穷举、新旧实现的差分）是最强的证据，要请他们做，并留下它们。
- **在改坏代码的时候不跑 `make gen*`。**
- **复原改坏的文件不用 `git checkout --`**，它会连没提交的改动一起丢掉；从备份复原。
- **`oxlint` 的退出码要单独看。** 接一个 `| tail` 的管道藏住过一个警告，结果被推了上去。
- **在工具的输入里写 `\uXXXX` 会被当成 JSON 转义变成字符**（Claude 的工具的毛病，Codex 未必有）。Go 的测试里要转义时，事后用 Python 的 `chr(92)` 补；新的测试文件 lint 之前扫一遍非 ASCII 的字符。
- **只改契约的说明也要 `make gen`**，然后 `make gen-check`。生成物在提交之后才一致。
- **逐个提交的核对，要跑读工具表与契约的测试。** 一个提交加了 MCP 工具，只跑了它自己的测试，漏了按工具表要每个工具一组参数的 `TestToolStrings*` 与断言工具数的 e2e，到门禁才红（M11/P2/S2）。
- **改一条所有路都走的规则，设计说"现有的格照过"之前，在原型上跑到组合根。** 第 302 条的 spec 只在原型上跑了 page 模块的测试；`make test` 在实施的第一个头上红了两格钉着旧 409 的组合根的测试，翻转放进第 2 个提交、只好重做第 2–5 个（M12/P3/S2，P3 设计 3.22 第 1 条）。先 grep 旧结论（码、断言的文字）在整个程序的测试里出现在哪里。

## 9. 实测

- **量法自己会定结论，逐个条件问它把结论往哪边推。** M12/P4/S2 的审查找出的都在量法里，不在产品里：
  - 附件列表的复测让 B 在上传窗口之后多打 3 秒，多出的一次保存在桶回满之后答 200，替窗口末尾被拒的那次补上：记下 0 / 5，B 跟窗口一起停手是 3 / 5（审查 C 的 I1）；
  - 编辑器的解析每格在新页里只量 5 次：垃圾多的形状在新页里头几次便宜，中位总落在便宜的一段，判成"不超"；量 20 次是 85–90 ms（核对 B 的 C2-I1）；
  - 展开文件夹的 T3 排在五次新建之后，文件夹已被挤出视口，"视口里的孩子画出"一画出列表就成立（审查 B 的 M1）；"插一个字"放在段中，把按长度平方增长的一串劈成两半，只量到约一半（审查 B 的 M2）；
  - 也有往"超"推的：一次计时包住了两次解析（审查 B 的 I1）；同一页里先量二十来种形状，后面的读数随页的堆涨到两倍（核对 B 的 C1-M1）。

  停在哪里、量几次、插在哪里、页里先做过什么、终点看得见什么，各是一个条件。终点要事后断言它不是平凡成立的（T3 断言视口里的孩子 ≥ 1）。
- **复算之前先问量的条件是谁定的。** 从结果文件复算只证明数算对了；条件里实施者自己定的那几个，照设计的读法结论会不会变，要单独问。附件列表那一次，"B 打到窗口之后 3 秒"写在实施中定的小决定里，理由只有"窗口里恰 6 次"，主持者接受时不知道它决定了结论（M12/P4/S2 的 C-I1）。实施者记量的条件时写明照设计的读法会怎样，并把能复算它的数记下来（每次复测最后一次保存的时刻与状态）。
- **只记的量也要与改前并排看。** M12/P4/S4 的再量里，"移到……"对话框（没有界线，只记）从 1.26 秒变成 2.3–2.5 秒：行每次渲染给对话框新建的函数，菜单在挂上对话框的那次提交里关上，layout effect 让行再渲染，对话框跟着把整棵树又算一遍（M12 决定 533）。界线只管它管的那几格；改法碰到的路上，别的量翻倍也是发现。再量的报告把只记的量逐个与改前列在一起。
- **量时间的那一段，锁外的负载要看得见。** 锁只让排队的人排队，挡不住不经锁的进程：P4/S2 有一轮撞上别人不经锁的 vitest，P4/S4 的补量撞上别人锁外约 45 秒的 Node，都是事后别人说了才知道，作废重量（M12 决定 535）。量的那一段里每几秒记一次负载与前几名进程（P4/S4 的重量每 5 秒一行），开跑前记 `uptime` 与锁外的进程；重叠的轮作废重量，读数过界也一样：结论不变，可要写进文档的数会偏高。
