## 改法

只改 `.github/workflows/ci.yml` 与新的守卫，产品与故事都没动。

- **三个时限**（决定 599）：
  - **E2E 一步自己 18 分钟**，是 00-M12 第 3 节第 11 条的界。原来作业 20 分钟里 E2E 实际能用的时间，绿的 235 次最少 15:14、中位 18:32、最多 19:19（审查 B）；18 约是最长的绿 E2E（8:52）的两倍。超过时这一步失败、作业红，不是被取消，报告照传（见"反向对照与分支 CI"）。
  - **装浏览器一步自己 30 分钟**：实施时 25，修复第 1 轮改。
  - **作业 55 分钟**：实施时 50。两步各自的时限要先于它到；守卫要求不少于 30 + 18 + 5。
- **缓存**（决定 600）：
  - 键 `playwright-debs-<ImageOS>-<Playwright 的版本>-<ISO 周>`，restore-keys 是去掉周的前缀。Playwright 的版本定要装哪些包。
  - 每周一个新键：Ubuntu 的更新让存下的 `.deb` 渐渐过时。11-07 至 18 日的 242 份包表里，6 个包换过版本（gstreamer 的 3 个换了两次），新多出 4 个 mesa 的包；包表是 181 或 185 个，185 个的只出现在 20261111.* 的镜像上（审查 B）。新的一周先取回最近存的一份，只取变了的，再存成新键。
  - 装浏览器一步：缓存里有 `.deb` 就 `sudo cp` 进 `/var/cache/apt/archives`；装完 `apt-get autoclean` 删掉索引里已没有的版本，再把留下的拷回缓存的目录（A 在本机核过 `autoclean` 只删索引里没有的版本）。
  - restore 与 save 分开，是钉住的同一个 `actions/cache` 提交的两个子 action，不是新的第三方 action。save 在装浏览器之后、E2E 之前，只在没有恰好命中时存；装浏览器失败时不存（`if` 里没有状态函数，隐含 `success()`）。合在一起的 `actions/cache` 只在作业成功时存（`post-if: success()`），E2E 红了，重跑就取不到。
  - 一份约 119 MB；仓库的缓存在审查时 14 项、约 2.1 GB，上限 10 GB（A）。
- **守卫** `TestTheE2EStepHasALimitOfItsOwn`（`server/internal/platform/buildinfo/e2e_limits_test.go`，与读工作流的 `TestOnlyATagsJobsMayWrite` 同包，共用它的帮手）：
  - 恰有一步跑 `make e2e`，时限恰是 18；恰有一步装浏览器，有自己的时限；
  - 两步都不带 `if`；作业的 `if` 是 server 作业的；
  - 作业的时限不少于两步之和加 5 分钟；
  - 作业与各步都没有 `continue-on-error`；
  - 失败的信息带读到的值与类型。在 `main` 的 `ci.yml` 上红。
- **不采用的**：
  - 换镜像：哪个镜像从 AWS 上快，核实不了；apt 的 mirror 方法只在失败时换下一个，慢不算失败。
  - apt 的 `Acquire` 超时与重试：没有按速率的超时，管不了慢而不断。
  - Playwright 的官方容器：`make e2e` 要 Docker 起 PostgreSQL，容器里要另装 Go 与 Node、挂 Docker 的套接字，每次还要拉约 2 GB 的镜像。

## 接受与推后的

- **缓存的善后命令失败也让作业红**（EIA-N2）：`autoclean` 或拷回失败（例如磁盘满）时，装浏览器一步在 `bash -e` 下失败，E2E 不跑。很少见，守卫又不许 `continue-on-error`；不改，注释也不改。
- **注释里的计数截在 11-18 07:34 UTC**（EIA-C1-N4）：是下限，口径写在"定因"。
- **守卫不钉 30**（核对第 1 轮 A）：30 是判断，不是第 11 条的数。
- **守卫对作业没有 `if`、一步上 `if: true` 也报红**（修复第 1 轮的变异 x5；核对第 1 轮 C 读代码）：作业没有 `if` 时因 `needs` 同样随 server 被跳过，不会漏跑；守卫照作业的注释"if 与这两个任务相同"，偏严，只会多报红。守卫只与 server 作业的 `if` 比，现在 web 作业的逐字相同（核对第 1 轮 C）。
- **守卫不管的几样**（审查 C 的变异照绿）：E2E 之前另起一个不带时限的步骤、save 挪到 E2E 之后或带 `always()`、两个时限都调得很大。它们不碰第 11 条：卡住时到作业的时限被取消，不会变绿；其余只让缓存变差或浪费资源（C）。
- **周的轮换还没在 CI 上走过**（A）：W48（2026-11-23 起）第一次运行的日志看三样：是否 "Cache restored from key: …-2026-W47"，是否 "Cache saved with key: …-2026-W48"，`.deb` 的个数与大小是否没涨。
- **restore 卡住**（A、C）：`actions/cache` 每段下载默认最多约 10 分钟（两位都凭记忆，没有复现）；碰上慢的安装时，作业的 55 分钟可能先于 E2E 的 18 分钟到，结论是 cancelled。仍是红，发布的闸门只认 success。
- **合并之后 `main` 的第一次取不到缓存**（核对第 1 轮 A）：分支存的 `main` 读不到。那一次若在 AWS 的慢镜像上，装浏览器大概又是 25 分钟上下，在 30 之内。
- **没有核实的**：
  - runner 上的 apt 2.7.x 同样只比大小，是凭记忆（A）；
  - PR 的运行也读它目标分支的缓存，一个分支的缓存因此也会被以它为目标的 fork PR 读到；只是被读，碰不到 `main` 的，不影响决定 601 的结论（凭记忆，核对第 1 轮 A）；
  - 缓存的写入凭作业的运行时令牌、不归 `permissions` 管（核对第 1 轮 A 的推断）。
