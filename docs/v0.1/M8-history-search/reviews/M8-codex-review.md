# M8 代码质量评审（Codex）

评审日期：2026-10-16。基线：`main`，`4db8503ae5c26bb2dd097bdd5f011c1fcef2efad`。本文不包含后续处置。

## 1. 结论

发现 **3 项：Critical 0、Important 1、Minor 2、Nit 0**。

- **R1 / Important**：搜索响应的耗时可区分无权访问范围内某组查询键的大量候选是否存在。真实 HTTP、身份认证和笔记本权限下，返回内容始终为空，隐藏正文从 A 改为 B、再改回 A，慢查询也随之反转。这是 **P5A C-S1 的复核升级**，与 M12 性能第 17 项为同一根因；依据本次评审明确允许的“经耗时推断内容”例外重新计数，不称为全新根因。
- **R2 / Minor**：Go 与 PostgreSQL 的 NFC 处理不同，合法的 `a + 31 个 U+0301` 用完全相同的原文查询，排队及建好索引后都找不到自己的正文。
- **R3 / Minor**：活着的页面在旧版本中独有的别名引用，不随目标的别名变更刷新。服务端重新读取已经返回未解析链接，当前打开的历史页仍保留旧链接，刷新后才一致。

所要求的基线门禁全部通过。没有证实新的数据丢失、错误写入、返回正文/摘录越权或服务端、浏览器崩溃；R1 是已证实的内容相关耗时侧信道，不能据此声称能恢复单页秘密、精确频率或全文。建议 R1 在 M9 前修复；R2、R3 不单独阻断 M9。

## 4. 发现详情

### R1 — Important：空结果的耗时仍暴露无权范围的内容相关信号

**位置与原因。** `server/migrations/sql/00040_page_search.sql:40` 的 `page_search_hits` 只接受查询键，没有范围；`:44` 起读全实例 GIN 候选。`server/internal/modules/page/adapter/postgres/queries/search.sql:143` 对这个全局集合计数，正文查询 `:166` 再读一次，直到 `:173` 连接 `nodes` 才按笔记本过滤。`server/internal/modules/page/app/search.go:182` 调用 `SearchHitCount(ctx, scope.Query)`，端口本身也不携带可见范围。`MaxSearchWalk` 限的是后面的正文复查，挡不住前面的全局倒排枚举。

**复现。** 在本地测试自己的数据库里，用真实 API 建立工作区和用户 Alice/Bob；Bob 是工作区成员，只能读 Eng，Eng 放一页空正文。Alice 的 Ops 不向工作区开放。用夹具 SQL 在 Ops 准备 60,000 页和对应搜索索引，正文全部为 `quartzalpha`。索引键使用原 `domain.SearchTokens` 生成，测量前 `VACUUM ANALYZE page_search` 并分析节点/正文表。用 Bob 的真实 bearer token 检查：笔记本列表只有 Eng 且角色 reader，Ops、Ops 节点列表和隐藏页面的 GET 均 404。随后通过本地实际 HTTP 服务交替搜索两个等长词 `quartzalpha` / `quartzborta`，每词 32 次、弃前两次，得到 30 个样本。只把隐藏 Ops 的正文及索引改为第二个词，重复；再改回第一个词，重复。测量包含 HTTP 往返及读取响应体，不含建语料和 ANALYZE。共 192 次请求、180 个有效时延样本；表中中位数沿用日志定义，为 30 个样本排序后的第 16 项。

**实际与预期。** 三阶段所有搜索都返回 200、`data=[]`、`count={kind:exact,value:0}`、`building=false`、`next_cursor=null`，但耗时随隐藏内容反转：

| 隐藏 Ops 正文 | 查 `quartzalpha` 中位数（最小–最大） | 查 `quartzborta` 中位数（最小–最大） |
|---|---:|---:|
| A：`quartzalpha` | 30.154 ms（29.557–32.517） | 3.190 ms（2.832–3.473） |
| B：`quartzborta` | 3.274 ms（2.918–3.613） | 30.418 ms（29.216–32.808） |
| 回到 A | 30.336 ms（29.989–32.588） | 3.317 ms（3.142–3.894） |

每阶段快慢两个集合的样本范围均不重叠。独立的原 app+真实 PG 探针也得到约 32 ms / 2.2 ms 的同向反转；该独立探针的可见范围是测试端口固定值，不冒充 HTTP 权限证明。预期是不可见范围不参与该用户搜索的候选扫描与估算，不应仅隐藏内容变化就产生这个确定的查询相关信号。

**影响与边界。** 一个具有少量可见内容的合法读者，可对比候选词请求的耗时，辨认隐藏范围内某组查询键是否有大量候选。内容与频率相关信号泄露发生在普通只读请求，不需要写隐藏范围。实测的是同工作区的私有笔记本；SQL 无工作区条件，跨工作区适用是源码推导，未另建跨工作区 HTTP 语料。未证明能判断单个页面、定位具体隐藏笔记本、得出精确频率或恢复原文；三元组交集也不能保证存在原样连续子串。语料是合成极端分布，测量是本机 HTTP，未验证公网噪声下的分辨能力。上述限制不消除已经复现的保密边界问题。

**证据。** `http-scope-timing-first.log`、`http-scope-timing-probe_test.go`、`root-scope-timing-first.log`。HTTP 测试名 `TestReviewHTTPHiddenSearchTiming`；实际命令为 `GOMAXPROCS=2 go test -p 1 -count=1 -timeout 3m -run '^TestReviewHTTPHiddenSearchTiming$' -v ./internal/bootstrap`。语料为直接 SQL 准备，未通过 60,000 次保存，也未补全无关的历史行；搜索、认证、授权、VisibleIn、路由和 SQL 读取均为原实现。

**与已知项的区别。** 这不是新的“缺 notebook 列”或普通延迟长尾。P5A **C-S1**、主持者决定 8、M12 性能 **第 17 项“跨工作区的计时”**已经记录同一根因及大量频率风险，原记录没有被证明错误。本轮补上真实身份/权限、相同响应、等长词、交换隐藏语料再换回的运行证据。依据用户明确的保密例外重新列为 R1，不能与旧 C-S1 再算两项。

**建议。** 把允许搜索的 notebook IDs 传入候选和估算路径，使候选读取本身按权限范围分区；同步处理标题层、正文层、计数与队列，避免只在最后过滤。`page_search` 增加不可变的 `notebook_id` 并采用能限制倒排读取的复合索引/分区是候选方案；仅在全局扫描外面补 WHERE 不足，必须检查实际计划和隐藏语料放大实验。按范围列/位图是否仍读取全局词表重新验证，不能把加列等同于已修复。回归应保留真实 reader 与隐藏范围的反转实验，同时覆盖普通可见性、准确计数/估计及原性能规模。

### R2 — Minor：合法组合字符的完全相同原文查询漏搜

**位置与原因。** `server/internal/modules/page/domain/search.go:418` 用 `norm.NFC.String(f)` 生成查询文本；`server/internal/modules/page/adapter/postgres/queries/search.sql:182` 用 PostgreSQL 的 `normalize(raw, NFC)` 处理正文，`:185` 起复查模式。Go `x/text` 在超过 30 个连续 non-starter 时还做 stream-safe 处理，插入 U+034F（CGJ），PostgreSQL 不插入。双方都称为 NFC 并不代表所得字符串相同。

**复现输入。** 页名 `Exact content`，正文和查询都为 `"a" + strings.Repeat("\u0301", 31)`，即 63 字节合法 UTF-8，没有 NUL，在 256 字节查询上限内。先准确入队查询，再建好索引查询；不涉及大小写变换，也不截取部分词。

**实际与预期。** Go 查询为 `U+00E1 + 29×U+0301 + U+034F + U+0301`；PostgreSQL 正文为 `U+00E1 + 30×U+0301`。queued 和 built 都走查到该页，但均为 `passed=false`，无法搜到自己的正文。预期两阶段均命中。相邻的 30 个组合记号控制、正文显式为 Go NFC 含 CGJ 的控制，两阶段均通过；既有越南文/谚文非 NFC 回归也通过。因此不是排队漏项或索引候选缺失。

**影响。** 少见但合法的密集组合字符文本漏搜；重建索引不能修复。未发现正文写坏、崩溃或越权，因此定为 Minor，不因输入少见否认缺陷，也不升级为普遍不可搜索。

**证据。** `search-unicode-probe.go`、`search-unicode.log`；`TestReviewSearchFindsItsExactLongCombiningSequence` 的正确行为断言失败，两个控制子例通过。命令为 `GOFLAGS=-p=1 go test -p 1 -count=1 -v -run '^(TestReviewSearchFindsItsExactLongCombiningSequence|TestTheSearchReadsContentNotInNFC)$' ./internal/modules/page/adapter/postgres`。根评审在另一份 archive 中独立重跑该新探针，仍仅 raw31 子例失败、两个控制通过，退出 1，墙耗时 2.491 s；见 `root-unicode-recheck-retry.log`。这次退出 1 是正确行为断言暴露缺陷，与首次容器启动失败不同。

**与已知项的区别。** P5A **A-N1** 接受的是特定字符 case-fold 后组合改变，部分词在建好索引后缺候选键；本例全小写、整词同原文、两阶段候选都在，失败点是 SQL 复查。P5A **A-M4** 已修普通 NFC/分解正文不一致，这里是该修复未覆盖的 stream-safe 差异。A-N8、软连字符/ZWJ/异体字选择符的已知字面匹配例外也不是查询规整器凭空插入 CGJ 的情况。

**建议。** 查询、索引、正文复查和摘录坐标使用一致的 NFC/stream-safe 策略，保留用户原始正文与显式 CGJ 的含义；不要全局删除 U+034F。加 30/31 边界、显式 CGJ、queued/built 回归；若改变索引键，依 `SearchTokenizer` 版本约定处理重建。摘要可能受同一规整差异影响，但本轮只实测漏搜，不另计摘要问题。

### R3 — Minor：旧版本独有的别名引用缺少失效事件

**位置与原因。** `web/apps/web/src/events/handlers.ts:85` 对普通 pages 事件只刷新编辑中的版本正文，`:86` 只有 `tree=true` 才刷新全部历史 view；`:131` 对 links 事件按当前来源页面 IDs 刷新历史 view，`:199` 起继续按这些 IDs 筛选。`server/internal/modules/linking/app/index.go:113` 从当前链接索引的变化构造来源，`:131` 在没有当前边变化时不发 links。旧版本独有的引用不在当前索引中，别名作为正文 frontmatter 变化又是 `tree=false`，因此当前策略遗漏它。

**操作序列。** 建立 Target，正文为 `---\naliases: [OldAlias]\n---\nInitial\n`；建立 Source v1=`[[OldAlias]]\n`，再写 v2=`No links now\n`。在 Chromium 打开 Source v1，确认 OldAlias 链接到 Target；另一个标签页打开 Target。经 API 把 Target 正文改为 `Alias removed\n`，不改名或移动。等待第二标签页确实通过事件显示新正文，再检查仍开着的 v1。

**实际与预期。** 真实 `getPageVersionView(Source,1)` 已返回 `nw-unresolved`，但原标签页仍显示可点击的 OldAlias、href 仍为 Target；刷新前旧版 view 重读次数是 0，reload 后才变成未解析按钮。控制场景让 Source v2 仍含该引用，同一次别名变化发送 `links.pages=[Source]`，旧版自动重读并正确更新。预期旧版本的“按当前树解析链接”阅读视图在解析依据变化后与重新 GET 一致，无须整页刷新。

**影响。** 活着的页面旧版中、当前正文已不再出现的引用可能保留过时目标；读者会看到与当前解析不一致的链接。重新读取可纠正。没有证明越权、内容写坏或数据丢失，定为 Minor。

**证据。** 真实 Chromium 双标签页、实际服务和事件，两个场景首轮 2 项、重复三轮 6 项、最终带截图 2 项共 10 次；日志 `frontend-alias-browser*.log`，源码 `frontend-alias-browser-probe.spec.ts`，截图 `frontend-alias-stale-0.png`。第二标签页的正文更新用于排除事件流尚未建立；直接 GET 和 reload 用于排除后端解析器仍未更新。探针是在基线构建后运行，未修改生产代码。

**与已知项的区别。** `02-P2-trash.md:577` 已写明回收站预览没有当前索引，不接点名 links；本条只报告**仍活着的 Source 的历史版本**，不重计那个已知限制。P1B **B-I1** 是旧正文缓存积累，收尾 **B-M1、K2-1** 是删除后的树/焦点；本例没有删除或导航焦点变化。依据为 `00-M8-design.md:102` 的当前解析语义、`:263` 的版本 view 事件重读，以及 M6→M8 移交第 3 项。

**建议。** 不要只用当前正文索引的来源 ID 作为历史 view 的失效集合。可为别名等解析键变化增加笔记本范围的解析代际/失效信号，或者给挂载的历史 view 独立的失效机制；避免每次普通保存都刷新全部历史正文。把“当前正文有/无旧引用”两种真实事件路径都纳入回归。

## 5. 设计层面的疑问

### D1：搜索的范围是否应该成为底层候选端口的必需参数？

关联 R1，不另计发现。`SearchHitCount(ctx, SearchQuery)` 和 SQL 函数的签名允许应用层拿到范围后仍做无范围工作；最后过滤保证返回值权限，却不能表达本轮要求的耗时保密边界。建议把“已授权范围”贯穿候选、计数、计划估算，而不是仅靠调用者记得加最终条件。新增范围列后仍应要求计划证据，不以接口参数存在代替隔离成立。

### D2：历史字节不可变，历史 HTML 的解析依据可变，缓存是否需要分别表达？

关联 R3，不另计发现。版本原文按 revision 缓存成立，`page-version-view` 却还依赖当前名称、别名和目标状态。当前对“哪些来源改变”的理解沿用当前正文索引，表达不了历史独有依赖。建议在修复时明确 view 的解析代际和失效协议，保持原文字节缓存稳定。若选择仅在焦点/刷新时更新，须明确调整当前承诺和测试，而不能用“版本不可变”解释 view 永远无需事件更新。

### R1 的决定（负责人，2026-10-17）

R1 就是 P5A 审查的 C-S1（那时存疑，主持者的决定 8 随未决项 9 移交 M12），这次以真实的身份、权限与 HTTP 量出：读者看不到的笔记本里 6 万页写着 `quartzalpha` 时，读者搜它 30.2 ms、搜等长的 `quartzborta` 3.2 ms，隐藏的正文换成另一个词、再换回来，快慢都跟着反转。原因是 `page_search` 的键是整个服务器的：一个词的倒排列表里有所有笔记本的行，候选的读先读完它，连 `nodes` 时才去掉范围之外的。

设计调查在一份合成的语料上比了五种做法（299,200 页、5,000 本笔记本、1.88 GB 正文，PostgreSQL 18.6 的默认设置；Codex 的 A→B→A 经用例与经 HTTP 各量一遍，另数每个读取的块）：

| 做法 | 结果 |
|---|---|
| O1：加 `notebook_id` 列，`btree_gin` 的多列 GIN | 不取：规划器可以（1 本与 5,000 本时确实）不带笔记本的键扫位图、之后再过滤，就是今天的全局读；逐本强制时它仍走这个词全局的倒排树、按笔记本跳着读，隐藏的项越多越慢：+1.33 ms（噪声 0.07 ms） |
| O2：每行加一个笔记本的词，与查询 AND、范围里各本的 OR | 不取：K 路的 OR 对每一项算一遍，200、5,000 本时 0.2–16 秒；拆成按笔记本的查询数组（O2A）时罕见的词每本走一遍全局的倒排，仍泄露（随阶段 6.8、9.4 对 2.9 ms），5,000 本时慢 30 倍 |
| O3：按工作区分区 | 不取，没有建：同一工作区里的私有笔记本（Codex 量的正是这一种）仍是今天的索引，+27.8 ms；LIST 分区要运行时建表，运行时的角色不能 |
| O4（读作 O4A）：每个词带它的笔记本的前缀 | 推荐：一个 GIN 的键只是一本笔记本的词，倒排列表里只有这本的行；候选的读以读者的笔记本作必需的参数、每本读一次（`body @@ ANY (page_search_queries(notebooks, keys))`）；两个 GIN 都 `fastupdate = off`（待处理列表每次读都整个读，又只有表的主人能清空它）。通道 −0.010 ms |
| O5：对工作区开放的笔记本另加工作区的键 `W#` | 没有建：只在几百上千本开放的笔记本的工作区是目标时才值得，移交 M12 |

### 我的决定（负责人可以改判）

1. **R2 的判断与接受的局限**：凡是 Go 的 NFC 改了的查询词在正文里按 PostgreSQL 的 NFC 找（照 NFC 打的查询不多一条语句）。接受：30 个以上的组合记号以两种次序写的同一串，排队时找到、建好之后找不到；从一串记号中间开始的词；两边的 Unicode 不一致的记号（今天是 Unicode 17 新加的 34 个）上，次序不同的查询与正文互相找不到，两个方向都是（C2-1）；显式的 CGJ 在正文里保持意思，不带 CGJ 的查询不再找到恰在 Go 插 CGJ 处写着 CGJ 的正文，包括改名时"更新链接"写进链着它的页的那一种（修复核对第一轮的判断）；同一个词两种写法算两个词，8 个词的上限照这样数（C2-3）。另一种做法是核对者给的：没插 CGJ 的改了的词在正文里两种写法都认。
2. **R3 用 `links` 事件的 `aliases`**，不另加解析的代际（D2）；别名的事件重读这本笔记本挂着的全部版本视图与回收站的预览，不只点到的页：旧版本里的链接不在索引里，服务端不知道哪些版本用到这个别名。别名很少改，普通的保存不受影响。
3. **A-1 的界线按最长的前缀算**：一页中文约 0.8 MB 以内全部进索引（R1 之前约 2.1 MB，按真的前缀约 1.3 MB），更大的页之后的部分只在排队时找得到；P5 的语料里最大的页 469 KB，仍在界线之内。
4. **留给 M12 的**（[M12 的性能移交](../../M12-release/handoffs/M4-performance.md)第 17 项）：一次请求只读一遍候选（只读的快照里没有临时表，交回 Go 再传回要重新解析，共用一个候选集又要合并用例的几条语句，没有小的改法；`page_search_queries` 在 200 本以内 0.5–1.1 ms，5,000 本时 4.4–24 ms）；O5；名称层对很常见的键的估计；数据库确定地拒绝的行（一直留在队列里，批量的让它的笔记本一直"正在建立"）。名称层只看键的半连接（调查时列的缓解之一）试过，通用计划之后没有帮助（200 本的 `锅 中国` 38.5 → 40.0 ms），没有取；表达式索引的变体（体积少约 1 GB，约 4.7 倍）为简单不取；以 `SECURITY DEFINER` 的函数在每批之后清空待处理列表（任务快约五成，搜索在一批期间读到一点隐藏的写）没有做。
5. **任务按笔记本走**（B-3）：快一倍左右、WAL 少一半多，一本笔记本的行写完就不再说"正在建立"；代价是一次运行停在的那本要等这一遍绕回来，升级的重建里最早、最大的约 15 本笔记本整个重建期间都说正在建立（第二轮核对的 R2-N3）；不是退步：按 id 走时每本都到最后。README 写明次序与进度的查法。
6. **守卫的时限照 P5A 的规则重量**：读的时限多数收紧（之前在待处理列表上量的），建 5,000 页的从 7 秒放宽到 26 秒；本机的余量足（安静时至多是时限的 0.40，负载下 0.66），持续集成上那一行没有读到（M12）。
