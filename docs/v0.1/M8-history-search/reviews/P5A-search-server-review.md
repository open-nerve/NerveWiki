## 主持者的决定

负责人可以改判：

1. **后台任务的节点以批量入队**（C-I1、B-M3）：导入、后台的恢复与撤销的单元以批量入队，建好之前不当候选、答复带 `building`；同步的单元（用户的写、请求里的恢复与撤销，P2 的界线一个单元至多 100 页）准确；任务先按 id 做准确的，再按 id 做批量的。`TestTheSearchFindsEachWriteAtOnce` 的后台两步随之改为建好之后找到，C 的积压的形状另写一个测试钉住。
2. **64 的界线只对 ASCII 的字母与数字**（A-I1）：分词的 `word()` 与查询的 422 一样；别的长串以三元组进索引，受 1 MB 的词的界线；泰文与高棉文过 64 个码位的句子进测试。
3. **不是 NFC 的正文按它的 NFC 读**（A-M4，A 的 (b)）：复查、摘要的切与命中的位置都取 `normalize(content, NFC)`，是 NFC 的（常见的）只多一次检查；存的正文不动。分解的越南文与谚文字母的正文，排队时与 `Drain` 之后各测。
4. **回到 3.3 的按词的规则**（A-M2，偏离 8）：只有一个有键的段、是一个汉字的词只搜标题；几个被隔开的单字的词（`中·国`、`タ・ネ`）只给标题的键，在名称或正文里复查；整个查询都没有正文的键时，这样的词才是正文层的 `title_keys`（只在名称里找），写进契约与 4.12。
5. **`page_search_hits` 的 `work_mem` 64 MB**（C-M3）：在 `00040_page_search.sql` 里就地改（迁移没有发布过），加测试核对函数带它。
6. **启动时丢掉留在运行中的任务**（B-I1）：只在 `serve` 启动时、River 的定时任务开始之前，丢掉这种任务留在 `running` 的行（v0.1 只跑一个服务，注释写明）；CLI 的 `reindex`、`migrate` 可以在活着的服务旁执行，从不丢。`MaxAttempts: 1`，同 transfer 的任务。整个程序的测试复现 B 的场景，启动之后任务再次运行。
7. **任务在它取锁的连接上跑**（B-M4）：推荐的做法，一个连接，锁就是运行自己的（B-S3 随之）；不是小改动时才在 `validate.go` 的规则里给搜索的任务算两个连接。规则与它的测试都算上搜索的任务。
8. **这一轮不做**（移交 M12，或随合并写进文档）：`page_search` 的笔记本的列（未决项 9）、跨工作区的计时（C-S1）、并集的溢出（C-S2）、WAL 与磁盘（B-M2，README 随合并）、`TitleKey` 对切罗基文不幂等（在 P5A 之外）、`3月15日` 一类的日期的查询是走查的类（A 的存疑）、300 ms 的尾巴（接受，M12）、autovacuum 与任务的 `ANALYZE`（B-S2）、大量 WAL 下提交的超时（B-S1，幂等）。
9. **按 NFC 读的代价**（修复之后定）：`IS NFC NORMALIZED` 按字符算，一个 4 KB 的正文中文约 19 µs、中英各半约 28 µs、英文约 34 µs，是读它的几倍（实施者：1 万个 4 KB 的正文、15 次取最小，读与长度 4.4 µs，带 `CASE` 24.2 µs，检查本身 21.5 µs，正则约 2 µs；修复核对第一轮按文字量：8 KB 的正文 2,000 个、9 次取最小，中文 37.5 µs、中英各半 54.5 µs、英文 67.1 µs）；30 万页的语料（平均 7.95 KB 一页）上走查 500 页约多 20–35 ms（主持者起初写的 10–20 ms 偏低，修复核对第一轮改正；决定不变：`A股`（全部）第三页无统计的 p99 282.5 ms 会过 300 ms，在已接受的尾巴之内）；守卫的语料上走查正文的读至多慢到约 2 倍（`中国 database` 第一页 24–30 → 37–43 ms，`theirs` 第一页 21–28 → 34–40 ms），其余的约不变；实施者那时的比较（`0b2f2ba4` 对修复一轮）还含短的走查之后的取样，`latency`、`go` 的第一页与 8 个常见的词多出的大半是取样的（8 个常见的词 28–35 → 53–61 ms，修复二轮撤回取样之后又是 28–35 ms）。为了对，照现在做的留着；量过的更便宜的两种移交 M12：正则的预检（`raw !~ '[…]' OR raw IS NFC NORMALIZED`，类取自 x/text、2,177 个字符 295 个区间，7.4 对 19.8 µs，约便宜六成，印地文、泰文与分解的正文仍走完整的检查），任务在它读的版本上存下 NFC 的标记（约一次按键的读，要一列与一次连接，排队的仍要检查）。
10. **计数的取样**（修复核对第一轮之后定，取代修复之后对它的代价的接受）：修复一轮的取样让走查停在 100 个之前的第一页多一次 `SearchBodies`，实施者在守卫的语料上量得多 5–9 ms（`latency`、`go`）与 20–30 ms（8 个常见的词），主持者先接受了；修复核对第一轮 I-1 量出它在 30 万页上约多 160–250 ms（`参考文献`（全部）第一页无统计的 p50 从 258 到约 420 ms，过了 300 ms），答复却不变。所以取样回到只在第一页的走查没有跑时做；走查因页满停在第 k 个通过（查了 n 个、第 n 个通过）时比例取无偏的 (k−1)/(n−1)；停在走查的界线时照旧 k/n；走到候选的末尾时正文层是准确的；通过的少于 2 个而还有没查的时照旧 `at_least max(n0, 这一页的个数)`（k = 1 时比例为 0，正是下界；决定 13 把这里的"通过的"改为比例依据的通过）。代码的注释写明为什么短的走查之后不取样。
11. **运行的连接断了**（修复核对第一轮 M-1）：一个节点的事务开始不了时，错误属于这次运行而不属于节点：`write` 交回它，不逐个记"没写"，运行以一个错误结束；节点留在队列里，下一次运行在新的连接上接着做。实施取标记的做法：平台的 `TxManager` 在开始事务失败时交回带 `TxNotBegun()` 的错误（文字不变、拆得出原因），`shared.TxNotBegun` 隔着包装认出它，两边都不互相引用；修复三轮让运行的错误同时带着这一批的写的失败（修复核对第二轮 N2-1）。
12. **契约与细节**（修复核对第一轮 M-2、N-1–N-7）：照核对者给的文字改契约：后台的恢复与撤销的节点同导入，任务建好之后才找得到、其间 `building`（`searchWorkspace` 与 `building` 的说明）；摘要是正文的写法、不是 NFC 的组成 NFC；`at_least` 加候选多得数不完时向下取整的估计；单独的情形的用词含组合记号；`config.yaml` 的注释算上搜索的任务；`validate.go` 的消息不说负的"至多"；00040 的三处旧注释；反引号也结束 `data:` 串。分词没有发布过，版本仍是 2。
13. **`at_least` 的门槛数比例自己的通过**（修复核对第二轮 F-1，取不加读的改法）：走查因页满停在第 k 个通过时比例依据 k − 1 个通过，k = 2 时只有一个，正是 A-M5 拒绝的精度（核对者的模拟：页满停下、要 2 个通过时 51–71% 在真的 2 倍之内，要 3 个时 69–89%）。所以门槛数比例自己的通过，这时答 `at_least max(n0, 这一页的个数)`，值仍是已见的命中（页满的最后一个是命中，不是取的样）；只改 `EstimateCount` 的一行。另外四条细节照核对者的建议改：运行的错误带着这一批的失败、连接池的消息先说 worker 的数、页满而走完只查了一个候选的一例进测试、422 的用词含组合记号。
