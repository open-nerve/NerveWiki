## 1. 目标

1. **版本**：一页的正文版本可以列出、查看（只读的阅读视图）、与上一版或当前比较，还原到任意一个版本；还原是一次新的写，产生新的变更集。
2. **日志与整组撤销**：笔记本的变更集按时间列出，可按人、客户端、页面筛选（M9 的 `log` 用同一个用例）；每个变更集看得到它改了哪些节点、怎么改的；整个变更集可以撤销，前提是其中每个节点的当前状态仍是它写出的，否则整体拒绝并列出冲突的节点（总体设计 3.8）。连续的撤销（从新到旧逐个撤销、撤销之后再撤销这次撤销）都成立，M11 的回滚靠它。
3. **回收站**：删除的子树进笔记本的回收站，列出、预览、恢复；原父节点在回收站里或放回去会太深时放到根下，标题冲突时加序号；清理期之后不能再恢复（总体设计 3.10）。恢复带回正文、历史、附件的行与链接索引（M6、M7 的移交）。
4. **大的恢复与撤销**：超过一个写入单元的恢复与撤销（大的子树、一次几万个节点的导入）作为后台任务分批完成，有进度与报告（M7 的移交第 4 项）。
5. **搜索**：在工作区里按标题与正文搜索，中文可用，只列出调用者看得到的笔记本里活着的页与附件，正文命中给出摘要片段；方案经真实中文语料的实测定下（M0/P1 的移交）。
6. **接到后面的 M**：日志、撤销与搜索的用例可由 M9 的 MCP 适配器直接调用；写入守卫看得到一个单元是不是撤销（M10 的来源区、M11 的冻结与回滚）。

## 2. 范围

**做**：

- page 模块：版本的读（列表、内容、阅读视图）；还原版本（类型 `version_restore`）；回收站的列表、单项与恢复（类型 `trash_restore`，操作 `OpRestore`）；变更集的日志、单个变更集与变更的明细；整组撤销（类型 `revert`，记下撤销的是哪一个）；给 transfer 的分批恢复与分批撤销；清理截掉的变更集的标记；恢复的期限；搜索的索引与用例；迁移（第 4.2 节）。
- asset 模块：恢复节点时恢复附件的行（观察者，同一事务）；给 page 的附件信息的读（类型与大小，含已删的）。
- linking：恢复的页经观察者进索引（与新建相同）；回收站里的页渲染时按它原来的路径解析链接。
- transfer 模块：后台任务的两种新类型 `trash_restore`、`revert`，沿用导入的分批、预算、心跳、取消与报告；导入的任务记下它的变更集。
- notebook、workspace 模块：给 page 的"看得到的笔记本"与"按 slug 找工作区"（工作区搜索），只接线。
- 平台：`jobs.purge_retention` 的下限改为 1 天；`InstanceInfo.trash_retention_seconds`。
- 前端：右栏"页面信息"的版本列表；版本页（阅读、比较、还原）；Web Worker 里有上限的按行比较（M4 的冲突对比一并改用它）；笔记本的历史页与单个变更集页（日志、明细、撤销）；回收站页与预览；工作区的搜索框与结果页；页面树在任何恢复之后重新显示；删除页面与附件的确认框写明回收站。

**不做**：

- 版本的保留策略、合并或删除单个版本（总体设计 1.2：留给 v0.2）；永久删除回收站里的一项、清空回收站：只由清理任务清除（第 11 节第 1 条）。
- 编辑会话之内的中间版本：一次会话每页一个版本（M4 的决定），自动保存的中间状态没有存；版本列表写明"一次编辑一个版本"。
- 任意两个版本之间的比较：只与上一版、与当前比较。
- 从一个被删的子树里只恢复其中一页：恢复的单位是回收站的一项（同一次删除的子树）。
- 附件的版本（M7：附件写入之后不变）。
- 撤销笔记本、工作区的删除：它们不是写入单元，没有变更集；删除笔记本的确认框已写明无法撤销。
- 搜索的相关度排序、分词、拼音、模糊匹配、繁简互通、不区分重音；搜索附件的内容；正则搜索（M9 的 `grep` 在 M9 做，用 M8 的索引）；跨工作区的搜索；搜索的并发上限（M12 压测之后再看）。
- 历史与搜索的实时推送：列表随 `pages` 事件按间隔重读，不加新的事件类型；搜索的结果页除外：不随事件、焦点、重连重读，再提交时读（4.13）。

## 3. 完成标准

总体设计 12.5 的通用标准之外：

1. **版本**：一页的版本按版本号倒序分页，每个版本带变更集的类型、客户端、执行者（显示名）与时刻；版本的正文与只读的阅读视图（链接按当前的树解析，回收站里的页按它原来的路径解析）；回收站里的页同样读得到；编辑会话进行中的那一行按它当前的版本号答出；比较在 Web Worker 里、有时间与大小的上限，超过时给出摘要并说明。接口给出两个版本的原样正文，比较的结果在网页上（总体设计 12.5"接口能做页面能做的"的例外：比较只是展示，正文都经接口读得到）。
2. **还原版本**：以 `base_revision` 防覆盖，经编辑锁（有人编辑、包括自己在别处编辑时 409 `page.locked`），产生类型 `version_restore` 的变更集；与当前相同时不写并说明。
3. **日志与撤销**：日志按变更集的创建时刻倒序分页，按人、客户端、页面筛选；单个变更集与它的明细（按节点分页）。撤销的表格测试覆盖每种条目（页面与附件的新建、删除、恢复、改名、移动、重新排序、写正文、还原版本、撤销）与每种冲突（之后又改过、标题被占、父节点不在、太深、成环、新建或恢复的节点下有别的变更集放进的节点、已被清理截掉、超过恢复的期限、页被锁、太大）；冲突整体拒绝、列出冲突的节点（至多 100 个与总数），什么都不写；性质测试：随机的操作序列之后从新到旧连续撤销 k 个变更集，树、正文与链接索引等于这 k 个之前的状态；撤销之后 `checkLinks` 成立，`links` 事件到达。
4. **回收站**：列出被删除子树的根（分页），带原位置、删除者与时刻、可恢复的期限、子树里页与附件的数目、恢复之后会放到哪里；预览页的只读视图与附件的信息；恢复带回正文、版本、条目、附件的行（之后照常下载，无主列表的大小算上它们）与链接索引；父节点在回收站、太深时放到根下，标题冲突加序号；超过期限答 409；不变式 `checkPages` 加上"活着的节点，它的正文、版本、条目都活着"。
5. **后台的恢复与撤销**：超过一个单元的恢复与撤销分批完成、并入一个变更集，每批在锁下重新核对，途中停下时报告已完成的部分与原因；一次在上限之内的导入可以撤销（按变更集的条目数：5 万个 zip 条目，路径隐含的文件夹也各是一页，至多约 55 万个条目；`MaxJobItems` 实测为 60,000，所以导入另有与它相同的节点上限，条目加路径隐含的文件夹超过它时整包失败 `too_many_nodes`，[P4](04-P4-background.md) 2.2、3.11）。
6. **搜索**：第 4.12 节的方案在实测的语料规模下达到它的目标（[P5](05-P5-search.md) 3.9 的表：各类查询第一页与"更多"的 p99、建索引时与积压时的同上、索引体积、任务的吞吐与从空建完的时间、保存时多出的开销、计数的误差）；只列出调用者看得到的笔记本（"列表的结果"等于"逐项判定读取"的集成测试）与活着的节点（用户的写：删除之后立即消失、恢复之后立即回来）；增量维护的索引等于重建（13.4 第 10 条），复查蕴含索引的键（P5 3.3 的例外之外）；附件只按名称列出；摘要片段与高亮的位置；`q` 的上限与转义。P5A 的结果（P5 3.9）：体积、任务的吞吐与从空建完的时间、保存时多出的开销达标，计数在第一页 92 格里 84 格合规则（8 格是走查用完的类，照 P5 3.5 的规则）；第一页与"更多"的 p99 在 30 万页上三个阶段各 204 格里 3、9、14 格过 300 ms（至多 719 ms），建索引时、待处理列表满、准确的积压与导入的清空期间更多（至多约 1.2 秒），都是重的类：主持者接受、移交 M12，负责人可以改判。可见性的集成测试、增量等于重建、复查蕴含键（P5 3.3 的例外之外）、删除与恢复立即反映、上限与转义各有测试。
7. **并发与权限**：4.14 的交错各有确定性的测试，结束时核对不变式（`checkPages`、`checkLinks`、`checkAssets`）；权限矩阵覆盖新操作的每一格。
8. **最后一跳**（总体设计 13.1 第 21 条）：恢复经观察者带回附件的行与索引、搜索经端口得到看得到的笔记本、transfer 的任务经 `TreeWrites` 到达 page 的写，组合根交空时整个程序上的测试失败。
9. **前端**：版本列表、版本页、比较（上限处的测试）、历史页、回收站页、搜索各有 vitest，经组合根到达；e2e 的 HI、TB、SE 系列故事（第 9 节）通过；搜索框的输入法一步加进人工清单（负责人在 v0.1 的最后统一验收）。

## 4. 关键决定

### 4.1 模块、端口与构建次序

| 项 | 决定 | 放弃的方案 |
|---|---|---|
| 归属 | 版本、日志、撤销、回收站、搜索都在 page 模块：读写的都是 page 的表；搜索的索引迁移归 page（总体设计 7.2 末句） | 新的 `history`、`search` 模块：要经端口读 page 的全部表，跨模块的 SQL 不能 join，只多一层转发 |
| 看得到的笔记本 | notebook 已有的 `VisibleNotebooks.VisibleIn` 与 workspace 已有的 `workspace.NewWorkspaces` 由组合根交给 page：slug 经 page 的 `Workspaces` 端口加的 `FindBySlug` 得到工作区，角色取判定答的 `Grant.WorkspaceRole`（同 notebook 的 `ListNotebooks`），再经端口 `VisibleNotebooks` 得到看得到的笔记本；page 以 `notebook_id = ANY($ids)` 过滤（[P5](05-P5-search.md) 3.6） | page 自己判定每一本：越过模块的边界 |
| 显示名 | page 已有的 `Names` 端口；总体设计 6.1"内嵌账户资料"的例外加上版本、日志、回收站（与审计记录同理） | 只给 id：没有读别的用户的接口 |
| 附件的信息 | asset 给只凭连接池的读 `asset.NewAttachmentInfos(pool)`（类型、大小，按节点 id，含已删的），在 `page.New` 之前构建，经 `Deps` 交给 page（13.1 第 11 条：只凭连接池的构造）；不叫 `AssetMeta`：`page.AssetMeta` 已是守卫看到的新附件的文件 | page 读 `asset_blobs`：sqlc 按模块列迁移，越过边界 |
| 附件的行 | 恢复时由 asset 的观察者在同一事务里恢复（`asset/app/follow.go` 加 `NodesRestored`），与删除对称；观察者从 `Change.Restored` 认出恢复（新建的附件节点同样没有"前"，它的行由单元写）；`Restored` 带删除的时刻与是否附件：asset 按同一时刻恢复行，并核对行数 | 恢复的用例直接写 `asset_blobs` |
| 链接索引 | 恢复的页与新建一样：变更带 `Revision` 与 `Facts`，linking 的观察者 `ReplacePage` 并重新解析受影响的键（M6 的移交第 1、2 项）；`Relocation` 要求"前"不空，恢复不触发改写的参与者 | 回收站里保留索引行：所有的索引读都要排除回收站里的来源 |
| 回收站里的页的链接 | 渲染时来源页的路径照它被删时的位置读（经已删的祖先）；候选的目标仍只有活着的节点。渲染路径带"来源在回收站里"（`PageRef.Deleted` → `markdown.Page.Deleted` → linking 的 `Page.Deleted`），linking 的视图这时经新的端口 `Pages.SourcePath` 读来源的路径；索引的维护不变。所以链到同一次删除的页的链接，预览里可能解析到别处同名的活着的页或不解析，恢复之后才回到组里的页 | 照现在：来源已删时每条链接都成了未解析（A-M5、B-I2） |
| 大的恢复与撤销 | page 在一个单元之内完成时直接答；超过（4.9）时答 422 `page.restore_too_large`、`page.revert_too_large`，网页再请 transfer 开后台任务（`startTrashRestore`、`startRevert`），任务经 `TreeWrites` 的核对、计划与 `RunBatch` 分批写回到 page。依赖仍是 transfer → page | page 直接开 transfer 的任务：构建次序是 page → asset → transfer（transfer 要 `TreeWrites()`），page 反过来依赖 transfer 造不出来（C-I1、A-I4） |
| 守卫看得到撤销 | `Write`（守卫与观察者都看得到）加上单元的 `Kind` 与 `RevertsID` | 守卫只看操作：撤销与普通的写分不开，M10 的来源区、M11 的冻结都要分开它们（A-M13、C-M10） |

page 的新用例：读 `ListVersions`、`GetVersion`、`GetVersionView`、`ListChangesets`、`GetChangeset`、`ListChanges`、`ListTrash`、`GetTrashItem`、`Search`；写 `RestoreVersion`、`RestoreNode`、`RevertChangeset`；给 transfer 的 `TreeWrites` 加 `CheckRestore`、`PlanRestore`、`CheckRevert`、`PlanRevert`、`RunBatch`（请求里的核对与任务开始时的计划未加锁，每批一个单元，[P4](04-P4-background.md) 3.3）。

`Deps` 加：`VisibleNotebooks`（交空时 `page.New` panic）、`Attachments`（端口 `AttachmentInfos`）；`Retention`（配置值 `jobs.purge_retention`）；`SearchInterval`（配置值 `page.search_index_interval`）；`Snapshots`（搜索的只读快照，P5A）。

### 4.2 数据：迁移

page 的（搜索的见 4.12）：

| 表 | 改动 | 为什么 |
|---|---|---|
| `changesets` | `kind` 加 `version_restore`、`trash_restore`、`revert`；加 `reverts_id uuid`（不建外键；`CHECK ((kind = 'revert') = (reverts_id IS NOT NULL))`）；加 `trimmed boolean NOT NULL DEFAULT false` | 3.8 的类型；撤销记下撤销的是哪一个；外键会让清理器的先后受制于被撤销的变更集 |
| `changesets` | 索引 `(notebook_id, created_at DESC, id DESC)`（日志；不带 `WHERE`：`notebooks` 的清理删行时外键 `RESTRICT` 的核对只按 `notebook_id` 找 `changesets`，部分索引用不上它，同一个索引两用）、`(notebook_id, created_by_id, created_at DESC, id DESC) WHERE deleted_at IS NULL`（按人筛选，M9 的 `log`）、`(id) WHERE trimmed`（空变更集的清理）、`(reverts_id) WHERE reverts_id IS NOT NULL`（日志的 `reverted_by`、撤销之前的"已被撤销过"，P3 建，M8/P1 审查 C3）；`changesets_notebook_id_idx` 去掉（核对过：别的用法 `DeleteNotebooksPages`、`NotebookActivities` 以 `notebook_id = ANY(…) AND deleted_at IS NULL` 读，前缀相同；[P3](03-P3-log-revert.md) 2.1 第 4 条） | 13.1 第 27 条：与次序相同的索引；按客户端筛选在日志的索引上过滤（取值很少），计划测试核对 |
| `changeset_items` | 加 `restored boolean NOT NULL DEFAULT false` 与 `revision integer`；`CHECK`：`restored` 只在"前"为空、"后"不空时可以有值，`revision` 只在"前"或"后"为空（新建、恢复与删除）的条目上，`revision >= 1`；迁移给已有的页面新建条目补上 `revision = 1`（同一变更集里这一页有创建的版本行时；运行时同样记 1）；删除的条目记删除时页的版本号（P3 的 00038，补值给删除之后一直在回收站里的）；条目合并时 `restored` 保留第一次的，`revision` 合并成删除时取删除的、否则保留第一次的 | 恢复与新建都没有"前"：日志、撤销与观察者要分开它们；撤销一次恢复要知道恢复时的版本（恢复不写版本行）；撤销一次删除要比回收站里的正文（[P3](03-P3-log-revert.md) 2.1 第 1 条） |
| `page_revisions` | 唯一索引 `(node_id, revision)`，去掉被它覆盖的 `page_revisions_node_id_idx` | 按版本号寻址与倒序列出；钉住"一页的每个版本号至多一行" |
| `nodes` | 加 `trash_root boolean NOT NULL DEFAULT false`（`CHECK (NOT trash_root OR deleted_at IS NOT NULL)`）与这一组的统计 `trash_pages`、`trash_assets`、`trash_height`（只在根上，删除时记下；`CHECK` 有统计 ⇔ 是根）；部分索引 `(notebook_id, deleted_at DESC, id DESC) WHERE trash_root`；迁移按"父节点为空或父节点的 `deleted_at IS DISTINCT FROM` 它的、且不是随笔记本删除的"补上已有的根与统计：随笔记本删除的以"同一时刻删除的变更集"认出（笔记本的删除给它的变更集与节点同一个时刻，子树的删除不删变更集），不读 notebook 的表 | 回收站的一页只读根，不读过一次删除里的几万个节点（A-M9）；统计让列表不为每一项数整组，恢复在读组之前就能答 422 |

transfer 的：`transfer_jobs.kind` 加 `trash_restore`、`revert`；加 `changeset_id uuid`（导入、恢复、撤销写入的变更集，建行时定下，任务第一个写了东西的单元以这个 id 建它）；撤销任务另有它撤销的变更集，放在 `root_id` 之外的新列 `target_changeset_id`，与它的说明 `message`；删掉 `transfer_jobs_importing_key`，建 `transfer_jobs_writing_key` 覆盖 `import`、`trash_restore`、`revert`（一本笔记本同时一个写入的任务，[P4](04-P4-background.md) 3.2）。

**`trash_root` 的维护**：删除一个子树时它的根设上并记下统计，同一时刻删除的子孙不设；一个单元从上往下删，每棵子树一次：同一单元里先删子孙、再删它的祖先，子孙会留着根的标记，`DeleteNodes` 拒绝（调用者的缺陷）；恢复的节点取消并清掉统计；分批恢复途中，父节点已恢复而自己仍在回收站的节点设上并记统计（停下时它们各自列出）；笔记本删除不设（回收站只列活着的笔记本）。

**清理截掉的变更集**：清理器只删已删节点的行，所以活着的笔记本里的一个变更集，只有它碰过、后来被删除并过了保留期的节点的条目与版本会被删。被截掉一部分的变更集不能再整组撤销。`changeset_items` 与 `page_revisions` 的清理语句改为：以 `FOR UPDATE OF i SKIP LOCKED` 与 `FOR NO KEY UPDATE OF c SKIP LOCKED` 同时锁住要删的行与它所属的变更集（拿不到的下次再删，清理从不等待，13.1 第 5 条），删掉这些行并给活着的笔记本里的这些变更集设上 `trimmed`，答删掉的行数（`:execrows` 照旧给分批的循环用，A-M2）：标记与删除在一条语句里，删除在最外层（`:execrows` 数的是它），标记在数据修改的 CTE 里。`changesets` 的清理器在删完随笔记本删除的之后，接着删活着的笔记本里 `trimmed` 而条目与版本都已删光的（标记之后笔记本被删的，等笔记本的保留期，P3A 审查 A-6）。撤销先读条目、后读 `trimmed`（READ COMMITTED 下，条目的读看得到的清理，之后的读也看得到它的标记，A-M3）。P1 只加了列，标记与清理语句的改写一起在 P3 做；v0.1 之前没有发布的实例，所以不补记 P3 之前的清理截掉过的变更集（M8/P1 审查 C2）。

### 4.3 版本：列表、查看、比较

- **版本就是 `page_revisions` 的一行**，以它写出的版本号寻址：`/pages/{page_id}/versions/{revision}`。编辑会话的一行覆盖 `(base_revision, revision]`，会话每次保存都改这一行的版本号：请求的版本号落在某一行的区间里时答那一行（带它真实的版本号，网页随之替换地址），不在任何一行里答 404 `page.version_not_found`。
- **列表**：一页的版本按 `revision` 倒序，游标是版本号，不读正文；每项带行的 id（网页以它为键）、`base_revision`、字节数、写出的时刻（行的 `updated_at`）与变更集（id、类型、客户端、执行者的 id 与显示名、创建的时刻）。最新的一行若属于活着的编辑会话，标出"编辑中"。不列树的变化（改名、移动在日志里）。
- **正文**：原样的正文（至多 5 MiB），供比较与复制。
- **阅读视图**：照 `getPageView` 的形状与渲染路径（`PageRef{Revision}`），链接按当前的树即时解析（M6 4.7）；来源页在回收站里时按它原来的路径解析（4.1：候选仍只有活着的节点，链到同一次删除的页要恢复之后才回到组里的页）。网页上只读：没有任务复选框的勾选、没有"新建这一页"。
- **回收站里的页**同样读得到（M4 的移交第 2 项），权限与活着的页相同。
- **比较在网页上**：`@codemirror/merge` 默认的设置（`scanLimit` 500）会把超过约 16,000 个码元的改动合成一整块，`timeout` 又管不住它的全部算法（B-I1 的实测：3 万字的页改 8 个词显示为整页删除再插入；20 万字的重复行 90 秒算不完）。所以：
  - 按行比较（行的哈希上的 Myers）放在 Web Worker 里（小的文字在主线程上同步比较），硬性的期限（2 秒）一到就终止它；每个视图同一时刻至多一个比较；结果经 `diffConfig.override` 交给只读的统一视图，一处改动的范围小时才在行内细分，细分与合并都在 Worker 里做完（P1B 的审查：留给主线程的合并是平方的）。
  - 上限：改动的行数、字节数与期限。超过时显示"+a −b 行，太大，不能逐行比较"，两个版本以只读的编辑器并排显示（不标逐行的改动）。
  - 删除的大段不作为一整块 DOM 插入（超过上限时走并排）。
  - 只差换行或 BOM 时说明"只差换行或 BOM"（比较对换行做了规整）。
  - 无障碍：改动不只靠颜色（加 +/− 标记与删除线）、"N 处改动"的摘要、"上一处、下一处"的按钮，三种显示是有名称的一组标签页。
  - M4 的冲突对比（`ConflictDiff`）改用同一个比较，有同样的问题（13.2 第 25 条）。
- 服务端不做比较（不加 diff 的依赖）。

### 4.4 还原版本

- `POST /pages/{page_id}/versions/{revision}/restore`，请求体 `{base_revision}`。网页的确认框显示"当前 → 这个版本"的比较（读当前的正文），`base_revision` 就是这次读到的版本号；不一致答 409 `page.revision_mismatch`，网页重读当前、刷新比较、确认框留着并说明变了（不自动重发，13.2 第 7 条）。
- 一次正文的写：新的变更集，类型 `version_restore`；单元之前按 `Take` 取预算解析（13.1 第 19 条）；经写入守卫：这一页有活着的编辑会话时 409 `page.locked`（调用者自己在别处编辑同样被拒，总体设计 3.9）；与当前正文相同时不写，答当前的版本号与"未改动"，网页说明"与当前相同，没有改动"。
- 答复：新的版本号与变更集的 id（不回传正文）。网页回到页面，焦点在标题，状态行"已还原到版本 N"。
- 回收站里的页：404 `page.not_found`（先从回收站恢复）；网页上不显示"还原"。
- 权限：写者。

### 4.5 回收站：列表与预览

- `GET /notebooks/{notebook_id}/trash`：`trash_root` 的节点，按 `deleted_at` 倒序、id 倒序分页，只列期限之内的（4.11）。
- 每项：节点（id、类型、名称）；原位置（祖先的名称，读已删的祖先）；删除者（`nodes.updated_by_id`，删除时写的）与显示名；删除的时刻；`restorable_until`（删除时刻加保留期减 1 小时，4.11）；这一组里的页数与附件数（删除时记下的准确值，4.2）；恢复之后会放到哪里（原父节点，或根下，以及原因）。
- `GET /nodes/{node_id}/trash-item`：单项（同上，另带 `notebook_id`、页的正文的版本号 `revision`、附件的类型与大小），预览页用；码是恢复的 409 里的三种（`page.not_in_trash`、`page.not_trash_root`、`page.restore_expired`）。
- **预览**在回收站自己的路由里（`/:slug/notebooks/:id/trash/:nodeId`），不在页面的外壳里（外壳对不在树里的页答 404）：只显示根，页显示它当前版本的只读阅读视图（4.3，以单项的 `revision` 读），附件显示名称、类型与大小（4.1 的附件信息），不签发下载地址；组里的其余只给数目。
- 能读这本笔记本的人都看得到回收站与预览；恢复要写者。

### 4.6 从回收站恢复（一个单元）

- `POST /nodes/{node_id}/restore`：恢复一个回收站的根与同一时刻删除的子孙。节点活着答 409 `page.not_in_trash`；在回收站但不是根答 409 `page.not_trash_root`，扩展成员 `root_id`（写进契约，13.1 第 8 条）；超过期限答 409 `page.restore_expired`；超过一个单元（4.9）答 422 `page.restore_too_large`。
- **放在哪里**：父节点活着、且放回去不超过 10 层时放回原父节点下（原来在根下的回到根下），次序值用它原来的（删除时保留，插在兄弟之间）；父节点在回收站里、或会超过 10 层时放到根下的末尾。父节点不会"不在"：父节点的外键是 `ON DELETE RESTRICT`，清理只删叶子。标题与活着的兄弟冲突时加序号（`page/domain.Numbered`，附件加在扩展名之前，同导入的 `children.free`）。一个单元恢复整组，与活着的兄弟冲突的只有根（它的子孙的兄弟要么一起恢复，要么仍在回收站）。重算 `name_key`（`reindex` 只重算活着的节点）；组内同一父节点下重算之后键相同的（Unicode 数据升级之后的 `reindex` 才有），先到的留名，后到的同样加序号：答 409 会让这一项永远恢复不了。
- **单元**：树的写入单元（`Tree: true`），操作 `OpRestore`，新的变更集，类型 `trash_restore`。每个恢复的节点一项变更：没有"前"、"后"是恢复后的状态、页面带当前的 `Revision` 与 `Facts`、`Restored`（删除的时刻与是否附件；`Change.Then` 合并时保留第一项的，与"前"同出于第一项）。条目照新建写，另记 `restored` 与页的 `revision`。在锁下清空这一组的 `deleted_at`（`nodes`、`page_contents`，以及这些节点在所有变更集里 `deleted_at` 等于这一时刻的版本与条目，包括删除它们的变更集的条目），取消 `trash_root`，根的父节点、名称与次序照上面，`updated_by_id`、`updated_at` 记恢复者与时刻。
- **核对**：在锁下核对这一组仍是同一时刻删除、每页的版本号未变（否则 409 `page.trash_changed`）；页的正文行与节点数相符，每页的版本行从创建起连成链（清理先删条目、版本，后删正文：缺了说明被清理过，答 409 `page.trash_changed`，作为期限之外的防线，A-M6）。防线之外的两种不检测：被清理拿走的条目、附件的清理删了文件却提交失败留下的行（只在下载时发现）；两者都要清理的时钟比恢复的快一小时以上。
- **解析在单元之前**：未加锁地读出这一组的正文，按大小从大到小、按 `Take` 取预算解析（总体设计 4.3、13.1 第 19 条；M7 设计审查 A-I2 去掉了锁下的 `TakeNow`，M6 的移交第 1 项写的 `TakeNow` 照此改；从大到小，后面的小页总拿得到预算）。各次 `Take` 的等待合计至多 `page.parse_max_wait`，用完答 503（每次等 2 秒，100 页会超过 15 秒的请求期限）。
- **观察者**：linking 为每页建索引、重新解析受影响的键；asset 恢复附件的行，行数与附件节点数不符时让单元失败，答 409 `page.trash_changed`（组合根把 asset 的计数换成 page 的码）；`pages` 事件照常（树变了）。
- 权限：写者（与删除相同）。

### 4.7 日志

- `GET /notebooks/{notebook_id}/changesets`：按 `created_at` 倒序、id 倒序（`created_at` 是第一次写入的时刻，不随会话的后续保存与导入的后续批次移动），游标 `[created_at, id]`。筛选：`actor`（账户 id）、`client`（`web`、`api`、`cli`、某个 `mcp:<名>`，或 `mcp` 表示全部 MCP 客户端）、`page_id`（碰过这一页的：它的条目或版本行所属的变更集；回收站里的页照列；不是这本笔记本的节点、含已被清理的，答 404 `page.not_found`，同 4.12 的约定与 `listAssets` 的 `parent_id`）。
- 每条：id、类型、客户端、执行者（id、显示名）、创建与最后写入的时刻、说明（`message`）、撤销的是哪一个（`reverts`：id、类型、执行者、时刻；被撤销的那一个已被清理时为空，那时撤销自己也只剩空壳）、被哪些撤销过（`reverted_by`：id 的列表，至多 100 个、新的在前）、是否被截掉（`trimmed`）、节点数（`node_count`：条目，即树的变化）与正文数（`content_count`：版本行，即写了正文的页；各数到 1,000 为止，"1,000 表示这么多或更多"，同反链的计数）、前三项变更（节点名称与变化，按节点 id）。
- `GET /changesets/{changeset_id}`：单个变更集，形状同上，另带 `renames`、`moves`（前 1,000 项条目里有没有改名、移动：撤销的确认框据此提示链接不跟着改回，冲突里据此给"改回原名"；只在这里算，日志的每条不带：一页 100 个大的变更集要读约 10 万行条目）。导入任务的"在历史里查看"、撤销的"撤销了…"都读它。
- `GET /changesets/{changeset_id}/changes`：按节点 id 分页：节点（id、类型、现在的名称、是否活着）；变化（新建、恢复、删除、改名、移动、仅次序，可兼有正文）；前后的父节点（id 与名称：已删的照读，已清理的名称为空）与名称；正文前后的版本号（链到版本页的比较）。
- 权限：能读这本笔记本的人（读者能读页面就能读它的历史）。

### 4.8 整组撤销

`POST /changesets/{changeset_id}/revert`（请求体可带 `message`，1–4,096 字节）：把变更集 C 碰过的每个节点恢复到 C 之前的状态，产生类型 `revert`、`reverts_id = C` 的新变更集 R。

**"当前状态仍是 C 写出的"按状态比较**，不按版本号或"之后有没有别的条目"：

- 树：活着与否、父节点、名称（原样的字符串）、次序值，都等于 C 的"后"。C 删除的节点不比删除的时刻：它们仍在回收站里，每个最上层（"前"的父节点不是 C 删除的节点）各是一项的根，它的组恰是 C 删除的、它之下的节点，组里的每个节点（最上层也是）在 C 删除它时的父节点、名称与次序之下：这一项恢复之后、再删除之前的改名与移动是 `changed`，不被撤销悄悄改回（P3A 审查 A-1、C-M5）。例外：最上层现在的删除撤销了 C 留下的那一项的恢复，即撤销了 C 之后第一个把它带回来的变更集（从回收站恢复，或撤销里的恢复：恢复可能把这一项放到根下、加了序号，从新到旧撤销时那次恢复的撤销把它删在那里），这时只比它仍是根、组恰是 C 删除的节点，S\* 照 C 的"前"放回它；"C 之后"按条目自己的时刻（删除、恢复的条目各带它那一单元的时刻：后台的任务并入自己的变更集，后面的批在之后的时刻写，变更集却建在第一批，[P4](04-P4-background.md) 3.7），同 4.11 假设时钟不往回走（[P3](03-P3-log-revert.md) 3.5）。撤销一次恢复会以撤销的时刻把这一组再删一次（回收站里的项不改名、不移动，不能"放回"原来那一项），按时刻比较时"撤销这次恢复、再撤销更早的那次删除"永远冲突，第 1 节目标 2 与第 9 节的性质测试都做不到（[P3](03-P3-log-revert.md) 2.1 第 1 条、3.5）。
- 正文：当前的 `content_hash` 等于 C 留下的正文的哈希：C 有这一页的版本行时取它的；C 只是恢复了这一页时取条目记下的 `revision` 那一行的；C 删除的页比回收站里的正文：它的版本号那一行的哈希等于删除的条目记下的 `revision` 那一行的（附件没有正文，不比；没有 `revision` 的旧条目算 `changed`）。
- 按状态而不按版本号，是因为撤销把旧的字节写成新的版本：按版本号，"撤销 C2 之后再撤销 C1"永远冲突（A-I1、C-I2）。次序值也按状态比：之后的重新排序改了它（冲突），之前的撤销照原值写回它（不冲突）；兄弟被重新编号（M4：间隔小于阈值时，不记条目）会改它而显示为冲突，罕见，写明；反过来，C 自己的放置重新编号了兄弟时，撤销照原值放回的节点相对兄弟的位置可能不同、不报冲突（P3A 审查 A 的存疑，没有复现），同样罕见。

**一次核对全部**：先算出目标状态 S\*（C 碰过的节点取 C 的"前"：新建的不再存在、改名移动的回到原处；删除的整组回来，每个节点回到 C 删除它时的父节点、名称与次序，不改放根下、不加序号，放不回就冲突（第 11 节第 6 条），用的是这一组现在的删除时刻；恢复的不再活着：撤销以它的时刻把它们从最上层删除，名称与位置是恢复之后的（序号、根下的位置留着），这一组在回收站里以撤销者、撤销的时刻列出，期限从撤销时算起（它是一次新的删除）；其余节点取当前的），对 S\* 一次核对，冲突全部列出（每项的名称是节点在 S\* 里的，`title_taken` 即被争的名称；S\* 里不在的是现在的）：

| 原因 | 什么时候 |
|---|---|
| `changed` | 节点的当前状态不是 C 写出的 |
| `parent_gone` | S\* 里一个活着的节点，它的父节点不在 S\* 里活着（已删、已清理） |
| `title_taken` | S\* 里同一父节点下两个活着的节点标题键相同：列出 C 的那个，另带占着名称的节点 `holder_id`（4.13 要链到它） |
| `too_deep` | S\* 里的层级超过 10 |
| `cycle` | S\* 里成环（C 之后有别人把原父节点移到了这个节点之下） |
| `children_added` | C 新建或恢复、S\* 里不存在的节点下有不在 C 里的活着的节点（撤销会把它们一起删掉）：列出的是之后放进去的那个节点 |
| `expired` | C 删除的节点已超过恢复的期限 |

有冲突时答 409 `page.revert_conflict`，扩展成员 `conflicts`（每项节点 id、名称、原因与 `title_taken` 的 `holder_id`，至多 100 项）与 `conflict_count`，什么都不写。另：C 被截掉过答 409 `page.changeset_trimmed`；超过一个单元答 422 `page.revert_too_large`（4.9）。

**单轮应用**：S\* 核对过之后，在一个单元里应用一轮，次序固定：放回（改名与移动改回，先移动后改名）→ 删除 C 新建的（只删 S\* 里最上层的，从上往下）→ 恢复 C 删除的各组 → 写回正文（C 的 `base_revision` 那一行的正文，按页 id；同一页的版本链连续）。`PlanRevert` 模拟这一轮，每一步的前提（父节点活着、名称空着、不成环）在它那一刻成立；不成立是缺陷（未分类的错误）。M8 的每个变更集只有一种操作（撤销是被撤销者的反面），一轮做完；之后发生的互换名称、移入新建的文件夹、删除再新建同名在 S\* 里是 `title_taken`、`children_added`，以冲突答出。推后、多轮与临时名称交给 M9 的 `batch`（[M8/P3 的移交](../M9-mcp/handoffs/M8-P3-revert.md)）：`MoveNode` 带着现在的名称移动会撞上兄弟的唯一索引，临时名称会超出 255 字节的名称界线、丢掉附件的扩展名，要在数据库上解决并测试（[P3 设计审查](reviews/P3-design-review.md) A-M5；原来的写法见 A-I6、C-M9）。

- **不经改写的参与者**（`Options.UpdateLinks = false`）：C 若是改名、移动并改写了别的页的链接，那些正文的写就在 C 的版本行里，撤销逐字节写回，链接回到原样；再经参与者改写会改两次（M6 的移交第 4 项：定为不经参与者，因此不会答 `linking.pages_locked`）。代价：C 之后新写的、指向新名称的链接（在 C 没有改写过的页里）会断开或指向别处，与 M6"改名不改变链接的指向"不同，写进总体设计 4.5 与第 11 节第 4 条；撤销改名冲突时网页提示可以"改回原名"（普通的改名，会改写链接）。
- **锁**：撤销里的正文写、删除经编辑锁的守卫：有一页被人编辑就整个拒绝，答 409 `page.locked`，带第一页的持锁人（M5 的移交第 1 项；跳过被锁的页违反"整组"，不做）。
- **正在写入的变更集**：编辑会话的变更集被撤销之后，会话的下一次保存按现有的规则另起一个变更集（它的版本号已不是会话上次写的）；导入、恢复的任务还在并入的变更集被撤销之后（撤销又被撤销的也算），任务的下一批在 `Run` 加锁之后、做任何事之前锁住并核对要并入的变更集（`LockChangeset` 之下读得到 `reverts_id` 指向它的变更集；在第一次写时才核对，导入的下一批会先因父节点已被撤销删掉而以 `tree_changed` 停下，原因不对），答 page 的哨兵错误 `ErrChangesetReverted`；transfer 在 `Tree.Import` 与 `RunBatch` 的结果上接住它，算确定的拒绝（什么都没提交，这一批的文件删掉），任务以新的失败 `changeset_reverted` 停下并在报告里写明（transfer 契约的 `TransferFailure` 加这一项；C-M11、A-M12）。撤销的任务同样（P4）；只是撤销任务的变更集带着它删除的最上层时（例如撤销一次导入），在请求里撤销它常答 409：请求未加锁地解析之后、加锁之前，任务的下一批把更多删除并入它，锁下多出没有解析过的组，这些页列为 `changed`（[P3](03-P3-log-revert.md) 3.6 的规则），什么都不写、任务照常；先取消任务或等它结束，网页在冲突之前说明（[P4](04-P4-background.md) 3.5、3.10 第 6 条，P4A 审查 A-M2）。
- **撤销的撤销**：R 是普通的变更集，可以再撤销；从新到旧连续撤销同样成立（按状态比较）。
- **解析**：要写回的正文在单元之前按大小从大到小解析（同 4.6）。

### 4.9 大小：一个单元与后台任务的界线

恢复（4.6）与撤销（4.8）都在请求里一个单元完成，界线相同，量的是花时间与占预算的部分：

- 要解析的页：合计不超过 100 页（是页，附件计入树的操作）、8 MiB 正文，解析之后链接合计不超过 20,000 条（与导入的一批相同，13.1 第 31 条；8 MiB 正文留下的提取结果约 0.8 MiB，预算的下限 5 MiB 也容得下，A-I2、C-I4）。只有一页的组不受这三项限制：它曾在一个请求里写成（同导入的批"独自超过的一页单独成批"）。链接数要解析之后才知道，超过时的 422 可能排在 503 之后（4.14）。
- 树的操作（新建、删除、恢复、移动的节点，附件也算）：不超过一个实测的数 `domain.MaxUnitNodes` = 10,000（P2A 实测：满负载下单元至多约 2.7 秒，取不超过 5 秒的最大一档，在 15 秒的请求期限里留出余量，[02-P2](02-P2-trash.md) 3.11；删除与恢复用整组的语句、条目用 `INSERT … SELECT unnest`，不一个节点一条语句，M12 的移交第 4 项）；恢复按删除时记下的统计核对，不读组。
- 写回的历史（这一组以它的时刻删除的版本行与所有变更集里的条目）：不超过 `domain.MaxUnitHistory` = 400,000，同样实测（P2A 的审查 A-M4：节点数管不到每页几千个版本的组，那样的恢复在请求里超时或答 500）；只有一页也算。
- 撤销：树的操作数就是 C 的条目数（新建的被删、删除的回来、恢复的被删、改名与移动改回，各一个节点）；放回一个节点同 `Unit.Move`，子树里的节点各一项交给观察者，代价与子树成正比、不计入（原来的移动也是这样，撤销不比它多）；写回的历史是要恢复的各组的版本与条目；撤销里的删除与 `DeleteNode` 一样没有历史的界线（M12 的移交第 14 项）。撤销比恢复多读整本笔记本活着的树，P3A 实测（[P3](03-P3-log-revert.md) 3.11）：撤销一次满负载、一个最上层的删除（1 万个节点、40 万行历史）请求 3.3–3.8 秒，随 C 增长的部分至多约 3.5 秒，比它的恢复多 0.1–0.4 秒（两遍读 C、读树与 `PlanRevert`）；另有 10 万个节点的笔记本里读树与 `PlanRevert` 各 61–79 ms，用不到只读附近的节点（M12 的移交第 15 项）。所以撤销沿用 `MaxUnitNodes`、`MaxUnitHistory`。
- 撤销的单轮的步数（放回一个节点、删除一棵子树、恢复一组，各是一次单元的操作；写回正文由上面的页数与字节限住）：不超过 `domain.MaxRevertSteps` = 1,500，同样实测（P3A 审查 C-I2：一个最上层的基准量不到它；根下几千个最上层的导入，它的撤销与撤销它的撤销恢复几千组，在节点的界线之内超过 15 秒的期限、答 500，其间持着笔记本行）。最贵的是恢复很多组：1,500 组至多 4.8 秒，2,000 组 3.5–7.7 秒、有一次到了期限。时间比步数增长得快（每个最上层的删除读它的子树，没有统计时经整本笔记本的标题的部分索引；`DeleteNodes` 的 `stray`；每组读两遍组、一遍历史），一次删除多个最上层、一次恢复多组是 M12 的（移交第 15 项）。没量过：很多组又带满一个单元的节点与历史（估约 7 秒；多于 100 页的被页数挡住，很多组只能是附件的组）。未加锁时在计划之后、读正文与解析之前核对，锁下再核对（4.14）。

超过任何一项答 422 `page.restore_too_large` 或 `page.revert_too_large`；网页说明这次的大小，问是否在后台进行（4.10）。没有"撤销不设上限"的例外（超过界线的撤销在后台分批；一个最上层的子树在一个单元里删，同 `DeleteNode`，P4 在 `MaxJobItems` 处实测，A-I3、C-I3）。

后台的撤销（P4）：变更集至多 `domain.MaxJobItems` = 60,000 个条目，超过答 422，网页说连后台也撤销不了；请求与任务开始时各读一遍它的全部条目、节点、组与树，很多组按层一起读（每层一条语句，同步的撤销同样）。P4A 实测，规则同 `MaxUnitNodes`：满负载（2 KiB 正文、每页 20 条解析的链接、十分之一是附件，P4A 审查 C-I1）下最大的一步（深的导入的一个最上层的删除）每次运行都不超过 5 秒的最大一档：6 万处 3.5–4.6 秒，7 万处有一次 6.9 秒，8 万处 5.9–6.1 秒；6 万处一组的第一批至多 2.2 秒，请求至多约 1.2 秒（很多组的形状 0.74–0.84 秒，不另设 `MaxJobGroups`），计划至多几十 MiB。每页多于 20 条链接时最大的一步随链接增长约 1.6 µs 一条（40 条时 5.9 秒），同用户 `DeleteNode` 同一个最上层，接受：删除要读到达已删的页的链接，经这个单元刚删的每一条链接的索引项，没有便宜的改法（[P4](04-P4-background.md) 3.11）。6 万小于第 3 节第 5 条的 55 万：导入另有与它相同的节点上限（条目加路径隐含的文件夹，超过时整包失败 `too_many_nodes`，[P4](04-P4-background.md) 2.2 的 (a)），负责人可以否决。后台的恢复没有这样的界线（删除也没有）：节点多于 `MaxJobItems` 的恢复任务，它的变更集撤销时答 422，再删一次恢复回来的根也是一样。

### 4.10 后台的恢复与撤销（transfer）

- 接口：`POST /notebooks/{notebook_id}/trash-restores`（`{node_id}`）、`POST /notebooks/{notebook_id}/reverts`（`{changeset_id}`），答 202 与任务；任务的类型 `trash_restore`、`revert`。权限与同步的相同（`node.restore`、`changeset.revert`）；一本笔记本同时一个写入的任务（与导入共用，`transfer.busy`）；排队的上限（`server_busy`）；队列与导入的相同。任务的状态机、心跳、启动时的收拾、取消、清理都沿用（M7 4.9、4.12）。
- **分批**：沿用导入的分批（`transfer/app/import_write.go` 的批的上限、按预算的退避、`ANALYZE`），抽出给三种任务共用；每批一个单元，并入任务的变更集（它的 id 建行时定下，第一个写了东西的单元以它建；`UnitSpec.Changeset`、`Create`），批之间放开笔记本的锁。批照导入的上限切（100 个节点、8 MiB 正文、20,000 条链接，可注入），写回的历史至多 `MaxUnitHistory`（page 在每批解析之前数，多于一步而超过时答 `ErrBatchTooLarge`、transfer 把批减半，同链接）；单独超过的一步自成一批，包括一页自己的历史超过 `MaxUnitHistory` 的（一页的版本与条目若与节点分开恢复，中途停下时已删的节点带着活着的版本与条目、或活着的页缺版本，都不对；这一页的删除也曾在一个单元里提交）。M8 的任务里一页的正文至多写一次（撤销的单轮每页至多一步写回，恢复不写版本，导入每页建一次），所以没有两批写同一页的正文；批之间别人写过这一页时，后一批的再计划以冲突停下；`RecordRevision` 的版本链守卫（M8/P1 审查 C4）照旧是最后的防线（[P4](04-P4-background.md) 2.1 第 1 条）。
- **恢复的任务**：先恢复根（决定位置与名称），之后按组的深度优先先序（孩子按次序值与 id，父节点总在孩子之前，同名先到的留名不变）：一批恢复先序里连续的一段，要设上根的只有这一段右边缘上各祖先余下的孩子，每批设根的数与途中停下时剩下的项数都约是"层数 × 扇出"。计划不加锁、只留骨架（id、父节点、类型、正文大小、组内统计），每批按 id 读这一批的成员。第一批在锁下核对根仍以这一时刻删除、仍是根、统计等于计划读到的（组里不是根的节点谁也改不了：恢复只认根，撤销一次删除要根与统计相符，清理被期限的间隔挡开）；之后每批在锁下核对：只恢复仍是这一时刻删除的（别人可能已经恢复了其中设上根的一项，跳过）、父节点活着（不然停下，`tree_changed`）、层级（超过时停下，`tree_changed`）、名称（与活着的兄弟冲突时加序号：分批之间别人可能在已恢复的父节点下建了同名的页，A-I5）、期限（不然停下，`restore_expired`）。已恢复的父节点之下仍在回收站的节点在同一个单元里设上 `trash_root` 与准确的统计：任务停下时它们各自列出，可以逐项恢复。历史的界线见上一条，不按历史的行分批（[P4](04-P4-background.md) 2.1 第 2 条、3.4）。
- **撤销的任务**：开始之前（请求里，不加锁）照 4.14 的次序核对一遍：条目超过 `MaxJobItems` 答 422，之后答 `transfer.busy`，再对 S\* 核对，有冲突就照 4.8 答 409，计划要删或写回的页正被别人编辑就答 409 `page.locked`（第 11 节第 3 条），都不开任务；任务开始时的计划再核对一遍（这期间的冲突与锁让任务什么都没写就停下）。之后按计划的单轮的步切批：放回一个节点；删除一个最上层（连同它的子树在一个单元里以单元的时刻删除，同 `Unit.Delete`：任何一次停下，每个最上层要么整棵还在、要么整棵在回收站里；撤销一次导入之后，回收站列出的是导入的最上层节点）；恢复组里的一个节点；写回一页。每批在锁下以只含这一批的步的节点的状态再跑 `PlanRevert`；一组要恢复的节点超过一批时同恢复的任务那样按先序分批，第一批带着整组再计划，之后各批的成员（续段）不进再计划、逐个核对，冲突照撤销的原因、不加序号（第 11 节第 6 条），读者先恢复了、正在它"前"的位置上的跳过，冲突的成员之下的成员不另列（P4A 审查 A-M3）。一组在计划之后被恢复又删除时，开始它的那一批按这一组现在的删除时刻读（A-M1）。第一个冲突、第一个被锁的页就停下。途中停下时已撤销的部分留着（不是整组的），报告写明已撤销的、停下的原因与冲突的节点（[P4](04-P4-background.md) 2.1 第 3–5 条、3.5）。
- **报告**：恢复的任务报恢复的页数、附件数、改名数、跳过数与根放在哪里；撤销的任务报恢复、删除、放回的节点数与写回的页数，冲突的节点（同撤销的原因与 `name`、`holder_id`，至多 100 项与总数，只在单个任务的读里），被锁的页与持锁人；停下的原因；剩下的数目是进度的总数减已处理的。新的失败：`trash_changed`、`restore_expired`、`revert_conflict`、`changeset_trimmed`、`page_locked`。任务行记 `changeset_id`（建行时定下，导入同样记，网页给出"在历史里查看"）、撤销的 `target_changeset_id` 与说明；撤销的任务的 `name` 是被撤销的变更集的类型。任务列表在笔记本设置的"导入、导出与恢复"（原来叫"导入与导出"），按类型显示（[P4](04-P4-background.md) 2.1 第 7 条、3.6）。

### 4.11 清理与恢复、撤销的先后

清理按时钟删 `deleted_at` 早于"现在减去保留期"（`jobs.purge_retention`，默认 60 天）的行，附件先删文件，页面的表逐表各自提交（条目 → 版本 → 正文 → 节点）。恢复（同步的、任务的每一批、撤销里的恢复）只认 `deleted_at` 晚于"现在减去保留期再加 1 小时"的组：清理与它们从不碰同一批行，不用在每张表上锁行、数行（M7 的移交第 2 项设想的 `FOR UPDATE` 由这一小时的间隔代替；M7 设计 4.6"M8 的恢复锁同样的行"随之改写）。

- 保留期的下限从 1 小时改为 1 天（`validate`），否则一小时的间隔会让回收站永远是空的（A-M6、C-M4）。
- 一小时的间隔假设实例的时钟由 NTP 校准、只有一个实例（总体设计第 11 节：单实例），与 13.1 第 6 条孤儿清扫的假设相同。
- 回收站显示 `restorable_until`（保留期减 1 小时），`InstanceInfo.trash_retention_seconds` 给的同样是可以恢复的期限。
- 清理任务的时钟不改为可以注入（不加 `PurgeConfig.Clock`）：期限两侧的交错测试直接调用清理器、自己给截止时刻，不经 `PurgeJob`；期限的边界（恰在期限的那一刻不能恢复）在 page 的用例里以假的时钟测。
- 撤销的任务的续段（一组跨批时之后各批的成员）的版本在计划之后被清理拿走：答 `changeset_trimmed`，同计划时读不到的版本（P4A 的交错 17 找到的缺陷）。
- 防线：正文行、版本链与附件行的数目在恢复的单元里核对（4.6）。

### 4.12 搜索

方案由 spike（2026-10-13，30 万页的中英语料）实测选定，负责人 2026-10-14 定下三个问题（第 11 节第 10 条），P5A 在同一份语料上以产品的代码再实测（[P5](05-P5-search.md) 3.9）；DDL、SQL、界线与数字在 P5 第 3 节。

- **索引**：应用（Go）算的词存在侧表 `page_search` 的两个 `tsvector` 列里，各有 GIN 索引，每个活着的节点一行，记下分词的版本（规则的版本、Go 与 x/text 的 Unicode 版本，P5 3.2、3.3）：
  - 标题：CJK 的单字与二元组；正文（名称加正文，只有页）：CJK 的二元组，不收单字。
  - 字母文字（含数字与组合记号）3 个及以上：三元组（子串；P5A 实测定下，词的前缀在常见的词上 2.5–3.7 秒）；1–2 个：整词。
  - 不进索引：超过 64 个的 ASCII 字母与数字的连续串（base64、十六进制一类；别的文字的长段照常，泰文、老挝文、高棉文、缅甸文词之间不留空格）；长于 64 个字符的 `data:` 串，到第一个 data 地址不会有的字符为止；一行的词的字节之和至多约 1 MB（约 2 MB 以上的中文才到，语料里没有）。
- **维护**：单元在事务里只把碰过的节点（新建、恢复、改名、写正文、删除）放进 `page_search_queue`；page 的 River 定时任务（自己的队列 `page_search`，同时只有一个）在请求之外重建行，先做准确的、后做批量的。用户在请求里的写是"准确"的；导入、后台的恢复与撤销的单元、迁移的补入与 `nervewiki reindex` 是"批量"的（P5 3.4）。任务的一次运行在它取 advisory lock 的那一个连接上、只试一次，启动时丢掉停下的服务留在运行中的行；它的写在自己的事务里以 `work_mem` 64 MB、待处理列表 16 MB。
- **读**（P5 3.5）：
  - 候选是索引的命中加上队列里准确的节点，连活着的节点、限看得到的笔记本；批量的节点不当候选，答复带 `building`，结果页写明"索引正在建立，结果可能不全"。
  - 正文层的命中经迁移里的函数 `page_search_hits` 只从 GIN 的位图读（它的设置关掉表的别的读、`work_mem` 64 MB），以同一快照里数出的命中数作 `LIMIT`，即规划器的估计；候选只带笔记本的条件连 `nodes`，别的检查在 `OFFSET 0` 之上。照写的语句在建索引中与待处理列表满时整表扫描 `page_search`、逐行解压正文，5–40 秒。
  - 两层：每个词都在名称里的在前（名称在排序之前检查）；其余的页在后，按 `(最后改动, id)` 倒序，每次请求至多走查 `MaxSearchWalk` = 500 个页的正文，对当前的名称与正文复查（PostgreSQL 的正则，大小写由 Go 按简单折叠的轨道写进模式；不是 NFC 的正文按它的 NFC），一页可能少于 `limit` 个而带"继续查找"的游标。
  - 所以用户的写按已提交的状态是准确的：删除之后立即消失，恢复、新写的立即找到。例外：不进索引的部分，与大小写的折叠改变了之后一个组合记号怎样组合的少数字符（P5 3.3），只在节点排队时找得到。
  - 一次请求的语句在一个只读事务里。
- **查询的语义**：单个汉字只搜名称；几个被标点隔开的单字的词（`中·国`）在名称或正文里，只在整个查询都没有正文的键时只搜名称；汉字 2 个起、字母与数字 3 个起按子串；字母与数字 1–2 个按整词（汉字算边界）；几个词各在名称或正文里、全部命中，折叠相同的词是一个；大小写对称地不敏感；全角与半角、繁简、重音不互通。
- **计数**：只在第一页，按层估：名称层定下时不数正文层；正文层的比例取走查的，走查因这一页满了停下时取 (k − 1) / (n − 1)，第一页没走到正文层时另取样 100 个。种类 `exact`（第一页拿到每一个命中，或只在名称里找）、`about`（约数，两位有效数字）、`at_least`（下界：1,000 总是它，"1,000+"；比例依据的通过少于 2 个而还有没查的（页满停下时最后一个不算）、候选多得数不完时也是）。
- **摘要与高亮**：摘要在 SQL 里只为答出的行切（命中处之前 40、共 160 个字符），高亮的区间由服务端以 UTF-16 码元给出、排好且不相交。
- **界线**（P5 3.9 的规则）：`MaxSearchWalk` = 500、`MaxSearchCountScan` = 20,000、`MinSearchRebuild` = 30 秒，名称层不设界线，GIN 的 `fastupdate` 开。

### 4.13 前端

- **右栏"页面信息"**加"版本"一节：最近的版本（时刻、执行者、类型；"编辑中"的标记；当前的一行没有"还原"），"更多"读下一页；点开进版本页。列表写明"一次编辑一个版本"。锁的状态仍在中栏（总体设计 9.2 随之改）。

- **历史页** `/:slug/notebooks/:id/history`：日志，筛选在地址里（人、客户端、页面；地址里的 id 读时转成小写），人从工作区成员、日志里出现过的执行者与地址里点名的账户里选，每条可以"只看此人"（同显示名的带邮箱或编号区分，按下之后焦点在"谁"上）；每条带"已撤销""已截掉"的标记；"更多"读到的一页写进它开始时的那个键，这期间换了筛选也回到它读的列表（[P3](03-P3-log-revert.md) 4.2）。**单个变更集页** `/:slug/notebooks/:id/history/:changesetId`：信息、明细（分页）、写者的"撤销"（确认框，发送中"撤销"`aria-disabled`、焦点留在它上面；冲突时列出每个节点与原因，原因各有可以去做什么的说明：`changed` 链到这个节点的历史、`title_taken` 链到占着名称的页并说明回收站的恢复会加序号、`parent_gone` 指向回收站；422 时说明太大，问是否在后台撤销（"在后台撤销"开一个撤销的任务，状态行"已开始……查看进度"链到任务列表的那一行；后台也撤销不了时说明；冲突时这本笔记本有进行中的写入任务，冲突之前说冲突可能因它而起、等它结束或取消；这一开始的答复丢了时重读任务列表找这次的任务：这个账户这种类型与目标的，进行中的不论时刻，已结束的只取按下时没持有、创建不早于按下之前一分钟的，不比两个时钟；晚到的结果不盖掉之后一次说过的，[P4](04-P4-background.md) 4.2）；答复丢了（500、网络错误、超时）时说"结果未知"，经 store 重读这次改动，按它最新的撤销说出已撤销、已被别人撤销或没有撤销，这次改动重读不到时才说不知道）。撤销之后单个变更集页的 `h1` 取得焦点、经 `aria-describedby` 读出状态行，读者其间有动作时不动（13.2 第 26 条）。页面的菜单（读者也有）加"查看这一页的历史"；版本页的"执行者 · 类型"链到它的变更集页。

- **搜索**（[P5](05-P5-search.md) 4.2–4.4）：工作区左栏顶部的搜索框（顶栏在工作区之外），带范围的提示，回车进结果页 `/:slug/search?q=&notebook_id=`（在笔记本里打开时默认限定这一本）；输入法组合中的回车与快捷键不生效；快捷键 `Mod+Shift+F` 用新的判断（`isMod` 拒绝 Shift），它在微软拼音、搜狗、fcitx 里是简繁切换，所以还有看得见的入口，并进输入法清单；结果页有范围的选择、约数、"继续查找"与"索引正在建立"的说明；摘要以文字放在 `<bdi>` 里，只高亮服务端给的位置（`<mark>`）；不随事件、焦点、重连重读，再提交同样的搜索时重读，后退显示缓存。
- **列表的模式**：回收站、日志、明细、版本列表的项会变或消失，用 `readPages` 那种"按已读的页数重读"（13.2 第 19 条），不用审计记录的"保留已读的尾巴"；"更多"接上的一页经共用的 `readNext` 写进"更多"开始时的那个键（五个列表共用，加搜索的结果；P3B 审查 C-M1）。
- **事件**：回收站只在 `tree: true` 时重读；版本列表在事件点到这一页（或 `pages` 为空）时重读；历史（日志、单个变更集与明细）在任何 `pages` 事件之后按 `refresher` 的间隔（5 秒）重读；版本的阅读视图在 `links` 事件与 `tree: true` 时重读；连上时重读已缓存的这些键（`refreshedOnConnect`）；本标签页离开编辑之后更新这一页的版本列表（每次自动保存由事件更新）；锁的事件、锁的租约到期时重读列表与编辑中的版本。
- **删除确认框**（页面与附件两个）改写："移到回收站，N 天内可以恢复；能读这本笔记本的人在回收站里仍看得到它"（N 由 `InstanceInfo`，可以不是整数天：向下取整，不把期限说长，不满一天写小时）。
- **无障碍与文字**：每个列表有名称；行上的按钮带对象（"恢复「X」（原位置：A / B）"），同名的项区分（回收站：同名同位置的带删除时刻，到分钟也相同的再带 id 的末六位；历史：同一分钟同类型、执行者的显示名相同的行与冲突里同名的节点带 id 的末六位）；焦点的去向与礼貌的播报（"已开始恢复""已撤销"、结果数）；每个新页面设文档标题。英文里 撤销 写 "Undo change"、还原 写 "Restore this version"；`mcp:<名>` 显示为 "MCP（名）"；英文不用复数形式（照现有的写法）。

### 4.14 权限、码的次序、上限、加锁与交错

- **新的动作**（规则表与矩阵各一行，`server/internal/bootstrap/actions_test.go` 的"规则 = 动作"）：`page.history`（版本、日志、单个变更集、明细、回收站的列表与单项，读者）；`page.restore_version`（写者）；`node.restore`（写者；同步的与后台的恢复）；`changeset.revert`（写者；同步的与后台的撤销；撤销别人的变更集不另要管理员）；`page.search`（工作区级，每种角色）。
- **码的次序**（13.1 第 4 条，契约与测试照这个次序）：
  - `revertChangeset`：取值 422（`message`）→ 404 `page.changeset_not_found` → 403 → 409 `page.changeset_trimmed` → 422 `page.revert_too_large`（条目数；读条目与版本之后再读变更集：不在了时，笔记本这期间被删或调用者的角色没了，照第一次的读答 404 或 403，否则是清理拿走了它，409 `page.changeset_trimmed`，P3A 审查 B-F2；然后页数与字节、历史的行）→ 409 `page.revert_conflict`（解析之前未加锁地对 S\* 核对一遍：冲突的撤销不去占解析的预算，P4 开任务之前同样要这一遍）→ 422 `page.revert_too_large`（单轮的步数，计划之后才知道，4.9）→ 503 `server_busy`（预算）→ 锁下再核对（409 `page.changeset_trimmed`：锁下变更集不在只能是清理；422 `page.revert_too_large`：条目数；409 `page.revert_conflict`；409 `page.changeset_trimmed`：读不到的版本；422：步数；409 `page.revert_conflict`：解析过的正文不是锁下要写的）→ 409 `page.locked`。C 删除的每一组先核对根（在回收站里、是根、根上记下的页数与附件数等于 C 删除的、它与它之下的页面与附件），不符的不读组、算 `changed`：组的大小只对确是 C 的那一组答 422。照 `restoreNode` 有两个例外：链接数的 422 要解析之后才知道，可能排在 503 之后；要比较的版本或要写回、恢复的正文未加锁时已被清理拿走，答 409 `page.changeset_trimmed`，排在 422 与冲突之后、503 之前：版本的在步数的 422 之前（读不到版本时计划没有步），正文的在它之后。撤销里的恢复撞上防线（`RestoreNodes` 的计数、附件的行数）答 409 `page.changeset_trimmed`，不是契约之外的 `page.trash_changed`；单元里别的已分类的错误（名称被占、版本号不符）在撤销里是缺陷，答 500（[P3](03-P3-log-revert.md) 3.6）。
  - `restoreNode`：404 `page.not_found` → 403 → 409 `page.not_in_trash`、`page.not_trash_root`、`page.restore_expired` → 422 `page.restore_too_large`（节点数，按记下的统计；页数、字节；历史的行，4.9）→ 503 → 409 `page.trash_changed`（锁下的核对与观察者）、`page.restore_expired`（单元以它的时刻再核对）。两个例外，契约写明：链接数的 422 要解析之后才知道，可能排在 503 之后（4.9）；未加锁时这一组有页的正文已被清理，在解析之前答 409 `page.trash_changed`（空的正文不能解析），排在 422 之后、503 之前（P2A 审查 B-3）。两次未加锁的读之间这一项被恢复了答 409 `page.not_in_trash`，读组时是 `page.trash_changed`。
  - `getTrashItem`：404 `page.not_found` → 409 `page.not_in_trash`、`page.not_trash_root`、`page.restore_expired`。
  - `restorePageVersion`：404 `page.not_found`、`page.version_not_found` → 403 → 503 → 409 `page.revision_mismatch` → 409 `page.locked`。
  - `searchWorkspace`：绑定的 400 `bad_request`（`notebook_id` 不是 UUID、`limit` 不是整数）→ 400 `bad_request`（游标）→ 422 `validation_failed`（`q`：自由文字，在找工作区之前）→ 404 `workspace.not_found`（没有、不是成员）→ 404 `notebook.not_found`（`notebook_id` 看不到）→ 422 `validation_failed`（`limit`）。没有 403（[P5](05-P5-search.md) 3.6）。
  - `startTrashRestore`：404 `notebook.not_found` → 403 → 404 `page.not_found` → 409 `page.not_in_trash`、`page.not_trash_root`、`page.restore_expired` → 409 `transfer.busy`（从这里到写行占住笔记本，同导入的上传）→ 503 `server_busy` → 事务里再判定、写行。没有 422。
  - `startRevert`：取值 422（`message`）→ 404 `notebook.not_found` → 403 → 404 `page.changeset_not_found` → 409 `page.changeset_trimmed` → 422 `page.revert_too_large`（条目超过 `MaxJobItems`）→ 409 `transfer.busy`（读任何东西之前）→ 读条目、组与树（不在了时照第一次的读答 404 或 403，否则 409 `page.changeset_trimmed`；P4A 实测不要 `MaxJobGroups`，没有组的 422）→ 409 `page.revert_conflict` → 409 `page.changeset_trimmed`（读不到的版本）→ 409 `page.locked`（计划要删或写回的页，第一页）→ 503 → 事务里再判定、写行。`revertChangeset` 与它共用这一遍核对，界线作参数留在上面的位置（[P4](04-P4-background.md) 3.5、3.6）。
- **上限**（13.1 第 31 条，测试在上限处）：`conflicts` 至多 100 项；`reverted_by` 至多 100 个；日志的计数至多数到 1,000（回收站的数目是删除时记下的准确值，4.2）；`q` 的字节、词数与词里连续的 ASCII 字母与数字（至多 64 个）；搜索的 `limit` 1–50、每次请求至多走查 `MaxSearchWalk` = 500 个页的正文、计数至多到 1,000；版本、日志、回收站、明细的分页照 `limit` 的上限。
- **加锁**：还原版本是正文的写（笔记本 `FOR SHARE`、正文行 `FOR NO KEY UPDATE`）；恢复与撤销是树的单元（笔记本行 `FOR NO KEY UPDATE`，同一笔记本的树写串行），撤销里的正文写按页 id 的次序锁正文行（13.1 第 5 条）。后台任务的每一批是树的单元，批之间放开笔记本行；两个开始从忙的核对到写行占住笔记本（同导入的上传）。读不加锁。搜索的队列 `page_search_queue` 的行在单元全部的写之后、观察者之前取，每条入队的语句按 `node_id` 升序（单元、笔记本删除、reindex）；搜索的任务只写 `page_search`、出队 `SKIP LOCKED`，从不等（P5 3.8）；一次运行的语句都在它取 advisory lock 的那一个连接上，连接池的规则算上这个连接（默认的配置下 `max_conns` 至少 6，P5 3.4）。
- **日志**（13.1 第 10 条）：新用例只记 id 与数目，`q` 与冲突里的名称不进日志；搜索语句的错误只记 SQLSTATE（PostgreSQL 的消息会带上模式与 `tsquery`，即用户的文字）。
- **交错**（确定性的测试，结束时核对不变式）：恢复与删除它原来的父节点；恢复与在原位置新建同名的页（序号）；撤销与对其中一页的并发写；撤销时其中一页被锁（M5 的移交第 3 项）；撤销与清理截掉 C（先读条目、后读 `trimmed`）；恢复与清理（期限两侧，测试给清理的截止时刻，4.11）；恢复附件的行与附件的清理（M7 的移交第 2 项）；后台的恢复与撤销的任务与批之间的各种写（[P4](04-P4-background.md) 3.10 的 20 种与修复时加的一种（一组在计划之后被恢复又删除）：删除或移深已恢复的部分、在已恢复的父节点下新建同名、同步恢复设上根的项、清理与期限、撤销自己的或原来的变更集、编辑锁、删除笔记本、上传与开始、每个批的边界上停下）；撤销正在被导入任务并入的变更集；还原版本与编辑会话的保存；搜索的索引的 9 种（[P5](05-P5-search.md) 3.8：任务读了之后的保存、写行时删除、删除之后恢复、单元持着队列的行、删除笔记本、reindex 的入队对删除子树、导入的两批之间、任务停着时清理、两个任务）。

### 写给后面的 M

由发现它的 Phase 写进目标 M 的 `handoffs/`，收尾时核对：

- **M9**：`log` 调用 `ListChangesets`（筛选与游标已备）；`grep` 用 4.12 的索引（从正则的字面片段取键、候选并上队列里准确的节点、SQL 里以正则复查；字母文字定为三元组，字母与数字的子串 3 个起都取得出键；[M8/P5 的移交](../M9-mcp/handoffs/M8-P5-search.md)）；`batch` 写 `message`；一个单元里删除再恢复同一节点时 `RecordItem` 的 upsert 会清掉条目的 `deleted_at`（M4 的移交第 3 项）；batch 的撤销要的多轮应用、临时名称、一页既要恢复又要写回正文、一页先写正文再删除，单轮的步数界线同样适用（[M8/P3 的移交](../M9-mcp/handoffs/M8-P3-revert.md)）；`transfer_jobs` 的客户端只许 `web`、`api`，MCP 开的后台任务要先改它，`batch` 的大变更集的撤销同走后台（[M8/P4 的移交](../M9-mcp/handoffs/M8-P4-background.md)）；要不要给 agent 历史、撤销与恢复的工具（总体设计 5.3"失败的 ingest 可以整组撤销"）。

- **M11**：回滚一次升级 = 按时间从新到旧逐个撤销它的变更集（按状态比较，连续撤销成立）；冻结与护栏经 `Write.Kind` 放行回滚的撤销；冲突时停下并报告；大的变更集走后台的撤销，停下时：没停在一组中间的，撤销那次撤销回到之前、再整组撤销；停在一组中间的，逐项恢复剩下的，不要先撤销那次撤销（[P4](04-P4-background.md) 3.5）；撤销任务正在写时不在请求里撤销它的变更集（[M8/P4 的移交](../M11-upgrade/handoffs/M8-P4-background.md)）。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 中文搜索的延迟与索引体积，保存时维护索引的开销（总体设计 14） | spike 实测选定方案（4.12），P5A 在产品的方案上再实测（[P5](05-P5-search.md) 3.9），字母文字定为三元组；保存只入队（保存的 p50 多 0.3–0.5 ms），行由后台的任务重建。重的类（几万个命中）的第一页在 30 万页上 p99 至多约 0.7 秒，建索引与积压时至多约 1.2 秒：接受、移交 M12。剩下的局限：一页不同的词的字节超过约 1 MB（约 2 MB 以上的中文）时超出的部分、超过 64 个的 ASCII 字母与数字的连续串、长的 `data:` 串不进索引，只在排队时找得到（泰文等的长段照常进索引）；繁简、重音、全角与半角不互通，ß/ss 这类完全折叠的差别（不是 NFC 的正文按它的 NFC 读，只差基本字母的找不到）；导入、后台的恢复与撤销、升级、reindex 之后建索引期间结果可能不全（页上写明）；命中不按范围，小的工作区的搜索也读整个服务器的命中（M12） |
| 撤销的次序值比较：兄弟被重新编号过时显示为冲突 | 重新编号要连续约 30 次插在同一个间隔里才发生；冲突的说明链到这个节点的历史；精确的做法（条目记前一个兄弟）写进 M12 的移交 |
| 撤销改名之后，C 之后新写的指向新名称的链接断开 | 写进总体设计 4.5 与第 11 节；冲突时提示"改回原名"（会改写链接） |
| 大的恢复与撤销是分批的，途中停下时不是整组的 | 开始之前一次核对全部；每批在锁下重新核对；报告写明已完成的部分；停下的状态是一致的：恢复剩下的各自是回收站的一项；撤销的任务没停在一组中间时，它的变更集撤销之后可以再整组撤销，停在一组中间时逐项恢复剩下的就完成这一组（[P4](04-P4-background.md) 3.5） |
| 一次几万个条目的导入的撤销耗时长、占队列 | 后台任务分批，批之间放开锁；与导入共用"一本笔记本一个写入任务"，一个长的导入会让恢复排在它之后（任务列表里看得到） |
| 清理期的边界上恢复与清理相遇 | 一小时的间隔，假设时钟由 NTP 校准、单实例；正文行与附件行的数目作为防线 |
| 清理同时锁条目与变更集：长时间并入的变更集上的条目要等下一次清理 | 清理从不等待（`SKIP LOCKED`），下一次运行再删 |
| 冲突的列表很长（被改过的几万个导入的节点） | 至多 100 项与总数 |
| 浏览器里比较 5 MiB 的正文 | Web Worker、硬性的期限与上限，超过时并排显示 |
| 版本与回收站对读者可见：粘贴进页面的秘密删不掉 | 第 11 节第 1 条，负责人可以改判（限制给写者，或允许管理员永久删除）；永久删除写进 M12 的移交 |

## 11. 负责人确认的决定

M8 开工时负责人确认进入 M8（2026-10-13："可以了，开始 M8 吧"；输入法清单留到最后统一验收），之后确认按初稿推进（2026-10-13："可以，按你的设计继续推进"）。搜索的三个问题（spike 之后）负责人 2026-10-14 答复"搜索三个问题都按你的建议来"：单个汉字只搜标题；字母文字 3 个及以上按子串（三元组：向负责人提问时推荐的，spike 量的是词的前缀，P5A 先实测，不达标时退回词的前缀，两种都不达标才再问），1–2 个按整词；结果的数目是约数（第 10 条，[P5](05-P5-search.md) 2.1 第 1 条）。下面是设计里的取舍，负责人可以改判：

1. 回收站与历史对读者可见（读者删除之前就读得到这些页）；v0.1 不能永久删除回收站的一项或一个版本，粘贴进页面的秘密只能等清理期（回收站）或一直留在版本里。
2. 恢复、还原、撤销要写者；撤销别人的变更集不另要管理员。
3. 整组撤销碰上被编辑的页整体拒绝（`page.locked`，只列第一页），不跳过。
4. 撤销不经链接改写的参与者：C 改写过的页逐字节写回；C 之后新写的指向新名称的链接不跟着改回。
5. 撤销按状态比较，次序值也比：之后的重新排序与（罕见的）兄弟重新编号都算冲突。
6. 撤销删除时放回原位置，放不回就冲突；回收站的恢复则改放根下或加序号。
7. 超过一个单元的恢复与撤销在后台分批进行，不是整组的：途中停下时已完成的部分留着；与导入共用每本笔记本一个写入任务的限制与队列。
8. 被清理截掉过的变更集整个不能撤销。
9. 回收站里的附件预览不给下载地址，恢复之后再下载；不能只恢复一个被删子树里的一页。
